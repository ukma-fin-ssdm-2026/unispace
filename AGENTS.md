
# AGENTS.md — правила для AI-агентів UniSpace

Цей документ визначає контекст і правила роботи AI-асистентів у репозиторії UniSpace.

Перед внесенням змін необхідно ознайомитися з актуальними `README.md`, `TeamCharter.md`, `Project-Description.md`, вимогами та кодом проєкту. Якщо документація суперечить реалізації, потрібно повідомити про невідповідність у відповідному Issue або PR.

## 1. Призначення системи

UniSpace — система керування університетськими аудиторіями, яка працює поверх системи САЗ.

САЗ залишається джерелом інформації про дисципліни, академічні групи та час занять. UniSpace відповідає за розподіл аудиторій, бронювання, перевірку конфліктів, пошук альтернативних приміщень і сповіщення користувачів.

До меж проєкту не входять:
- Редагування академічного розкладу в САЗ.
- Зворотний запис змін до САЗ.
- Мобільний застосунок.
- SMS/push-сповіщення без окремої погодженої вимоги.
- Облік відвідуваності або ремонтів аудиторій.

Важливо розрізняти заплановану функціональність і фактично реалізовану. Наявність моделі або API-ендпойнта не означає, що відповідний бізнес-сценарій повністю працює.

## 2. Технічний стек і структура проєкту

### Backend
- Python 3.12.
- Django 5.2.x.
- Django REST Framework.
- drf-spectacular для генерації OpenAPI.
- PostgreSQL для інтеграційних перевірок і розгортання.
- SQLite може використовуватися локально, але не замінює PostgreSQL для перевірки специфічних обмежень бази даних.

Основні директорії:
- `Backend/api/models.py` — моделі даних.
- `Backend/api/views.py` — API views.
- `Backend/api/serializers.py` — серіалізатори.
- `Backend/api/urls.py` — маршрути API.
- `Backend/api/services/` — сервісний шар.
- `Backend/api/tests/` — автоматизовані тести.
- `Frontend/` — окремий Django-проєкт фронтенду.

Залежності:
- `Backend/requirements.txt`
- `Backend/requirements-dev.txt`
- `Frontend/requirements.txt`
- `Frontend/requirements-dev.txt`

Актуальні версії бібліотек необхідно перевіряти у файлах залежностей, а не припускати.

### Автентифікація та ролі

UniSpace використовує кастомну модель користувача `api.User`.

Основні ролі:
- `student`
- `teacher`
- `dispatcher`

Інтеграція з Microsoft Entra ID реалізована через MSAL.

AI-агент не повинен замінювати поточну систему ролей стандартними Django-групами без погодженого архітектурного рішення.

## 3. Вимоги та простежуваність

Перед реалізацією нової функціональності потрібно перевірити:
1. Відповідну User Story.
2. Функціональні та нефункціональні вимоги.
3. Acceptance Criteria.
4. Матрицю простежуваності `docs/requirements/rtm.md`.
5. План тестування `docs/validation/test-plan.md`.

Не можна вигадувати ідентифікатори вимог або прив'язувати тести до неіснуючих FR/NFR.

Для нової функціональності необхідно передбачити:
- Позитивні сценарії.
- Негативні сценарії.
- Граничні значення.
- Перевірку прав доступу.
- Відповідні рівні тестування.

Тести повинні перевіряти очікувану поведінку, а не лише підтверджувати поточну реалізацію.

## 4. Локальний запуск і перевірки

Для роботи з Backend:

```bash
cd Backend
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt -r requirements-dev.txt
```

Перед запуском необхідно налаштувати локальні змінні середовища, зокрема `SECRET_KEY` та підключення до бази даних.

Основні перевірки:

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py migrate --noinput
python -m pytest -q --cov=api --cov-branch --cov-fail-under=75
python -m black --check .
python -m flake8 .
```

Перевірки безпеки:

```bash
python -m bandit -r . -c bandit.yaml
```

Для тестування конкурентних бронювань необхідно використовувати PostgreSQL, оскільки SQLite не забезпечує еквівалентну перевірку PostgreSQL-specific constraints.

CI налаштований у `.github/workflows/ci.yml`.

Перед створенням PR потрібно перевірити, що відповідні тести, форматування та лінтинг проходять успішно.

Зелений CI не гарантує відсутності логічних помилок або повного покриття бізнес-вимог.

## 5. Правила реалізації

AI-агент повинен:

1. Спочатку вивчити відповідну вимогу та існуючу реалізацію.
2. Не створювати дублікати вже реалізованих функцій.
3. Використовувати наявну архітектуру та домовленості команди.
4. Перевіряти коректність імпортів і залежностей.
5. Не додавати невикористані функції, класи або імпорти.
6. Передбачати обробку реалістичних помилок.
7. Не змінювати публічний API без перевірки сумісності.
8. Оновлювати тести разом зі змінами поведінки.
9. Не змінювати міграції чи схему БД без обґрунтування.
10. Документувати архітектурні рішення, якщо зміни впливають на структуру системи.

Для операцій бронювання особливу увагу потрібно приділяти:
- Перевірці доступності аудиторії.
- Недопущенню подвійних бронювань.
- Перевірці місткості.
- Транзакційності.
- Авторизації.
- Аудиту змін.
- Коректній обробці конфліктів.

Заборонено комітити `.env`, паролі, API-ключі, токени, віртуальні середовища та локальні бази даних.

## 6. Огляд коду, згенерованого ШІ (Lab07)

Код, створений за допомогою AI-асистента, повинен проходити ті самі перевірки, що й код, написаний вручну.

Додатково для AI-generated code review використовується контрольний список із п'яти пунктів.

### 6.1. Залежності

Перевірити, що:
- Усі імпортовані бібліотеки існують.
- Залежності зазначені у відповідних файлах.
- Шляхи імпорту відповідають структурі проєкту.
- Відсутні невикористані імпорти.

### 6.2. Обробка помилок

Перевірити:
- Невалідні вхідні дані.
- Відсутні об'єкти.
- Помилки бази даних.
- Конфлікти бронювань.
- Недостатні права доступу.
- Інші реалістичні сценарії відмов.

Не можна обмежувати перевірку лише happy path.

### 6.3. Відповідність вимогам

Переконатися, що:
- Реалізація відповідає FR/NFR.
- Поведінка узгоджується з Acceptance Criteria.
- Тести відповідають тест-плану.
- Логіка не містить прихованих відхилень від вимог.

Код, який виглядає правильним, не обов'язково є правильним.

### 6.4. Мертвий код

Перевірити відсутність:
- Невикористаних функцій.
- Недосяжних гілок.
- Зайвих допоміжних класів.
- Дублювання логіки.
- Непотрібних імпортів.

### 6.5. Розуміння автором

Рецензент повинен поставити автору PR щонайменше одне предметне запитання про:
- Логіку реалізації.
- Архітектурне рішення.
- Обробку помилок.
- Компроміси або альтернативні підходи.

Автор має пояснити ключові рішення власними словами.

До отримання відповіді цей критерій не вважається виконаним.

### Документування результатів

Результати огляду записуються в:

`docs/validation/review-log.md`

Для кожного оглянутого PR потрібно зазначити:
- Посилання на PR.
- Автора та рецензента.
- П'ять пунктів контрольного списку.
- Конкретні знахідки з посиланнями на код.
- Питання автору та його відповідь.
- Рекомендації щодо виправлення.
- Підсумковий статус огляду.

Для коментарів використовуються позначки:
- `Blocking` — проблема, яку потрібно виправити до merge.
- `Nit` — незначне покращення.
- `Question` — уточнення для автора.

Не можна позначати перевірку успішною без фактичного підтвердження.

## 7. GitHub Flow

Усі зміни виконуються через Pull Request.

Рекомендований процес:
1. Оновити локальну гілку `main`.
2. Створити окрему feature/fix/docs-гілку.
3. Внести зміни.
4. Запустити відповідні перевірки.
5. Створити PR з описом змін.
6. Дочекатися зеленого CI.
7. Отримати схвалення щонайменше одного іншого учасника команди.
8. Злити PR у `main`.
9. Закрити пов'язаний Issue після виконання його критеріїв прийняття.

Не можна обходити branch protection або зливати неперевірений код.

## 8. Використання ШІ

Використання AI-асистентів дозволене за умови прозорості та людської верифікації.

У PR необхідно вказувати:
- Для яких завдань використовувався ШІ.
- Які файли або частини коду створено за його допомогою.
- Які перевірки виконано людиною.
- Які обмеження або ризики залишилися.

Заборонено стверджувати, що тести або перевірки пройдені, якщо вони фактично не запускалися.

AI-асистент допомагає створювати та аналізувати код, але відповідальність за правильність, безпеку й підтримуваність залишається за командою.
