# AGENTS.md — інструкції для AI-агентів у репозиторії UniSpace

Цей файл — контекст і правила роботи для AI-асистентів (Claude, GitHub Copilot,
Gemini, Codex тощо), яких команда SpaceOps використовує при розробці UniSpace.
Це доповнення до README.md, TeamCharter.md і Project-Description.md, а не заміна
їх: якщо цей файл суперечить TeamCharter.md щодо процесу командної роботи —
керуйся TeamCharter.md і повідом про розбіжність.

## 1. Що таке проєкт

UniSpace — вебзастосунок-шар керування аудиторним фондом університету поверх
САЗу (системи автоматизації закладу). САЗ лишається єдиним джерелом істини щодо
розкладу (предмети, групи, час пар) і надається лише для читання (парсинг
HTML, без офіційного API). UniSpace відповідає виключно за розподіл аудиторій:
імпортує розклад і створює бронювання за замовчуванням, дозволяє викладачу
змінити аудиторію власного заняття, не допускає накладок, підбирає вільні
альтернативи за корпусом/місткістю та сповіщає причетних.

Повний опис ідеї, ролі користувачів, перелік функцій (F1–F7) і нефункціональні
вимоги (NFR-1…NFR-5) — у `Project-Description.md`. Перед тим як генерувати
код для нової функції, звірся з цим файлом і з `docs/requirements/user-stories.md`.

**Свідомо поза обсягом семестру** (не реалізовувати, якщо явно не попросили):
редагування самого розкладу в САЗ, зворотний запис у САЗ, мобільний застосунок,
SMS/push, SSO/LDAP-інтеграція з обліковими записами університету, облік
обладнання й ремонтів, оцінки/відвідуваність/навчальні матеріали, автоматичне
визначення місткості аудиторій із зовнішніх джерел.

## 2. Стек і поточний стан репозиторію

- Мова/фреймворк: Python, Django (`Project-Description.md` фіксує Python 3.12 /
  Django 5.x як цільовий стек; але заготовки `Backend/Backend/settings.py` і
  `Frontend/Frontend/settings.py` згенеровані під Django 6.1.1 — версія ще не
  зафіксована в залежностях. Перш ніж додавати код, що залежить від конкретної
  версії Django, уточни це в issue/PR, а не вибирай версію мовчки).
- База даних: SQLite (`db.sqlite3`, у git не комітиться).
- Планований стек інтеграції з САЗ: `requests` + `BeautifulSoup`, парсинг
  ізольований в окремому модулі-адаптері з тестами на збережених HTML-фікстурах
  (модуль ще не створено).
- **Залежності (`requirements.txt`) поки не існують у репозиторії.** Це не
  помилка агента — просто ще не додано. Якщо додаєш нову залежність, створи або
  онови `requirements.txt`/`requirements/*.txt`, не покладайся на глобально
  встановлені пакети.
- Репозиторій зараз на стадії Лабораторної 1–2 курсу СРПС: є два окремі
  Django-проєкти-заготовки (`django-admin startproject`), Django-застосунків
  (apps) із бізнес-логікою ще немає. Не вигадуй існуючі моделі/в'юхи — перевір
  файлову структуру перед тим, як стверджувати, що щось "вже реалізовано".

### Структура репозиторію

```
unispace/
├── Backend/              # Django-проєкт "Backend" (API-шар, окремий settings.py/urls.py)
│   ├── Backend/           # сам Django-проєкт (settings, urls, wsgi, asgi)
│   ├── manage.py
│   └── test_init.py       # плейсхолдер-тест, який зараз запускає CI
├── Frontend/              # Django-проєкт "Frontend" (окремий settings.py/urls.py)
│   ├── Frontend/
│   └── manage.py
├── docs/
│   └── requirements/
│       └── user-stories.md   # user stories US-01…US-10 з позначенням автора (id не послідовні)
├── Loom/Lab01/            # текстові файли з посиланнями на відео Loom по лабораторних
├── .github/workflows/ci.yml
├── README.md
├── TeamCharter.md
└── Project-Description.md
```

`Backend/` і `Frontend/` — це два окремі Django-проєкти з власними
`settings.py`/`urls.py`/`SECRET_KEY`, а не одна кодова база з двома додатками.
Якщо потрібно з'ясувати, як саме вони мають взаємодіяти (Backend як REST API +
Frontend як окремий клієнт, чи щось інше) — це архітектурне рішення команди,
яке AI-агент не повинен ухвалювати одноосібно; онови цей розділ, коли рішення
буде зафіксоване (наприклад, в ADR або в Project-Description.md).

## 3. Як запускати і перевіряти код

Django-застосунки поки не мають окремого віртуального середовища чи
зафіксованих версій пакетів у репозиторії, тож перед запуском:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install django          # зафіксуй версію в requirements.txt, коли команда її обере

cd Backend
python manage.py migrate
python manage.py runserver
```

Те саме для `Frontend/`, з відповідним `cd Frontend`.

### Тести й CI

Поточний конвеєр CI (`.github/workflows/ci.yml`) навмисно мінімальний (див.
Lab01: "не перемудрюй із CI, простого echo hello наразі достатньо"):

```yaml
runs-on: ubuntu-latest
steps:
  - actions/checkout@v4
  - actions/setup-python@v5 (python-version: '3.12')
  - working-directory: ./Backend
    run: python test_init.py
```

`Backend/test_init.py` — це не pytest/Django test runner, а один файл із
функцією `test_hello_world()`, який виконується напряму. Коли команда додасть
реальну бізнес-логіку, очікується перехід на `python manage.py test` або
pytest — онови цей розділ AGENTS.md і `ci.yml` разом, а не лише один із них.

**Перед відкриттям PR з кодом Django-моделей/в'юх, які торкаються бронювань,
обов'язково додай тест на NFR-2** (дві одночасні спроби забронювати ту саму
аудиторію на той самий слот → рівно одне успішне бронювання) — це явна вимога
з `Project-Description.md`, а не побажання.

## 4. Git-процес і конвенції (з TeamCharter.md, розділ 4)

- Гілкування: GitHub Flow. `main` захищена, прямі коміти заборонені.
  Будь-яка зміна: нова гілка від свіжої `main` → PR → мінімум 1 approve → merge.
- Іменування гілок: `<тип>/<короткий-опис>`, напр. `feat/room-search`,
  `fix/conflict-detection`, `docs/team-charter`.
- Коміти — Conventional Commits, англійською, наказовий спосіб, заголовок
  ≤ 72 символів: `<тип>: <що зроблено>`. Типи: `feat`, `fix`, `docs`, `refactor`.
  Приклади: `feat: add room availability check`, `fix: handle empty schedule cells`.
- Дрібні логічні коміти, не накопичувати тиждень роботи в один коміт.
- У `main` не потрапляє код, який не проходить CI, і код без хоча б одного
  approve. AI-агент не мерджить PR і не вимикає branch protection.
- Issue отримує мітки `type: ...` + `priority: ...`; самопризначення виконавця
  (crea self-assign), одночасно максимум 2 задачі в роботі на людину.
- Задача вважається зробленою, коли змерджена в `main`, а не коли працює
  локально.

## 5. Використання ШІ — обов'язкові правила (TeamCharter.md, розділ 8)

Команда відкрито декларує використання ШІ і вимагає:

1. **Розкриття.** У кожному артефакті лабораторної роботи, де застосовано ШІ,
   додається нотатка/секція «Використання ШІ»: що саме згенеровано і як це
   верифіковано. Якщо ти (AI-агент) створюєш або суттєво редагуєш файл — постав
   у PR-описі коротко: що зроблено ШІ, що саме перевірено людиною.
2. **Обов'язкова верифікація.** Будь-який згенерований код проходить ті самі
   механізми перевірки, що й написаний вручну: code review іншим учасником
   команди, автотести, статичний аналіз. Не пропонуй і не заохочуй merge в обхід
   цього.
3. **Захист основної гілки.** Неперевірений згенерований код ніколи не потрапляє
   в `main` напряму. Тільки через PR після проходження CI й approve.
4. **Особиста відповідальність.** Автор коміту має повністю розуміти
   згенерований код і вміти пояснити його логіку на захисті. Тому: пиши код
   максимально читабельно, короткими логічними одиницями, з поясненнями в
   PR-описі — не генеруй великі непрозорі "чорні скриньки", які людині складно
   буде пояснити.

## 6. Ролі й права доступу (для майбутньої бізнес-логіки)

Три ролі, реалізуються через Django permission-групи (не через кастомну
модель User, якщо не вирішено інакше):

| Роль | Доступ |
|---|---|
| Студент | Read-only: розклад своєї групи, сповіщення. Жодних write-ендпойнтів бронювання. |
| Викладач | Read/write власних занять: зміна аудиторії, пошук вільних аудиторій за корпусом/місткістю. |
| Адміністратор (диспетчер розкладу) | Повний доступ: довідник аудиторій, синхронізація з САЗ, розв'язання конфліктів, керування користувачами, аудит-лог. |

Ключові нефункціональні вимоги, які код має враховувати з самого початку:
автентифікація лише за корпоративною поштою домену університету; паролі —
хешовані (PBKDF2, стандарт Django); усі write-ендпойнти бронювань закриті для
ролі «студент» (мають повертати HTTP 403, не 404/500); аудит-лог зберігається
не менше 12 місяців; синхронізація з САЗ має бути ідемпотентною і не зупиняти
систему при недоступності САЗ (працювати на останньому знімку даних).

## 7. Чого AI-агент не повинен робити

- Не вигадувати й не комітити реальні облікові дані, SMTP-креденшели чи ключі —
  лише плейсхолдери/змінні середовища.
- Не змінювати `SECRET_KEY` у `settings.py` на production-подібний секрет і не
  вимикати `DEBUG`/branch protection "про всяк випадок" — це рішення Repo/CI
  Maintainer, не AI-агента.
- Не комітити `db.sqlite3`, `.venv/`, `__pycache__/` та інші файли з
  `.gitignore`.
- Не реалізовувати пункти зі списку "поза обсягом" (розділ 1) без явного
  запиту команди.
- Не мерджити PR і не позначати issue закритим самостійно — це робить людина
  після review.
