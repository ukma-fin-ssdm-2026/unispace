## Опис ідеї

Розклад університету публікується в САЗ, але САЗ фіксує лише початковий стан:
яка пара, у якої групи, в якій аудиторії. Реальні зміни — перенесення пари в
інший кабінет, тимчасова зайнятість приміщення, накладки двох занять в одній
аудиторії — відбуваються поза системою, узгоджуються в месенджерах і часто
доходять до студентів із запізненням або не доходять узагалі.

UniSpace — вебзастосунок, який працює як шар керування аудиторним фондом
поверх САЗу. Система періодично імпортує розклад із САЗу і створює на його
основі бронювання аудиторій за замовчуванням. Викладач може змінити аудиторію
свого заняття; система при цьому гарантує, що дві пари не опиняться в одному
приміщенні одночасно, підбирає вільні альтернативи за місткістю та корпусом і
повідомляє всіх, кого зміна стосується. Джерелом істини щодо самого розкладу —
предметів, груп, часу занять — лишається САЗ; UniSpace керує виключно
розподілом приміщень.

## Міні-ТЗ — технічне завдання

> Рамка проєкту на семестр за шістьма обов'язковими пунктами.
> Не є повною специфікацією вимог — її буде побудовано в Лабораторній 2.

### 1. Призначення системи

Система усуває неконтрольовані зміни в розподілі аудиторій. Студенти
отримують актуальну інформацію про місце пари; викладачі можуть змінити
аудиторію без ручних узгоджень і ризику накладки; диспетчер розкладу
контролює аудиторний фонд і розв'язує конфлікти. Користувачі — студенти,
викладачі та працівники навчальної частини одного університету.

### 2. Межі системи

**Входить в обсяг семестру**

- Парсинг розкладу з САЗ (односторонній, лише читання)
- CRUD довідника аудиторій
- Бронювання та перебронювання приміщень із контролем накладок
- Виявлення конфліктів і підбір вільних альтернатив
- Email-сповіщення та сповіщення в застосунку
- Рольова автентифікація й авторизація
- Аудит-лог змін бронювань
- Вебінтерфейс і REST API

**Свідомо поза обсягом**

- Редагування самого розкладу (предмети, групи, час занять) — джерелом істини
  лишається САЗ
- Зворотний запис у САЗ
- Мобільний застосунок, SMS та push-сповіщення
- Автентифікація користувачів через Microsoft Account з використанням університетської електронної пошти. UniSpace не зберігає паролі користувачів.
- Облік обладнання, ремонтів і матеріальних цінностей
- Оцінки, відвідуваність, навчальні матеріали
- Автоматичне визначення місткості аудиторій із зовнішніх джерел

### 3. Ролі користувачів

| Роль | Що може робити |
|---|---|
| **Студент** | Переглядає розклад своєї групи з актуальними аудиторіями; отримує сповіщення про зміни. Операції бронювання недоступні (read-only) |
| **Викладач** | Переглядає свої заняття; змінює аудиторію власного заняття; шукає вільні аудиторії з фільтром за корпусом і місткістю; отримує сповіщення про накладки зі своїми заняттями |
| **Адміністратор (диспетчер розкладу)** | Керує довідником аудиторій; запускає й контролює синхронізацію з САЗом; розв'язує зафіксовані конфлікти; керує користувачами та ролями; має доступ до аудит-логу |

Розмежування реалізується через permission-групи Django; роль «студент» не
має доступу до жодного ендпойнта запису, пов'язаного з бронюваннями.

### 4. Ключові функції

| № | Функція | Опис |
|---|---|---|
| F1 | Синхронізація з САЗ | Періодичний ідемпотентний імпорт розкладу і створення бронювань аудиторій за замовчуванням |
| F2 | Довідник аудиторій | Ведення переліку приміщень: корпус, номер, місткість, обладнання, доступність |
| F3 | Зміна аудиторії викладачем | Перебронювання власного заняття з перевіркою доступності цільової аудиторії на цей слот |
| F4 | Детектор конфліктів | Заборона накладок при діях користувача; накладки з даних САЗу фіксуються як інциденти з повідомленням обох викладачів |
| F5 | Підбір вільної аудиторії | Ранжований список альтернатив за корпусом і найближчою достатньою місткістю |
| F6 | Сповіщення | Email і повідомлення в застосунку студентам групи та задіяним викладачам про зміну аудиторії чи конфлікт |
| F7 | Аудит-лог | Історія змін бронювань: хто, коли, з якої аудиторії на яку і з якої причини |

### 5. Нефункціональні вимоги

| № | Вимога | Вимірюваний критерій |
|---|---|---|
| NFR-1 | Продуктивність | Сторінка тижневого розкладу групи віддається за ≤ 500 мс (p95) при 100 одночасних користувачах на наборі з 300 аудиторій |
| NFR-2 | Цілісність при конкурентності | Дві одночасні спроби забронювати ту саму аудиторію на той самий часовий слот дають рівно одне успішне бронювання; накладок, створених діями користувачів, — 0. Перевіряється тестом на 10 паралельних запитів |
| NFR-3 | Своєчасність сповіщень | 95 % сповіщень про зміну аудиторії відправляються протягом 2 хвилин після збереження зміни |
| NFR-4 | Безпека та приватність | Автентифікація здійснюється через Microsoft Account з використанням університетської електронної пошти; UniSpace не зберігає паролі користувачів; усі write-ендпойнти бронювань закриті для ролі «студент» (HTTP 403); персональні дані недоступні неавтентифікованим користувачам; аудит-лог захищений від зміни та видалення і зберігається не менше 12 місяців |
| NFR-5 | Відмовостійкість інтеграції | Недоступність або зміна розмітки САЗ не спиняє систему: застосунок працює на останньому успішному знімку даних, невдала синхронізація логується й повідомляється адміністратору |

### 6. Припущення та обмеження

**Стек.** Python 3.12, Django 5.x, PostgreSQL,
`requests` + `BeautifulSoup` для парсингу, management-команда за розкладом для
синхронізації та розсилки, GitHub Actions для CI.

**Припущення.** САЗ не надає публічного API, тому інтеграція будується на
парсингу HTML; логіка парсингу ізолюється в окремому модулі-адаптері, тести
використовують збережені HTML-фікстури. Централізованих машинночитних даних
про місткість аудиторій немає — довідник наповнюється вручну. Доступ до
корпоративного SMTP-сервера не гарантований; на час розробки використовується
тестовий SMTP. Система є навчальним прототипом, працює на власній копії даних
і не замінює САЗ.

**Обмеження.** Команда з 5 осіб, орієнтовно 5–8 годин на особу на тиждень;
один семестр, робота ітераційна за лабораторними; дані САЗ доступні лише для
читання і можуть змінюватися без попередження.

## Звірка з критеріями курсу

| Критерій | Як закривається |
|---|---|
| Складність: кілька взаємодіючих функцій, 2–3 ролі | Три ролі з відмінними правами: студент (read-only), викладач, адміністратор-диспетчер |
| Архітектура: компоненти з чіткими API | Модулі `saz_sync`, `rooms`, `booking`, `notifications`, `accounts`; зовнішній REST API |
| Нетривіальність: функціональні та нефункціональні вимоги | Сім функцій і п'ять вимірюваних NFR: продуктивність, конкурентність, своєчасність, безпека, відмовостійкість |
| Здійсненність за семестр | Обсяг утримується явним розділом «поза обсягом»; інтеграція одностороння, мобільного клієнта |
| Актуальність: реалістичні виклики інженерії | Парсинг зовнішнього джерела без API, race condition при одночасному бронюванні, ідемпотентна синхронізація, розсилка сповіщень |
| Залученість на 10+ тижнів | Команда є безпосереднім користувачем системи й щодня стикається з проблемою |

**Розглянуті альтернативи.** Студентський портал — відхилено через завеликий
обсяг і дублювання наявних систем університету. Узагальнена система
бронювання — взята за основу, але спеціалізована під реальний контекст
аудиторного фонду.

**Уточнення обсягу під час обговорення команди.** Студентам залишено лише
перегляд, оскільки зміна аудиторії є адміністративною дією. Розклад як такий
не редагується. Конфлікти розділено на два типи: створені користувачем —
забороняються з пропозицією альтернатив; наявні в даних САЗу — фіксуються як
інциденти з повідомленням обох викладачів.
