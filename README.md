## Опис проєкту
Розклад університету публікується в САЗ, але САЗ фіксує лише початковий стан: яка пара, у якої групи, в якій аудиторії. Реальні зміни — перенесення пари в інший кабінет, тимчасова зайнятість приміщення, накладки двох занять в одній аудиторії — відбуваються поза системою, узгоджуються в месенджерах і часто доходять до студентів із запізненням або не доходять узагалі.

UniSpace — вебзастосунок, який працює як шар керування аудиторним фондом поверх САЗу. Система періодично імпортує розклад із САЗу і створює на його основі бронювання аудиторій за замовчуванням. Викладач може змінити аудиторію свого заняття; система при цьому гарантує, що дві пари не опиняться в одному приміщенні одночасно, підбирає вільні альтернативи за місткістю та корпусом і повідомляє всіх, кого зміна стосується. Джерелом істини щодо самого розкладу — предметів, груп, часу занять — лишається САЗ; UniSpace керує виключно розподілом приміщень.

## Основні функції проєкту
* **Імпорт розкладу:** автоматичне завантаження даних із системи САЗ.
* **Створення бронювань:** гнучке бронювання аудиторій для занять або заходів.
* **Управління аудиторним фондом:** контроль статусу та доступності приміщень.
* **Попередження конфліктів:** алгоритми недопущення накладок (Race Condition) та подвійного бронювання однієї аудиторії.
* **Інтелектуальний пошук:** підбір вільних приміщень на основі заданої місткості, часу та необхідного обладнання.
* **Безпечна авторизація:** єдиний вхід до системи (SSO) через університетський акаунт Microsoft (Entra ID) з підтримкою ролей користувачів.

## Стек технологій
* **Backend:** Python (Django, Django REST Framework)
* **Frontend:** HTML5, CSS, JS, Django Templates, WhiteNoise
* **База даних:** PostgreSQL (локальна розробка через Docker Compose (`Backend/docker-compose.yml`) та продакшн на Render; міграції вимагають обов'язкової підтримки PostgreSQL та розширення GiST)
* **CI/CD, Тестування & Інструменти якості:** GitHub Actions, GitHub Flow, pytest, coverage, Flake8, Black, Bandit, pip-audit, Pre-commit, mutmut, hypothesis

## Інструкція із запуску (Локально)
Оскільки архітектура передбачає фізичне розділення на два незалежні Django-проєкти, для повноцінної роботи системи необхідно запустити обидва сервери:

**1. Запуск Backend (REST API та Документація)**
- Клонуйте репозиторій та перейдіть у папку бекенду: `cd Backend`
- Створіть віртуальне середовище: `python -m venv .venv`
- Активуйте віртуальне середовище:
   - **Windows:** `.\.venv\Scripts\activate`
   - **macOS / Linux:** `source .venv/bin/activate`
- Налаштуйте змінні середовища:
   - Створіть копію файлу `.env.example` і назвіть її `.env`
   - Відкрийте `.env` і впишіть свої локальні налаштування для доступу до бази даних (логін, пароль) та `SECRET_KEY`, а також дані для інтеграції з Microsoft (за потреби `MS_TENANT_ID`, `MS_CLIENT_ID`, `MS_CLIENT_SECRET`).
- Підготуйте базу даних:
   - Запустіть PostgreSQL локально або скористайтеся конфігурацією з `Backend/docker-compose.yml`.
   - Створіть порожню базу даних (наприклад, `CREATE DATABASE unispace;`).
   - Увійдіть у створену базу даних та активуйте обов'язкове розширення для перевірки часових перетинів і унікальності бронювань (GiST-індекси):
     ```sql
     CREATE EXTENSION IF NOT EXISTS btree_gist;
     ```
- Встановіть залежності: `pip install -r requirements.txt`
- Встановіть інструменти перевірки якості (виконайте ці дві команди **у корені проєкту**):
  - `pip install -r Backend/requirements-dev.txt`
  - `pre-commit install`
- Застосуйте міграції бази даних: `python manage.py migrate`
- Заповніть базу початковими даними (аудиторії, розклад, тестові користувачі ролей студента, викладача та диспетчера): `python manage.py seed_demo`.
- Запустіть сервер розробки: `python manage.py runserver 8000`
- *Специфікація OpenAPI генерується автоматично. Swagger UI доступний за адресою: `http://localhost:8000/api/docs/`*

**2. Запуск Frontend (Web UI)**
- Відкрийте нову вкладку терміналу та перейдіть у папку фронтенду: `cd Frontend`
- Створіть віртуальне середовище: `python -m venv .venv`
- Активуйте віртуальне середовище:
   - **Windows:** `.\.venv\Scripts\activate`
   - **macOS / Linux:** `source .venv/bin/activate`
- Налаштуйте змінні середовища:
   - Створіть копію файлу `.env.example` і назвіть її `.env`
   - Відкрийте `.env` і впишіть туди свій `SECRET_KEY` та переконайтеся, що `BACKEND_API_URL` вказує на ваш локальний бекенд.
- Встановіть залежності:
   - `pip install -r requirements.txt`
   - `pip install -r requirements-dev.txt`
- *Примітка щодо якості коду:* Переконайтеся, що ви виконали команду `pre-commit install` у **корені всього репозиторію**, щоб активувати автоматичні перевірки для фронтенду.
- Застосуйте міграції (для внутрішніх таблиць сесій Django): `python manage.py migrate`
- Запустіть сервер розробки на іншому порту: `python manage.py runserver 8001`
- *Клієнтський вебзастосунок доступний за адресою: `http://localhost:8001/`*

## Розгортання на Render (Deployment)
Обидва сервіси (Backend та Frontend) розгортаються на хмарній платформі Render як окремі вебсервіси (Web Services).

### 1. Backend (REST API)
* **Root Directory:** `Backend`
* **Build Command:** `pip install -r requirements.txt && python manage.py collectstatic --noinput`
* **Start Command:** `gunicorn Backend.wsgi:application --timeout 45`

**Необхідні змінні середовища (Environment Variables):**
* `PYTHON_VERSION` = `3.12.0`
* `SECRET_KEY` = `<ваш-унікальний-секретний-ключ>`
* `DEBUG` = `False`
* `ALLOWED_HOSTS` = `<unispace-wtf6.onrender.com>`
* `DATABASE_URL` = `<url-бази>` *(Internal Database URL від вашого PostgreSQL інстансу на Render)*
* `MS_TENANT_ID`, `MS_CLIENT_ID`, `MS_CLIENT_SECRET` = *(Дані з реєстрації застосунку в Microsoft Entra ID)*
* `MS_REDIRECT_URI` = `https://<ваша-адреса-бекенду>.onrender.com/auth/microsoft/callback/`
* `LOGIN_REDIRECT_URL` = `https://<ваша-адреса-фронтенду>.onrender.com/`

### 2. Frontend (Web UI)
Оскільки фронтенд також працює на базі Django, він розгортається аналогічно, використовуючи WhiteNoise для роздачі статичних файлів (CSS, JS).
* **Root Directory:** `Frontend`
* **Build Command:** `pip install -r requirements.txt && python manage.py collectstatic --noinput`
* **Start Command:** `gunicorn Frontend.wsgi:application`

**Необхідні змінні середовища (Environment Variables):**
* `PYTHON_VERSION` = `3.12.0`
* `SECRET_KEY` = `<ваш-унікальний-секретний-ключ>`
* `DEBUG` = `False`
* `ALLOWED_HOSTS` = `<unispace-front.onrender.com>`
* `BACKEND_API_URL` = `https://<ваша-адреса-бекенду>.onrender.com/api/v1/`

> **Важлива примітка щодо безпеки:** Щоб авторизація запрацювала, адресу, вказану в `MS_REDIRECT_URI` вашого бекенду, необхідно обов'язково додати до списку дозволених "Redirect URIs" у налаштуваннях застосунку на порталі Microsoft Entra ID.

## Робочий процес
Ми дотримуємося стратегії гілкування **GitHub Flow**. Процес розробки складається з наступних кроків:
1. **Створення гілки:** відгалуження від актуальної `main` (наприклад, `feat/room-search` або `fix/conflict-detection`).
2. **Коміти:** збереження змін невеликими логічними частинами. Повідомлення оформлюються за стандартом Conventional Commits (наприклад, `feat: add room availability check`).
3. **Pull Request:** відкриття PR у гілку `main`.
4. **Автоматичні перевірки (CI):** кожен PR зобов'язаний успішно пройти всі перевірки GitHub Actions (форматування `black`, лінтер `flake8`, аналізатор безпеки `bandit`). Усі тести також мають успішно завершитися з підтвердженим порогом покриття коду не нижче 75%.
5. **Огляд коду (Code Review):** схвалення (Approve) мінімум від 1 учасника команди (для важливих документів — перегляд усією командою).
6. **Злиття (Merge):** після схвалення та успішного проходження CI код додається до `main`.
