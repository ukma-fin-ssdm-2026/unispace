## 4. Співпраця та робочий процес 
- Стратегія гілкування: GitHub Flow  
  — main захищена, прямі коміти заборонені. 
  — Будь-яка зміна: нова гілка від свіжої main → PR → 1 approve → merge. 
  — Іменування гілок: <тип>/<короткий-опис> 
feat/room-search 
fix/conflict-detection 
docs/team-charter 
refactor/views-cleanup 
  — Гілка живе коротко: відкрили — за 1-3 дні змерджили. 
  — Гілку після мерджу видаляємо. 
  — Апрувить хоча б 1 людина, яка зараз вільна. Свій PR сама собі не апрувиш. 
- Практики комітів:
  — Частота: маленькі логічні порції. Один коміт = одна завершена думка. Не накопичуємо тиждень роботи в один коміт. 
  — Пушимо у свою гілку щодня, коли працюємо — щоб було видно прогрес і щоб не втратити роботу. 
  — Формат (Conventional Commits), англійською, наказовий спосіб, заголовок до 72 символів: <тип>: <що зроблено> 
Типи: feat, fix, docs, refactor
Приклади: 
feat: add room availability check 
fix: handle empty schedule cells 
docs: add AI usage section 
  — У main не потрапляє код, який не проходить CI. 
- Правила огляду коду: всі злиття вимагають PR та принаймні 1 схвалення. 
- Робочий процес завдань:  
1) Issue створюється з описом і критеріями приймання 
2) Отримує мітки: type: ... + priority: ... 
3) Початковий набір завдань створює й розподіляє Issue Tracker Lead (Ксенія Тимохина) — за узгодженням із командою та з урахуванням ролей. Далі діє самопризначення: кожна учасниця сама бере задачу зі свого напряму й ставить себе assignee. Якщо задача з міткою priority: high залишається без виконавця понад 48 годин, Issue Tracker Lead призначає виконавця самостійно. Незгода з призначенням вирішується в чаті протягом 24 годин. 
4) Створює гілку від актуальної main 
5) Працює, комітить, пушить 
6) Відкриває PR, призначає reviewer'а 
7) CI має стати зеленим 
8) Reviewer дивиться протягом 24 год і робить approve або залишає коментарі 
9) Merge → Issue закривається автоматично → гілка видаляється 
  — Одночасно в роботі максимум 2 задачі на людину. Хочеш узяти третю — спочатку закрий одну. 
  — Задача вважається зробленою, коли змерджена в main, а не коли "в мене локально працює". 
  — Якщо задача заблокована — мітка blocked + коментар, чим саме. 

**Політики щодо вимог та документації:**
- Політика рев'ю User Stories:
Усі User Stories повинні бути оформлені у відповідних Issue та пройти крос-рев'ю іншим учасником команди на відповідність критеріям INVEST перед затвердженням.
  
- Політика рев'ю NFR:
Нефункціональні вимоги (NFR) підлягають обов'язковому рев'ю на відповідність критеріям SMART. Рев'ю здійснює учасник, який не був автором цих вимог.

- Політика збереження вимог:
Затверджені User Stories, FR та NFR фіксуються в каталозі /docs/requirements/ репозиторію. Процес обговорення ведеться у Discord.

- Політика оновлення README.md:
Файл `README.md` обов'язково оновлюється перед здачею кожної лабораторної роботи або релізом. Оновлення включає актуалізацію статусу, ролей, інструкцій із запуску та додавання посилань на нові матеріали.

- Політика створення та рев'ю Loom:
Loom-відео для демонстрації роботи записується після того, як всі необхідні зміни інтегровані в `main`. У Loom-відео кожен учасник повинен пояснити ту частину роботи, за яку він відповідає згідно зі своєю роллю (наприклад, керівник вимог пояснює користувацькі історії, керівник якості - NFR, тощо), демонструючи не лише результати, а й глибоке розуміння створених артефактів. Якщо для виконання завдання використовувався згенерований код або документація, учасник також зобов'язаний пояснити логіку ШІ та свій внесок у верифікацію цього результату. Здача роботи, яку учасник не може пояснити самостійно, вважається порушенням академічної доброчесності. Після отримання принаймні одного рев'ю та схвалення (approve) відео додається до `README.md`.

**Політика якості та огляду коду:**
- **Основний стандарт кодування:** Для бекенду на Django використовується стандарт PEP 8 (Python). Усі назви змінних, класів та методів мають бути зрозумілими, англомовними та відповідати конвенціям фреймворку. Для документації API використовується підхід Code-First (анотації `@extend_schema`).
- **Обовʼязкові інструменти:** 
  - Статичний аналіз та лінтинг: `flake8` / `pylint` (для дотримання стилю).
  - Форматування коду: `black`.
  - Безпека та додаткові перевірки: `bandit`, `pip-audit`, `pre-commit`.
  - Автоматизовані перевірки (CI): GitHub Actions для перевірки збірки та базових тестів перед кожним злиттям.
- **Кроки огляду коду колегою (Cross-Review):**
  1. Розробник створює Pull Request (PR) із робочої гілки в `main`.
  2. Автор коду перевіряє успішне проходження CI-конвеєра (зелена галочка в GitHub).
  3. Рев'юер (інший учасник команди) аналізує код за п'ятьма критеріями: стиль кодування, підтримуваність/логіка, безпека (валідація), коректне використання фреймворку та наявність документації.
  4. Рев'юер залишає коментарі для виправлення (Request Changes) або схвалює код (Approve). 
  5. Свій код схвалювати заборонено. Злиття в `main` дозволяється лише після мінімум 1 Approve.
  - **Definition of Done (DoD):**
  - Завдання реалізовано відповідно до погоджених вимог.
  - Код або документацію додано до окремої гілки.
  - Створено Pull Request із коротким описом змін.
  - Автоматизовані перевірки CI пройдено успішно.
  - Отримано щонайменше один approve від іншого учасника команди.
  - Документацію та тести оновлено, якщо цього потребують зміни.
  - PR змерджено в `main`, а відповідне Issue закрито.

- Правило верифікації:
  — Обов'язкова верифікація:
  Весь згенерований код проходить ті самі механізми перевірки, що й написаний вручну. Це включає перегляд коду (Code Review) іншим учасником команди, написання та проходження автоматизованих тестів, а також статичний аналіз. 
  — Захист основної гілки:
  Неперевірений згенерований код за жодних обставин не потрапляє в основну гілку репозиторію. Злиття (merge) відбувається лише після успішної верифікації. 
  — Особиста відповідальність:
  Кожен учасник команди відповідає за кожен рядок коду, який він додає в проєкт. Автор коміту зобов'язаний повністю розуміти згенерований код і вміти пояснити його логіку та свій внесок під час захисту. Здача роботи, яку учасник не може пояснити, вважається порушенням.
