# Дизайн API — UniSpace

## 1. Огляд архітектури

* **Базова адреса:** `http://localhost:8000/api/v1` (відповідно до C-004, бекенд розгорнуто як окремий Django-сервер на порті 8000).
* **Стиль API:** REST.
* **Автентифікація (FR-001, SEC-002):** Здійснюється через Microsoft Account (Microsoft Identity Platform / Azure AD) з використанням університетської електронної пошти. Клієнт передає сесійний Bearer-токен у стандартному HTTP-заголовку.
* **Формат відповіді:** JSON з відповідним кодом статусу HTTP.
* **Стратегія версіонування:** версія в URI-шляху (`/v1`, `/v2`).
  
---

## 2. Модель ресурсів

### 2.1 Сесії та автентифікація (`AuthSession`)

* **Кінцева точка:** `POST /api/v1/auth/microsoft/callback`
* **Опис:** Обмінює тимчасовий код авторизації Microsoft Identity Platform на внутрішній токен доступу UniSpace та повертає дані профілю й роль користувача.

* **Атрибути:**
* `auth_code` *(string, required)* — код авторизації, отриманий від Microsoft OAuth2/OIDC.
* `redirect_uri` *(string, required)* — URI зворотного виклику клієнтського застосунку.
* `token` *(string, readonly)* — внутрішній JWT/Bearer токен UniSpace для наступних запитів.
* `user.id` *(uuid, readonly)* — унікальний ідентифікатор користувача.
* `user.email` *(string, readonly)* — корпоративна електронна пошта.
* `user.role` *(string, readonly)* — призначена роль користувача: `student`, `teacher` або `dispatcher`.

* **Зв'язки:**
* Асоціюється із сутністю користувача в системі UniSpace (`User`).
* Посилається на зовнішній обліковий запис у `Microsoft Identity Platform`.

---

### 2.2 Розклад (`ScheduleItem`)

* **Кінцева точка:** `GET /api/v1/schedule`
* **Опис:** Повертає зведений актуальний розклад занять для академічної групи або викладача за вказаний діапазон дат із деталями призначених аудиторій.

* **Атрибути:**
* `group_id` *(uuid, query)* — фільтр за академічною групою.
* `date_from` / `date_to` *(date, query, required)* — межі часового діапазону вибірки.
* `lesson_id` *(uuid, readonly)* — ідентифікатор заняття в розкладі.
* `discipline_name` *(string, readonly)* — назва навчальної дисципліни.
* `lesson_type` *(string, readonly)* — тип пари (лекція, практична).
* `timeslot` *(object, readonly)* — дата, час початку та завершення пари.
* `room` *(object, readonly)* — закріплена аудиторія.

* `previous_lesson` *(object, readonly, optional)* — відомості про дисципліну та викладача, що вели пару в цій аудиторії перед поточною.

* **Зв'язки:**
* Багато-до-одного (`N:1`) до `Classroom` (призначена аудиторія).
* Багато-до-одного (`N:1`) до викладача та академічної групи, імпортованих із САЗ.

* Пов'язаний з активним записом `Booking`.

---

### 2.3 Каталог аудиторій (`Classroom`)

* **Кінцеві точки:**
* `GET /api/v1/classrooms` — отримання списку аудиторій із фільтрацією за характеристиками.
* `POST /api/v1/classrooms` — внесення нової аудиторії в довідник диспетчером.

* **Опис:** Ресурс представляє фізичне приміщення університету, його місткість, характеристики та наявне технічне оснащення.

* **Атрибути:**
* `id` *(uuid, readonly)* — унікальний ідентифікатор приміщення.
* `number` *(string, required)* — номер кабінету.
* `building` *(integer, required)* — навчальний корпус.
* `capacity` *(integer, required)* — кількість посадкових місць.
* `has_projector` *(boolean, required)* — наявність робочого проєктора.
* `computers_count` *(integer, optional)* — кількість комп'ютерних робочих місць.
* `is_available` *(boolean, readonly)* — статус доступності приміщення для використання.

* **Зв'язки:**
* Один-до-багатьох (`1:N`) до `Booking` (одна аудиторія може мати множинні бронювання на різні таймслоти).
* Один-до-багатьох (`1:N`) до `AuditLog` (історія дій, пов'язаних із цим кабінетом).

---

### 2.4 Підбір вільних аудиторій (`AvailableClassroomSearch`)

* **Кінцева точка:** `GET /api/v1/classrooms/available`
* **Опис:** Виконує аналітичний пошук і повертає список вільних приміщень на вказаний часовий слот із перевіркою місткості та пріоритетом за корпусом.

* **Атрибути:**
* `date` *(date, query, required)* — дата запланованого проведення заняття.
* `start_time` / `end_time` *(time, query, required)* — часові рамки таймслота.
* `min_capacity` *(integer, query, required)* — мінімально необхідна місткість аудиторії.
* `building` *(integer, query, required)* — пріоритетний навчальний корпус.
* `matches_in_requested_building` *(array of Classroom, readonly)* — вільні кімнати у запитаному корпусі.
* `alternative_buildings` *(array of Classroom, readonly)* — варіанти з інших корпусів (якщо в основному немає місць).

* **Зв'язки:**
* Читає та агрегує дані з ресурсів `Classroom` та `Booking` для визначення перетину зайнятості.

---

### 2.5 Перебронювання та розв'язання конфліктів (`Rebooking`)

* **Кінцева точка:** `POST /api/v1/bookings/rebook`
* **Опис:** Виконує перенесення заняття у нову аудиторію в межах атомарної транзакції з перевіркою зайнятості слота (`FOR UPDATE`).

* **Атрибути:**
* `lesson_id` *(uuid, required)* — ідентифікатор заняття, для якого змінюється приміщення.
* `new_room_id` *(uuid, required)* — ідентифікатор цільової аудиторії.
* `reason` *(string, required)* — текстове обґрунтування зміни приміщення (фіксується в аудиті).
* `booking_id` *(uuid, readonly)* — ідентифікатор оновленого запису бронювання.
* `status` *(string, readonly)* — результат виконання (`success` або `conflict`).
* `updated_at` *(datetime, readonly)* — точний час фіксації перенесення в системі.

* **Зв'язки:**
* Багато-до-одного (`N:1`) до `Classroom` (нове цільове приміщення).
* Багато-до-одного (`N:1`) до `ScheduleItem` (заняття).
  
* Ініціює створення запису в `AuditLog`.
* Ініціює надсилання повідомлень через `Notification`.

---

### 2.6 Скасування бронювання (`BookingCancellation`)

* **Кінцева точка:** `POST /api/v1/bookings/{id}/cancel`
* **Опис:** Звільняє призначену аудиторію (статус «Скасовано») без вилучення заняття з розкладу UniSpace чи зміни даних у САЗ.

* **Атрибути:**
* `id` *(uuid, path, required)* — ідентифікатор активного бронювання, яке скасовується.
* `reason` *(string, required)* — причина скасування.
* `status` *(string, readonly)* — кінцевий статус слота (`cancelled`).
* `cancelled_at` *(datetime, readonly)* — часова мітка операції скасування.

* **Зв'язки:**
* Змінює стан пов'язаної сутності `Booking`.
* Пов'язаний з ініціатором дії (`User` — викладач або диспетчер).
* Фіксується в незмінному журналі `AuditLog`.

---

### 2.7 Синхронізація розкладу із САЗ (`SyncOperation`)

* **Кінцева точка:** `POST /api/v1/sync/ca3`
* **Опис:** Запускає фоновий односторонній парсинг HTML-розкладу із зовнішньої системи САЗ, формує базові бронювання та повертає виявлені накладки.

* **Атрибути:**
* `semester` *(string, required)* — ідентифікатор навчального семестру для імпорту.
* `force_update` *(boolean, optional, default: false)* — примусове оновлення знімка даних.
* `sync_id` *(uuid, readonly)* — унікальний ідентифікатор запущеної операції імпорту.
* `imported_lessons_count` *(integer, readonly)* — кількість успішно опрацьованих занять.
* `collisions_detected` *(integer, readonly)* — кількість зафіксованих накладок у розкладі САЗ.
* `collisions` *(array of objects, readonly)* — структурований список конфліктних пар (час, кабінет, викладачі, групи).

* **Зв'язки:**
* Зчитує дані з зовнішньої системи `CA3 System (САЗ)` у режимі Read-Only.
* Генерує сукупність сутностей `ScheduleItem` та `Booking`.
* При виявленні колізій надсилає тригери до `Notification` для викладачів.

---

### 2.8 Журнал аудиту (`AuditLog`)

* **Кінцева точка:** `GET /api/v1/audit-logs`
* **Опис:** Надає диспетчеру доступ до незмінного списку історичних записів про перенесення та скасування занять (доступний лише на читання).

* **Атрибути:**
* `id` *(uuid, readonly)* — первинний ключ запису логу.
* `timestamp` *(datetime, readonly)* — дата й час виконання операції.
* `actor_name` / `actor_email` *(string, readonly)* — дані користувача, який вніс зміни.
* `action` *(string, readonly)* — тип зафіксованої дії (`ROOM_CHANGE`, `BOOKING_CANCELLED`).
* `previous_room` *(string, readonly)* — номер аудиторії до зміни.
* `new_room` *(string, readonly, nullable)* — новий номер аудиторії (або null при скасуванні).
* `reason` *(string, readonly)* — зазначена користувачем причина коригування.

* **Зв'язки:**
* Посилається на користувача-виконавця (`User`).
* Пов'язаний з аудиторіями (`Classroom`) та заняттями (`ScheduleItem`).

---

### 2.9 Сповіщення (`Notification`)

* **Кінцева точка:** `GET /api/v1/notifications`
* **Опис:** Повертає список адресованих поточному користувачу внутрішніх системних повідомлень про перенесення пар або виявлені накладки розкладу.

* **Атрибути:**
* `id` *(uuid, readonly)* — ідентифікатор повідомлення.
* `type` *(string, readonly)* — тип сповіщення (`ROOM_CHANGED`, `SCHEDULE_COLLISION`).
* `title` *(string, readonly)* — заголовок повідомлення.
* `message` *(string, readonly)* — повний зміст повідомлення із параметрами зміни.
* `created_at` *(datetime, readonly)* — час генерації сповіщення.

* **Зв'язки:**
* Багато-до-одного (`N:1`) до `User` (користувач-одержувач: викладач або студент).
* Пов'язаний із подіями операцій `Rebooking` або `SyncOperation`.
  
---

## 3. Архітектурні рішення

### 3.1 Контроль конкурентності та транзакційність
* Використання атомарних транзакцій transaction.atomic() на рівні бази даних для операцій перенесення аудиторій.
* Песимістичне блокування рядків SELECT ... FOR UPDATE під час перевірки зайнятості таймслота.
* Гарантує усунення гонки (Race Condition / TM-09) і виконання вимоги REL-001 (рівно одне успішне бронювання при паралельних запитах).

### 3.2 Асинхронність сповіщень
* Відправка поштових повідомлень через SMTP відокремлена від основного життєвого циклу HTTP-запиту.
* Запит на перенесення пари фіксується в базі негайно, а задача відправки email ставиться у фонову чергу (PERF-002).
* Запобігає зависанню інтерфейсу клієнта у разі повільної відповіді або тимчасової недоступності SMTP-сервера.

### 3.3 Незмінність журналу аудиту (Append-Only)
* Ресурс /audit-logs надає виключно метод GET без підтримки модифікацій через API.
* Створення записів аудиту ініціюється виключно самою системою у момент успішного коміту транзакції зміни аудиторії (SEC-003).
