# Дизайн API — UniSpace

## 1. Огляд архітектури
- **Базова адреса:** `http://localhost:8000/api/v1` (відповідно до C-004, бекенд розгорнуто як окремий Django-сервер на порті 8000).
- **Стиль API:** REST.
- **Автентифікація (FR-001, SEC-002):** Здійснюється через Microsoft Account (Microsoft Identity Platform / Azure AD) з використанням університетської електронної пошти. Вхід починається на `GET /auth/microsoft/login/` (перенаправлення до Microsoft), Microsoft повертає браузер на `GET /auth/microsoft/callback/`, після чого сервер створює сесію Django. Потік входу зберігається в сесійній cookie, яка прив'язана до хоста, тому якщо вхід розпочато на іншому хості, ніж у `MS_REDIRECT_URI` (наприклад, `127.0.0.1` замість `localhost`), `GET /auth/microsoft/login/` спершу перенаправляє на хост із `MS_REDIRECT_URI`. Клієнт далі передає сесійну cookie, а не Bearer-токен (запити з фронтенду виконуються з `credentials: 'include'`); для небезпечних методів (POST, PATCH, DELETE) діє CSRF-захист DRF SessionAuthentication. У production cookie мають `Secure` і `SameSite=None`, а CORS з `credentials` дозволено лише для відомих origin (локальний фронтенд і `unispace-front.onrender.com`). Вихід: `POST /auth/logout/`. Фронтенд на іншому домені не може прочитати cookie бекенду, тому CSRF-токен видає `GET /api/v1/auth/csrf/` (відповідь `{"csrfToken": ...}` і cookie), а клієнт передає його в заголовку `X-CSRFToken`. Шляхи входу, виходу та `auth/csrf/` не входять до OpenAPI-схеми, на відміну від `GET /api/v1/auth/me/`.
- **Формат відповіді:** JSON з відповідним кодом статусу HTTP.
- **Стратегія версіонування:** версія в URI-шляху (`/v1`, `/v2`).

## 2. Модель ресурсів

### 2.1 Аудиторії (Rooms)
- **Кінцева точка:** `/api/v1/rooms/`
- **Опис:** повертає каталог аудиторій університету. Для списку застосовується пагінація зі зсувом.
- **Атрибути:**
  - `id` (string, UUID) — унікальний ідентифікатор аудиторії в базі даних.
  - `name` (string) — назва або номер аудиторії.
  - `capacity` (integer) — кількість місць.
  - `has_projector` (boolean) — наявність функціонуючого проєктора.
- **Зв'язки:**
  - має багато бронювань (bookings)
  - має багато доступних часових слотів (available_slots)

### 2.2 Бронювання (Bookings)
- **Кінцева точка:** `/api/v1/bookings/`
- **Опис:** створення, перегляд та скасування бронювань аудиторій.
- **Атрибути:**
  - `id` (string, UUID): унікальний ідентифікатор бронювання
  - `lesson_id` (string, UUID): ідентифікатор заняття
  - `room_id` (string, UUID): ідентифікатор аудиторії
  - `user_id` (string, UUID, nullable): автор бронювання
  - `start_time` (datetime): час початку бронювання
  - `end_time` (datetime): час завершення бронювання
  - `status` (string): `active` або `cancelled`
  - `source` (string): `saz` або `manual`
  - `created_at` (datetime): дата створення
  - `updated_at` (datetime): дата останнього оновлення
- **Зв'язки:**
  - належить до одного заняття (Lesson)
  - належить до однієї аудиторії (Room)
  - може мати автора (User)

### 2.3 Користувачі (Users)
- **Кінцева точка:** `/api/v1/users/me/bookings/`
- **Опис:** користувачі системи та доступ до їхніх особистих бронювань.
- **Атрибути:**
  - `role` (enum): роль користувача у системі (`student` | `teacher` | `dispatcher`)
  - `is_authenticated` (boolean): прапорець автентифікації користувача
- **Зв'язки:**
  - має багато власних бронювань

## 3. Кінцеві точки та HTTP статус-коди

Згідно з підходом Code-First, усі відповіді та статус-коди автоматично генеруються з анотацій `@extend_schema` у нашому коді. Нижче наведено зведену таблицю всіх 18 операцій API `/api/v1/`: їхніх методів, шляхів та статус-кодів успіху й помилок, які вони повертають:

| HTTP Метод | Шлях (Endpoint) | Опис операції | Код успіху | Коди помилок |
| :--- | :--- | :--- | :--- | :--- |
| **GET** | `/api/v1/rooms/` | Отримати список аудиторій (з пагінацією limit/offset) | `200 OK` | `400 Bad Request` |
| **GET** | `/api/v1/rooms/available-slots/` | Пошук вільних слотів для конкретної аудиторії на дату | `200 OK` | `400 Bad Request` |
| **POST** | `/api/v1/bookings/` | Створити нове бронювання (при одночасних запитах на один слот один отримує 201, решта 409) | `201 Created` | `400 Bad Request`, `409 Conflict` |
| **DELETE** | `/api/v1/bookings/{id}/` | Скасувати бронювання за ідентифікатором | `204 No Content` | `403 Forbidden`, `404 Not Found` |
| **GET** | `/api/v1/bookings/{id}/` | Отримати бронювання (викладач — лише власні, диспетчер — будь-які) | `200 OK` | `403 Forbidden`, `404 Not Found` |
| **POST** | `/api/v1/bookings/{id}/change/` | Змінити аудиторію бронювання (запис в аудит + сповіщення групі; збій PostgreSQL через deadlock чи serialization failure теж дає 409) | `200 OK` | `400 Bad Request`, `403 Forbidden`, `404 Not Found`, `409 Conflict` |
| **GET** | `/api/v1/bookings/{id}/alternatives/` | Підібрати вільні аудиторії для заміни (FR-010): за замовчуванням лише в бажаному корпусі (`building`, типово — корпус поточної аудиторії); якщо там варіантів немає, `message` пропонує розширити пошук; `expand=true` додає інші корпуси (спершу бажаний, далі найменша достатня місткість); `min_capacity` — потрібна місткість. Відповідь: `{building, expanded, rooms, message}` | `200 OK` | `400 Bad Request`, `403 Forbidden`, `404 Not Found`, `409 Conflict` |
| **POST** | `/api/v1/rooms/` | Створити аудиторію (диспетчер) | `201 Created` | `400 Bad Request`, `403 Forbidden` |
| **GET** | `/api/v1/rooms/{id}/` | Отримати аудиторію | `200 OK` | `404 Not Found` |
| **PATCH** | `/api/v1/rooms/{id}/` | Частково оновити аудиторію (диспетчер) | `200 OK` | `400 Bad Request`, `403 Forbidden`, `404 Not Found` |
| **DELETE** | `/api/v1/rooms/{id}/` | Видалити аудиторію без бронювань (диспетчер) | `204 No Content` | `403 Forbidden`, `404 Not Found`, `409 Conflict` |
| **GET** | `/api/v1/users/me/bookings/` | Отримати список бронювань поточного користувача | `200 OK` | `400 Bad Request` |
| **POST** | `/api/v1/sync/` | Імпортувати розклад із САЗ (FR-004, FR-005; лише диспетчер). САЗ показує розклад тільки після входу, тому тіло — `multipart/form-data` зі збереженою сторінкою розкладу (`file`) і `semester_start`. Відповідь — запис журналу синхронізації та підсумок імпорту (`summary`); нерозпізнана сторінка дає `status: failed`, раніше імпортовані дані не змінюються | `201 Created` | `400 Bad Request`, `403 Forbidden` |
| **GET** | `/api/v1/sync-logs/` | Отримати журнали синхронізації (лише диспетчер) | `200 OK` | `403 Forbidden` |
| **GET** | `/api/v1/auth/me/` | Профіль поточного користувача (`id`, `email`, `full_name`, `role`); потрібна активна сесія після входу через Microsoft | `200 OK` | `403 Forbidden` (користувач не автентифікований) |
| **GET** | `/api/v1/bookings/{id}/previous/` | Блок «Попередня пара» (FR-019): дисципліна, група й викладач заняття, що було в тій самій аудиторії того ж дня безпосередньо перед цим; якщо такого немає — `previous_lesson: null` і `message` «Попередньої пари не було». Викладач — лише для власних занять, диспетчер — для будь-яких | `200 OK` | `403 Forbidden`, `404 Not Found`, `409 Conflict` (бронювання скасоване) |
| **GET** | `/api/v1/audit-logs/` | Історія змін бронювань (FR-017, лише диспетчер): перенесення й скасування, хто, коли, з якої аудиторії в яку і чому. Найновіші першими; фільтри `booking_id`, `room_id`, `action` (`room_changed` / `cancelled`), `date_from`, `date_to`; пагінація `limit` (за замовчуванням 50, максимум 200) і `offset`. Лише читання | `200 OK` | `400 Bad Request`, `403 Forbidden` |
| **GET** | `/api/v1/schedule/` | Розклад: студент — своєї групи, викладач — власні заняття, диспетчер — будь-які (`date_from`, `date_to`, `group_id`, `limit`, `offset`); кожен елемент містить `booking_id` активного бронювання заняття або `null` (для переносу чи скасування) | `200 OK` | `400 Bad Request`, `403 Forbidden` |

*Примітка: Усі помилки (400, 403, 404, 409) повертаються в єдиній стандартизованій структурі `ErrorResponseSerializer`, яка містить поля `code`, `message`, `details`, `request_id` та `documentation`*.

## 4. Архітектурні рішення

### 4.1 Чому Code-First?
Ми обрали підхід Code-First (генерація контракту OpenAPI за допомогою `drf-spectacular` безпосередньо з коду Django REST Framework), тому що:
- документація та схема `docs/api/openapi-generated.yaml` завжди на 100% збігаються з реальною поведінкою контролерів та моделей у репозиторії;
- типи мови Python, валідатори DRF та схема Django ORM автоматично гарантують цілісність типів та обов'язковість полів;
- ітерації командної розробки проходять швидше без потреби вручну синхронізувати схеми; відсутня рутина підтримки громіздких YAML/JSON файлів вручну.

### 4.2 Стратегія пагінації
- **Пагінація зі зсувом (Limit/Offset Pagination):** Застосовується для каталогу аудиторій (`/api/v1/rooms/`), оскільки цей довідник має фіксовану структуру, потребує прямого переходу по сторінках та найпростіший для інтеграції з фільтрами UI. Ліміт за замовчуванням: 20 елементів. Максимальний ліміт: 100 елементів.
- **Курсорна пагінація (CursorPagination):** Застосовується для ендпоінтів списку бронювань (`/api/v1/users/me/bookings/`). Вона захищає від дублювання та пропуску записів при постійному додаванні нових броней у реальному часі та має високу швидкодію на великих обсягах даних.

### 4.3 Узгоджена структура обробки помилок
Єдиний машинозчитуваний формат серіалізації помилок на базі класу `ErrorSchemaSerializer`. Обов'язкові стандартизовані поля в тілі кожної помилки:
- `code`: машинозчитуваний строковий ідентифікатор помилки (`VALIDATION_ERROR`, `PERMISSION_DENIED`, `NOT_FOUND`, `ROOM_CONFLICT`).
- `message`: зрозуміле користувачу повідомлення для відображення у спливаючих вікнах або формах UI (вимога USAB-001).
- `details`: деталізований словник із помилками валідації по кожному конкретному полю форми.
- `request_id`: унікальний ідентифікатор запиту для наскрізного трасування та швидкого пошуку інцидентів у серверних логах.

### 4.4 Контроль конкурентності та транзакційність
- **Атомарність:** створення та зміна бронювань виконуються в межах `transaction.atomic()` у `services/bookings.py`.
- **Запобігання накладкам:** PostgreSQL `ExclusionConstraint` (`booking_active_room_time_excl`) на рівні моделі `Booking` забороняє перетин часових інтервалів активних бронювань однієї аудиторії. Суміжні інтервали `[start_time, end_time)` допускаються.
- **Обробка конфліктів:** `IntegrityError` перетворюється на `BookingConflictError`, який API повертає як `409 Conflict`.
- **Конкурентні транзакції:** deadlock (`40P01`) та serialization failure (`40001`) також обробляються як `409 Conflict`. Інші помилки БД не приховуються.
- **Перевірка REL-001:** інтеграційний тест із 10 паралельними запитами підтверджує, що лише одне бронювання створюється успішно, а решта отримують `409 Conflict`.

### 4.5 Ручний імпорт розкладу із САЗ (`POST /api/v1/sync/`)
САЗ не має публічного API і показує розклад лише після входу, тому UniSpace не завантажує сторінку сам: диспетчер надсилає збережену HTML-сторінку попереднього перегляду розкладу (`my.ukma.edu.ua/schedule/preview/...`).
- **Запит:** `multipart/form-data` з полями `file` (HTML, не більше 5 МБ) і `semester_start` (будь-який день першого навчального тижня семестру). Доступ лише для ролі `dispatcher`.
- **Відповідь `201 Created`:** запис журналу синхронізації (`id`, `started_at`, `finished_at`, `status`, `trigger`, `error_message`) та `summary` (`lessons_created`, `lessons_updated`, `bookings_created`, `conflicts_created`, `teachers_created`, `online_lessons`, `warnings`). Якщо сторінку не вдалося розібрати, відповідь теж `201`, але `status: failed`, `error_message` містить причину, а `summary` дорівнює `null`; раніше імпортовані дані не змінюються (REL-002).
- **Помилки:** `400` (немає `file` або `semester_start`, файл більший за 5 МБ), `403` (не диспетчер).
- **Ідемпотентність:** повторний імпорт того самого розкладу не створює дублікатів (заняття шукаються за `source_key`), а чинне бронювання заняття, зокрема перенесене викладачем, не змінюється. Накладки аудиторій записуються як `Conflict` замість бронювання (FR-013).
- **Консоль:** той самий імпорт і журнал доступні командою `python manage.py import_saz <файл> --semester-start РРРР-ММ-ДД`.
