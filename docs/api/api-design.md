# Дизайн API — UniSpace

## 1. Огляд архітектури

* **Базова адреса:** `http://localhost:8000/api/v1` (відповідно до C-004, бекенд розгорнуто як окремий Django-сервер на порті 8000).
* **Стиль API:** REST.
* **Автентифікація (FR-001, SEC-002):** Здійснюється через Microsoft Account (Microsoft Identity Platform / Azure AD) з використанням університетської електронної пошти. Клієнт передає сесійний Bearer-токен у стандартному HTTP-заголовку.
* **Формат відповіді:** JSON з відповідним кодом статусу HTTP.
* **Стратегія версіонування:** версія в URI-шляху (`/v1`, `/v2`).
  
---

## 2. Модель ресурсів

### 2.1 Аудиторії (Rooms)
* **Кінцева точка:** `/api/v1/rooms/`
* **Опис:** повертає каталог аудиторій університету. Для списку застосовується пагінація зі зсувом.
* **Атрибути:**
* id (integer) — унікальний ідентифікатор аудиторії в базі даних.
* name (string) - назва або номер аудиторії.
* capacity (integer) — кількість місць.
* has_projector (boolean) — наявність функціонуючого проєктора.

* **Зв'язки:**
* має багато бронювань (bookings)
* має багато доступних часових слотів (available_slots)  

### 2.2 Бронювання (Bookings)
* **Кінцева точка:** `/api/v1/bookings/`
* **Опис:** створення, перегляд та скасування бронювань аудиторій.
* **Атрибути:**
* id (integer): унікальний ідентифікатор бронювання
* room_id (integer): ідентифікатор заброньованої аудиторії
* title (string): тема або назва події / пари
* start_time (datetime): дата та час початку бронювання
* end_time (datetime): дата та час завершення бронювання
* status (string): статус бронювання (booked, active)
* **Зв'язки:**
* належить до однієї аудиторії (Room)
* належить до користувача (User), який створив бронювання 

### 2.3 Користувачі (Users)
* **Кінцева точка:** `/api/v1/users/me/bookings/`
* **Опис:** користувачі системи та доступ до їхніх особистих бронювань.
* **Атрибути:**
* role (enum): роль користувача у системі (student | teacher | dispatcher)
* is_authenticated (boolean): прапорець автентифікації користувача
* **Зв'язки:**
* має багато власних бронювань

## 3. Архітектурні рішення

### 3.1 Чому Code-First?
Ми обрали підхід Code-First (генерація контракту OpenAPI за допомогою drf-spectacular безпосередньо з коду Django REST Framework), тому що:
* документація та схема docs/api/openapi-generated.yaml завжди на 100% збігаються з реальною поведінкою контролерів та моделей у репозиторії;
* типи мови Python, валідатори DRF та схема Django ORM автоматично гарантують цілісність типів та обов'язковість полів;
* ітерації командної розробки проходять швидше без потреби вручну синхронізувати схеми;відсутня рутина підтримки громіздких YAML/JSON файлів вручну.

### 3.2 Стратегія пагінації
* Пагінація зі зсувом (Limit/Offset Pagination): Застосовується для каталогу аудиторій (/api/v1/rooms/), оскільки цей довідник має фіксовану структуру, потребує прямого переходу по сторінках та найпростіший для інтеграції з фільтрами UI.
* Ліміт за замовчуванням: 20 елементів.
* Максимальний ліміт: 100 елементів.
* Курсорна пагінація (CursorPagination): Застосовується для ендпоінтів списку бронювань (/api/v1/users/me/bookings/). Вона захищає від дублювання та пропуску записів при постійному додаванні нових броней у реальному часі та має високу швидкодію на великих обсягах даних.

### 3.3 Узгоджена структура обробки помилок
Єдиний машинозчитуваний формат серіалізації помилок на базі класу ErrorSchemaSerializer.
Обов'язкові стандартизовані поля в тілі кожної помилки:
* code: машинозчитуваний строковий ідентифікатор помилки (VALIDATION_ERROR, PERMISSION_DENIED, NOT_FOUND, ROOM_CONFLICT).
* message: зрозуміле користувачу повідомлення для відображення у спливаючих вікнах або формах UI (вимога USAB-001).
* details: деталізований словник із помилками валідації по кожному конкретному полю форми.
* request_id: унікальний ідентифікатор запиту для наскрізного трасування та швидкого пошуку інцидентів у серверних логах.

### 3.4 Контроль конкурентності та транзакційність
* Застосування атомарних транзакцій transaction.atomic() на рівні бази даних під час перевірки та фіксації бронювання.
* Використання блокування на рівні рядків SELECT ... FOR UPDATE для перевірки перетину таймслотів аудиторії.
* Повністю усуває ризик гонки (Race Condition / TOCTOU), гарантуючи успішне створення рівно одного бронювання при одночасних паралельних спробах зайняти аудиторію.
