# Дизайн API — UniSpace

## 1. Огляд архітектури
- **Базова адреса:** `http://localhost:8000/api/v1` (відповідно до C-004, бекенд розгорнуто як окремий Django-сервер на порті 8000).
- **Стиль API:** REST.
- **Автентифікація (FR-001, SEC-002):** Здійснюється через Microsoft Account (Microsoft Identity Platform / Azure AD) з використанням університетської електронної пошти. Після входу сервер створює сесію Django; клієнт передає сесійну cookie (`credentials: 'include'`), а для методів `POST`, `PATCH`, `DELETE` діє CSRF-захист DRF `SessionAuthentication` (заголовок `X-CSRFToken`). У production cookie мають атрибути `Secure` і `SameSite=None`, а CORS з `credentials` дозволено лише для довірених origin (локальний фронтенд і `unispace-front.onrender.com`).

| Метод    | Шлях                        | Призначення                                                                         | Входить до OpenAPI |
|:---------|:----------------------------|:------------------------------------------------------------------------------------|:------------------:|
| **GET**  | `/auth/microsoft/login/`    | Початок входу (перенаправлення на `MS_REDIRECT_URI`, далі до Microsoft)             |         Ні         |
| **GET**  | `/auth/microsoft/callback/` | Обробка відповіді Microsoft та створення сесії Django                               |         Ні         |
| **POST** | `/auth/logout/`             | Завершення сесії користувача                                                        |         Ні         |
| **GET**  | `/api/v1/auth/csrf/`        | Отримання CSRF-токена (`{"csrfToken": ...}` та cookie) для крос-доменного фронтенду |         Ні         |
| **GET**  | `/api/v1/auth/me/`          | Отримання профілю поточного автентифікованого користувача                           |        Так         |

- **Формат відповіді:** JSON з відповідним кодом статусу HTTP.
- **Стратегія версіонування:** версія в URI-шляху (`/v1`, `/v2`).

## 2. Модель ресурсів

### 2.1 Аудиторії (Rooms)
- **Кінцева точка:** `/api/v1/rooms/`
- **Опис:** повертає каталог аудиторій університету. Для списку застосовується пагінація зі зсувом.

| Атрибут             |      Тип      | Обов’язковість | Опис                                            |
|:--------------------|:-------------:|:--------------:|:------------------------------------------------|
| `id`                | string (UUID) |      Так       | Унікальний ідентифікатор аудиторії в базі даних |
| `building`          |    string     |      Так       | Корпус університету                             |
| `number`            |    string     |      Так       | Номер аудиторії (унікальний у межах корпусу)    |
| `capacity`          |    integer    |      Так       | Кількість місць                                 |
| `board_type`        |    string     |       Ні       | Тип дошки                                       |
| `projector_working` |    boolean    |      Так       | Наявність справного проєктора                   |
| `has_computers`     |    boolean    |      Так       | Наявність комп'ютерів                           |
| `is_available`      |    boolean    |      Так       | Загальна доступність аудиторії для використання |

- **Зв'язки:**
  - має багато бронювань (`bookings`)
  - має багато доступних часових слотів (`available_slots`)

### 2.2 Бронювання (Bookings)
- **Кінцева точка:** `/api/v1/bookings/`
- **Опис:** створення, перегляд, зміна аудиторії та скасування бронювань.

| Атрибут      |      Тип      | Обов’язковість | Опис                                                          |
|:-------------|:-------------:|:--------------:|:--------------------------------------------------------------|
| `id`         | string (UUID) |      Так       | Унікальний ідентифікатор бронювання                           |
| `lesson_id`  | string (UUID) |      Так       | Ідентифікатор заняття                                         |
| `room_id`    | string (UUID) |      Так       | Ідентифікатор аудиторії                                       |
| `user_id`    | string (UUID) |       Ні       | Автор бронювання (`null` для автоматично імпортованих із САЗ) |
| `start_time` |   datetime    |      Так       | Час початку бронювання                                        |
| `end_time`   |   datetime    |      Так       | Час завершення бронювання                                     |
| `status`     | string (enum) |      Так       | Статус бронювання: `active` або `cancelled`                   |
| `source`     | string (enum) |      Так       | Джерело створення: `saz` або `manual`                         |
| `created_at` |   datetime    |      Так       | Дата й час створення                                          |
| `updated_at` |   datetime    |      Так       | Дата й час останнього оновлення                               |

- **Зв'язки:**
  - належить до одного заняття (`Lesson`)
  - належить до однієї аудиторії (`Room`)
  - може мати автора (`User`)

### 2.3 Користувачі (Users)
- **Кінцеві точки:** `/api/v1/auth/me/`, `/api/v1/users/me/bookings/`
- **Опис:** профіль автентифікованого користувача системи та доступ до його особистих бронювань.

| Атрибут     |      Тип       | Обов’язковість | Опис                                                         |
|:------------|:--------------:|:--------------:|:-------------------------------------------------------------|
| `id`        | string (UUID)  |      Так       | Унікальний ідентифікатор користувача                         |
| `email`     | string (email) |      Так       | Університетська електронна пошта                             |
| `full_name` |     string     |       Ні       | Повне ім'я користувача                                       |
| `role`      | string (enum)  |      Так       | Роль у системі: `student`, `teacher` або `dispatcher`        |
| `group`     | string (UUID)  |       Ні       | Ідентифікатор академічної групи (заповнюється для студентів) |

- **Зв'язки:**
  - може належати до однієї академічної групи (`AcademicGroup`)
  - має багато власних бронювань (`bookings`)

## 3. Кінцеві точки та HTTP статус-коди

Згідно з підходом Code-First, усі відповіді та статус-коди автоматично генеруються з анотацій `@extend_schema` у коді контролерів. Нижче наведено зведену таблицю всіх 18 операцій API `/api/v1/` (детальні параметри запитів і формати відповідей для спеціалізованих ендпоінтів описано в п. 4.5–4.6):

| HTTP Метод | Шлях (Endpoint)                       | Призначення та доступ                                       |    Код успіху    | Коди помилок                                                        |
|:-----------|:--------------------------------------|:------------------------------------------------------------|:----------------:|:--------------------------------------------------------------------|
| **GET**    | `/api/v1/rooms/`                      | Список аудиторій (пагінація `limit`/`offset`)               |     `200 OK`     | `400 Bad Request`                                                   |
| **POST**   | `/api/v1/rooms/`                      | Створити аудиторію (диспетчер)                              |  `201 Created`   | `400 Bad Request`, `403 Forbidden`                                  |
| **GET**    | `/api/v1/rooms/{id}/`                 | Отримати деталі аудиторії                                   |     `200 OK`     | `404 Not Found`                                                     |
| **PATCH**  | `/api/v1/rooms/{id}/`                 | Частково оновити аудиторію (диспетчер)                      |     `200 OK`     | `400 Bad Request`, `403 Forbidden`, `404 Not Found`                 |
| **DELETE** | `/api/v1/rooms/{id}/`                 | Видалити аудиторію без бронювань (диспетчер)                | `204 No Content` | `403 Forbidden`, `404 Not Found`, `409 Conflict`                    |
| **GET**    | `/api/v1/rooms/available-slots/`      | Пошук вільних слотів аудиторії на дату                      |     `200 OK`     | `400 Bad Request`                                                   |
| **POST**   | `/api/v1/bookings/`                   | Створити бронювання (захист від гонок через БД)             |  `201 Created`   | `400 Bad Request`, `409 Conflict`                                   |
| **GET**    | `/api/v1/bookings/{id}/`              | Отримати бронювання (викладач — власні, диспетчер — усі)    |     `200 OK`     | `403 Forbidden`, `404 Not Found`                                    |
| **DELETE** | `/api/v1/bookings/{id}/`              | Скасувати бронювання за ідентифікатором                     | `204 No Content` | `403 Forbidden`, `404 Not Found`                                    |
| **POST**   | `/api/v1/bookings/{id}/change/`       | Змінити аудиторію бронювання (аудит + сповіщення групі)     |     `200 OK`     | `400 Bad Request`, `403 Forbidden`, `404 Not Found`, `409 Conflict` |
| **GET**    | `/api/v1/bookings/{id}/alternatives/` | Підбір вільних аудиторій для заміни (`FR-010`)              |     `200 OK`     | `400 Bad Request`, `403 Forbidden`, `404 Not Found`, `409 Conflict` |
| **GET**    | `/api/v1/bookings/{id}/previous/`     | Попереднє заняття в цій аудиторії (`FR-019`)                |     `200 OK`     | `403 Forbidden`, `404 Not Found`, `409 Conflict`                    |
| **GET**    | `/api/v1/users/me/bookings/`          | Список бронювань поточного користувача                      |     `200 OK`     | `400 Bad Request`                                                   |
| **GET**    | `/api/v1/schedule/`                   | Розклад за роллю користувача                                |     `200 OK`     | `400 Bad Request`, `403 Forbidden`                                  |
| **POST**   | `/api/v1/sync/`                       | Імпорт розкладу із САЗ (`FR-004`, `FR-005`, лише диспетчер) |  `201 Created`   | `400 Bad Request`, `403 Forbidden`                                  |
| **GET**    | `/api/v1/sync-logs/`                  | Журнали синхронізації (диспетчер)                           |     `200 OK`     | `403 Forbidden`                                                     |
| **GET**    | `/api/v1/audit-logs/`                 | Історія змін бронювань (`FR-017`, диспетчер)                |     `200 OK`     | `400 Bad Request`, `403 Forbidden`                                  |
| **GET**    | `/api/v1/auth/me/`                    | Профіль поточного автентифікованого користувача             |     `200 OK`     | `403 Forbidden`                                                     |

*Примітка: Усі помилки (`400`, `403`, `404`, `409`) повертаються в єдиній стандартизованій структурі `ErrorResponseSerializer` з кореневим об'єктом `error` (див. п. 4.3).*

## 4. Архітектурні рішення

### 4.1 Чому Code-First?
Ми обрали підхід Code-First (генерація контракту OpenAPI за допомогою `drf-spectacular` безпосередньо з коду Django REST Framework), тому що:
- документація та схема `docs/api/openapi-generated.yaml` завжди на 100% збігаються з реальною поведінкою контролерів та моделей у репозиторії;
- типи мови Python, валідатори DRF та схема Django ORM автоматично гарантують цілісність типів та обов'язковість полів;
- ітерації командної розробки проходять швидше без потреби вручну синхронізувати схеми; відсутня рутина підтримки громіздких YAML/JSON файлів вручну.

### 4.2 Стратегія пагінації

| Тип пагінації        | Застосування                                                                                       | Параметри / ліміти                                                            | Обґрунтування                                                                              |
|:---------------------|:---------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------|
| **Limit / Offset**   | Каталог аудиторій (`/api/v1/rooms/`), розклад (`/api/v1/schedule/`), аудит (`/api/v1/audit-logs/`) | Типово 20 (макс. 100) для аудиторій; типово 50 (макс. 200) для журналу аудиту | Фіксована або архівна структура, зручний перехід по сторінках та інтеграція з фільтрами UI |
| **CursorPagination** | Список особистих бронювань (`/api/v1/users/me/bookings/`)                                          | Курсорний токен (`cursor`)                                                    | Захищає від дублювання та пропуску записів при додаванні нових бронювань у реальному часі  |

### 4.3 Узгоджена структура обробки помилок
Усі помилки API повертаються в єдиному машинозчитуваному форматі на базі класу `ErrorResponseSerializer` (кореневий ключ `error`, схема `ErrorSchemaSerializer`). Поля об'єкта `error`:

| Поле            |     Тип      | Обов’язковість | Опис                                                                                                         |
|:----------------|:------------:|:--------------:|:-------------------------------------------------------------------------------------------------------------|
| `code`          |    string    |      Так       | Машинозчитуваний код помилки (`VALIDATION_ERROR`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`)                      |
| `message`       |    string    |      Так       | Зрозуміле користувачу повідомлення для відображення в інтерфейсі (вимога `USAB-001`)                         |
| `details`       |    array     |       Ні       | Список об'єктів `ErrorDetailSerializer` (`field`, `message`, `provided_value`) для помилок валідації (`400`) |
| `request_id`    |    string    |      Так       | Унікальний ідентифікатор запиту для трасування та пошуку інцидентів у логах                                  |
| `documentation` | string (URL) |      Так       | Посилання на опис відповідного типу помилки в документації                                                   |

### 4.4 Контроль конкурентності та транзакційність
- **Атомарність:** створення та зміна бронювань виконуються в межах `transaction.atomic()` у `services/bookings.py`.
- **Запобігання накладкам:** PostgreSQL `ExclusionConstraint` (`booking_active_room_time_excl`) на рівні моделі `Booking` забороняє перетин часових інтервалів активних бронювань однієї аудиторії. Суміжні інтервали `[start_time, end_time)` допускаються.
- **Обробка конфліктів:** `IntegrityError` перетворюється на `BookingConflictError`, який API повертає як `409 Conflict`.
- **Конкурентні транзакції:** deadlock (`40P01`) та serialization failure (`40001`) також обробляються як `409 Conflict`. Інші помилки БД не приховуються.
- **Перевірка REL-001:** інтеграційний тест із 10 паралельними запитами підтверджує, що лише одне бронювання створюється успішно, а решта отримують `409 Conflict`.

### 4.5 Ручний імпорт розкладу із САЗ (`POST /api/v1/sync/`)
САЗ не має публічного API і показує розклад лише після входу, тому UniSpace не завантажує сторінку сам: диспетчер надсилає збережену HTML-сторінку попереднього перегляду розкладу (`my.ukma.edu.ua/schedule/preview/...`).
- **Запит:** `multipart/form-data` з полями `file` (HTML, не більше 5 МБ) і `semester_start` (будь-який день першого навчального тижня семестру). Доступ лише для ролі `dispatcher`.
- **Відповідь `201 Created`:** запис журналу синхронізації (`id`, `started_at`, `finished_at`, `status`, `trigger`, `error_message`) та `summary` (`lessons_created`, `lessons_updated`, `bookings_created`, `conflicts_created`, `teachers_created`, `online_lessons`, `warnings`). Якщо сторінку не вдалося розібрати, відповідь теж `201`, але `status: failed`, `error_message` містить причину, а `summary` дорівнює `null`; раніше імпортовані дані не змінюються (REL-002).
- **Помилки:** `400` (немає `file` або `semester_start`, файл більший за 5 МБ), `403` (не диспетчер).
- **Ідемпотентність:** повторний імпорт того самого розкладу не створює дублікатів (заняття шукаються за `source_key`), а чинне бронювання заняття, зокрема перенесене викладачем, не змінюється. Накладки аудиторій записуються як `Conflict` замість бронювання (FR-013).
- **Консоль:** той самий імпорт і журнал доступні командою `python manage.py import_saz <файл> --semester-start РРРР-ММ-ДД`.

### 4.6 Особливості параметрів і контрактів спеціалізованих ендпоінтів

| Ендпоінт                                             | Параметри запиту                                                                                                                   | Формат відповіді та поведінка                                                                                                                                                        | Доступ і обмеження                                                                    |
|:-----------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------|
| `GET /api/v1/bookings/{id}/alternatives/` (`FR-010`) | `building` (типово — корпус поточної аудиторії), `expand` (`false` / `true`), `min_capacity`                                       | `{building, expanded, rooms, message}`; без `expand=true` шукає лише у вказаному корпусі, із `expand=true` — у всіх корпусах (спершу пріоритетний, далі найменша достатня місткість) | Викладач — власні заняття, диспетчер — усі; для скасованого бронювання повертає `409` |
| `GET /api/v1/bookings/{id}/previous/` (`FR-019`)     | —                                                                                                                                  | `{previous_lesson, message}`; повертає дисципліну, групу й викладача попередньої пари в цій самій аудиторії того ж дня або `previous_lesson: null`                                   | Викладач — власні заняття, диспетчер — усі; для скасованого бронювання повертає `409` |
| `GET /api/v1/schedule/`                              | `date_from`, `date_to`, `group_id` (лише для диспетчера), `limit`, `offset`                                                        | Список занять із полем `booking_id` активного бронювання (або `null` для дій перенесення чи скасування)                                                                              | Студент — своя група, викладач — власні заняття, диспетчер — будь-які                 |
| `GET /api/v1/audit-logs/` (`FR-017`)                 | `booking_id`, `room_id`, `action` (`room_changed` / `cancelled`), `date_from`, `date_to`, `limit` (типово 50, макс. 200), `offset` | Історія перенесень і скасувань від найновіших записів до старіших (`only-read`)                                                                                                      | Лише роль `dispatcher`                                                                |
