# Атрибути якості API — UniSpace

## 1. Мета

Цей документ визначає вимірювані атрибути якості REST API UniSpace, умови, за яких відповідна ціль вважається невиконаною, та спосіб її перевірки.

Цілі узгоджені з нефункціональними вимогами UniSpace та API, реалізованим у межах Лабораторної роботи 4.

---

## 2. Основні атрибути якості

Для API UniSpace основними атрибутами якості є:

- продуктивність (Performance);
- надійність і цілісність даних (Reliability);
- безпека (Security);
- зручність використання API та валідація (Usability);
- підтримуваність (Maintainability).

Для системи бронювання аудиторій пріоритет мають цілісність даних, контроль доступу та передбачувана обробка помилкових запитів.

---

## 3. Вимірювані цілі якості

| ID | Атрибут | Ціль | Умова провалу | Перевірка |
|---|---|---|---|---|
| QA-01 | Performance | Сторінка тижневого розкладу повинна завантажуватися за ≤ 500 мс (p95) при 100 одночасних користувачах і наборі з 300 аудиторій | p95 > 500 мс | Навантажувальне тестування |
| QA-02 | Reliability | При 10 паралельних спробах забронювати одну аудиторію на один часовий слот повинно бути створено не більше одного активного бронювання | Створено більше одного активного бронювання на один слот | Конкурентний інтеграційний тест |
| QA-03 | Security | Усі API-операції, що змінюють стан бронювання, повинні повертати HTTP 403 для користувача з роллю `student` | Хоча б одна write-операція доступна користувачу з роллю `student` | Authorization test |
| QA-04 | Validation | 100% перевірених невалідних вхідних параметрів повинні повертати контрольовану HTTP 4xx відповідь, а не HTTP 500 | Хоча б один перевірений невалідний запит приймається як валідний або спричиняє HTTP 500 | Swagger UI |
| QA-05 | Maintainability | 100% endpoint'ів Lab 4 повинні бути представлені в автоматично згенерованій OpenAPI-специфікації | Endpoint існує в коді, але відсутній у Swagger/OpenAPI або специфікація не відповідає коду | Порівняння URL configuration, Swagger UI та generated OpenAPI |

## 4. Сценарії якості

### QA-01 — Performance

**Стимул:** 100 користувачів одночасно звертаються до системи для перегляду тижневого розкладу.

**Очікуваний результат:** p95 часу завантаження не перевищує 500 мс.

**Умова провалу:** p95 перевищує 500 мс.

**Пов'язана вимога:** PERF-001.

---

### QA-02 — Reliability

**Стимул:** 10 паралельних запитів намагаються забронювати одну аудиторію на один часовий слот.

**Очікуваний результат:** лише один запит створює активне бронювання, інші конфліктні операції відхиляються.

**Умова провалу:** створено два або більше активних бронювань на один часовий слот.

**Пов'язана вимога:** REL-001.

---

### QA-03 — Security

**Стимул:** користувач із роллю `student` виконує API-запит, який змінює стан бронювання.

**Очікуваний результат:** API повертає HTTP 403 Forbidden.

**Умова провалу:** операція виконується або повертається успішний 2xx status code.

**Пов'язана вимога:** SEC-001.

---

### QA-04 — Validation

**Стимул:** клієнт передає невалідний query parameter або request body.

**Очікуваний результат:** API повертає контрольовану HTTP 4xx відповідь з описом помилки.

**Умова провалу:** API приймає невалідне значення або повертає HTTP 500.

**Перевірка:** ручне тестування через Swagger UI.

---

### QA-05 — Maintainability

**Стимул:** до Code-First API додається або змінюється endpoint.

**Очікуваний результат:** зміна відображається в автоматично згенерованій OpenAPI-специфікації та Swagger UI.

**Умова провалу:** реалізація API та згенерована документація не збігаються.

**Перевірка:** генерація OpenAPI через drf-spectacular та CI.

---

## 5. Trade-offs Analysis

### Reliability vs Performance

Перевірка конфліктів і використання транзакцій можуть збільшувати час виконання операції бронювання, але запобігання подвійним бронюванням важливіше за мінімальну затримку write-операцій.

**Пріоритет:** Reliability > Performance.

### Security vs Performance

Перевірка автентифікації, ролі користувача та його дозволів створює додаткову обробку API-запиту. Для операцій, які змінюють бронювання, контроль доступу має вищий пріоритет.

**Пріоритет:** Security > Performance.

### Maintainability vs Scalability

UniSpace є навчальним проєктом з обмеженим очікуваним навантаженням. Тому перевага надається простій архітектурі Django + PostgreSQL, Code-First API та автоматично згенерованій документації замість передчасного ускладнення системи для горизонтального масштабування.

**Пріоритет:** Maintainability > Scalability.

## 6. Перевірка валідації через Swagger UI

У межах ролі Quality Lead було проведено ручну перевірку валідації всіх endpoint'ів Lab 4 через Swagger UI. Перевірялися як валідні запити, так і некоректні значення query-параметрів та request body.

| Endpoint | Перевірка | Очікуваний результат | Фактичний результат | Статус |
|---|---|---|---|---|
| `POST /api/v1/bookings/` | Валідний request body | HTTP 201 | HTTP 201 | PASS |
| `POST /api/v1/bookings/` | `room_id=0` | HTTP 400 | HTTP 400 | PASS |
| `POST /api/v1/bookings/` | `start_time >= end_time` | HTTP 400 | HTTP 400 | PASS |
| `POST /api/v1/bookings/` | Відсутнє обов'язкове поле | HTTP 400 | HTTP 400 | PASS |
| `POST /api/v1/bookings/` | `title` довший за 100 символів | HTTP 400 | HTTP 400 | PASS |
| `GET /api/v1/rooms/` | Валідні параметри | HTTP 200 | HTTP 200 | PASS |
| `GET /api/v1/rooms/` | `limit=-1` | HTTP 400 | HTTP 400 | PASS |
| `GET /api/v1/rooms/` | `offset=-1` | HTTP 400 | HTTP 400 | PASS |
| `GET /api/v1/rooms/` | `capacity=0` | HTTP 400 | HTTP 400 | PASS |
| `GET /api/v1/rooms/available-slots/` | Валідні `room_id` та `date` | HTTP 200 | HTTP 200 | PASS |
| `GET /api/v1/rooms/available-slots/` | Відсутній `room_id` | HTTP 400 | HTTP 400 | PASS |
| `GET /api/v1/rooms/available-slots/` | `room_id=0` | HTTP 400 | HTTP 400 | PASS |
| `GET /api/v1/rooms/available-slots/` | Неправильний формат `date` | HTTP 400 | HTTP 400 | PASS |
| `GET /api/v1/users/me/bookings/` | Валідний `limit` | HTTP 200 | HTTP 200 | PASS |
| `GET /api/v1/users/me/bookings/` | `limit=0` | HTTP 400 | HTTP 400 | PASS |
| `DELETE /api/v1/bookings/{id}/` | Валідний позитивний `id` | HTTP 204 | HTTP 204 | PASS |
| `DELETE /api/v1/bookings/{id}/` | `id=0` | HTTP 404 | HTTP 404 | PASS |

Усі заплановані Swagger UI validation tests пройдені успішно. Невалідні значення були відхилені контрольованими HTTP 4xx відповідями та не призвели до HTTP 500.

Таким чином, для перевіреного набору сценаріїв ціль **QA-04 (Validation) виконана**.

Наприклад, для `POST /api/v1/bookings/` передача `room_id=0` повертає HTTP 400 з кодом `VALIDATION_ERROR` та вказує поле `room_id` як причину помилки.

## 7. Поточні обмеження Lab 4

API в межах Lab04 спочатку був реалізований як Code-First stub із mock-даними.

Під час Lab05 було виявлено та виправлено проблему контролю доступу в класі `IsTeacherOrDispatcher`. Раніше метод `has_permission()` завжди повертав `True`, через що створення та видалення бронювань були доступні навіть неавторизованим користувачам.

Після виправлення додано перевірку автентифікації та ролей `teacher` і `dispatcher`. Також створено чотири регресійні тести, які перевіряють заборону створення та видалення бронювань для анонімних користувачів і студентів (HTTP 403).

Після виправлення всі 22 Django-тести пройшли успішно. Таким чином, вимога **SEC-001 частково підтверджена автоматизованими тестами RBAC**.

Водночас повна інтеграція з Microsoft Account і перевірка прав доступу з реальними користувачами ще потребують додаткового тестування.

Перевірка REL-001 потребує реальної персистентності та конкурентних операцій із PostgreSQL. Її виконання не підтверджується лише mock-тестами.

Задокументований HTTP 409 Conflict для конфліктного бронювання також потребує перевірки реальної бізнес-логіки.

Отже, Swagger UI validation tests підтверджують QA-04, а регресійні тести RBAC надають окреме підтвердження SEC-001 у межах перевірених сценаріїв. Повне підтвердження SEC-001 та REL-001 потребує подальших інтеграційних тестів.
