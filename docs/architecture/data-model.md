# Модель даних UniSpace

## 1. Призначення

Цей документ описує логічну модель даних UniSpace. Для проєкту обрано ER-модель, оскільки система використовує реляційну базу даних, а ключовими для моделювання є сутності, їх атрибути, первинні та зовнішні ключі й зв’язки між ними.

Модель враховує актуальну архітектуру UniSpace: Django, Django ORM, PostgreSQL, автентифікацію через Microsoft Account з університетською електронною поштою та односторонній імпорт розкладу із САЗ.

ER-діаграма знаходиться у файлі `docs/architecture/uml/data_model.puml`.

## 2. Ключові функції, які покриває модель

ER-модель охоплює дані для 7 ключових функцій UniSpace:

1. керування користувачами, ролями та академічними групами;
2. синхронізація і перегляд розкладу із САЗ;
3. ведення довідника аудиторій;
4. бронювання, зміна та скасування бронювань аудиторій;
5. виявлення та розв’язання конфліктів;
6. внутрішні сповіщення;
7. ведення історії змін в аудит-лозі.

## 3. Основні сутності

### 3.1 User

Представляє користувача UniSpace, який проходить автентифікацію через Microsoft Account.

**Атрибути:**
- `id` — UUID, первинний ключ;
- `external_identity_id` — стабільний зовнішній ідентифікатор користувача від Microsoft;
- `email` — університетська електронна пошта;
- `full_name` — повне ім’я користувача;
- `role` — роль користувача: `student`, `teacher` або `dispatcher`;
- `group_id` — необов’язковий зовнішній ключ на `AcademicGroup`, використовується для студентів.

**Персональні та чутливі дані:**
- `external_identity_id` — чутливі дані, пов’язані з ідентифікацією користувача;
- `email` — персональні дані;
- `full_name` — персональні дані.

Модель `User` успадковує `django.contrib.auth.models.AbstractUser`, тому також має стандартні поля та механізми Django, не перелічені в цій логічній ER-моделі. Для входу через Microsoft Account система не зберігає пароль облікового запису Microsoft. Права доступу визначаються на основі ролі користувача.

### 3.2 AcademicGroup

Представляє академічну групу студентів.

**Атрибути:**
- `id` — UUID, первинний ключ;
- `name` — назва групи;
- `source_key` — логічний ідентифікатор для зіставлення даних під час повторної синхронізації із САЗ.

### 3.3 Lesson

Представляє заняття, імпортоване із САЗ.

**Атрибути:**
- `id` — UUID, первинний ключ;
- `source_key` — логічний ідентифікатор для повторної синхронізації без створення дублікатів;
- `subject` — назва дисципліни;
- `date` — дата заняття;
- `start_time` — час початку заняття;
- `end_time` — час завершення заняття;
- `teacher_id` — зовнішній ключ на `User`;
- `group_id` — зовнішній ключ на `AcademicGroup`.

Предмет, група, дата та час заняття надходять із САЗ і не змінюються UniSpace у зовнішній системі.

### 3.4 Room

Представляє університетську аудиторію.

**Атрибути:**
- `id` — UUID, первинний ключ;
- `building` — корпус;
- `number` — номер аудиторії;
- `capacity` — місткість;
- `board_type` — необов’язковий тип дошки;
- `projector_working` — наявність справного проєктора;
- `has_computers` — наявність комп’ютерів;
- `is_available` — загальна доступність аудиторії для використання.

Доступність аудиторії на конкретний часовий проміжок визначається на основі активних бронювань.

### 3.5 Booking

Представляє призначення аудиторії для конкретного заняття.

**Атрибути:**
- `id` — UUID, первинний ключ;
- `lesson_id` — зовнішній ключ на `Lesson`;
- `room_id` — зовнішній ключ на `Room`;
- `user_id` — необов'язковий зовнішній ключ на `User`, автор бронювання;
- `start_time` — дата й час початку бронювання;
- `end_time` — дата й час завершення бронювання;
- `status` — `active` або `cancelled`;
- `source` — `saz` або `manual`;
- `created_at` — дата й час створення;
- `updated_at` — дата й час останнього оновлення.

Поле `title` у моделі Booking відсутнє, оскільки назва дисципліни зберігається в пов'язаній сутності `Lesson`.

Часові поля `start_time` та `end_time` зберігаються окремо в Booking, оскільки вони потрібні для перевірки перетинів через PostgreSQL `ExclusionConstraint`. Метод `save()` автоматично встановлює їх на основі дати й часу пов'язаного заняття (`Lesson`).

Система не повинна дозволяти декілька активних бронювань однієї аудиторії на часові проміжки, що перетинаються. Скасування бронювання не видаляє заняття.

### 3.6 Conflict

Представляє конфлікт, коли два заняття призначені в одну аудиторію на час, що перетинається.

**Атрибути:**
- `id` — UUID, первинний ключ;
- `first_lesson_id` — зовнішній ключ на перше `Lesson`;
- `second_lesson_id` — зовнішній ключ на друге `Lesson`;
- `room_id` — зовнішній ключ на `Room`;
- `overlap_start` — початок перетину;
- `overlap_end` — кінець перетину;
- `detected_at` — дата й час виявлення;
- `status` — `open` або `resolved`;
- `resolved_at` — необов’язкова дата й час розв’язання.

### 3.7 Notification

Представляє внутрішнє сповіщення користувача.

**Атрибути:**
- `id` — UUID, первинний ключ;
- `user_id` — зовнішній ключ на `User`;
- `type` — тип сповіщення, наприклад `room_changed` або `schedule_conflict`;
- `message` — текст сповіщення;
- `created_at` — дата й час створення;
- `is_read` — ознака прочитання.

`user_id` пов’язує сповіщення з конкретним користувачем і тому є персональними даними.

### 3.8 AuditLog

Представляє історію змін бронювань.

**Атрибути:**
- `id` — UUID, первинний ключ;
- `booking_id` — зовнішній ключ на `Booking`;
- `user_id` — зовнішній ключ на `User`, який виконав дію;
- `action` — наприклад `room_changed` або `booking_cancelled`;
- `previous_room_id` — необов’язковий зовнішній ключ на попередню `Room`;
- `new_room_id` — необов’язковий зовнішній ключ на нову `Room`;
- `reason` — необов’язкова причина зміни;
- `created_at` — дата й час дії.

На рівні Django ORM для `AuditLog` реалізовано append-only поведінку через `AppendOnlyManager` та перевизначені методи `save()` і `delete()`. Повний захист від змін безпосередньо в PostgreSQL ще не реалізовано. Зберігання записів щонайменше 12 місяців залишається вимогою, механізм забезпечення якої потребує реалізації.

`user_id` пов’язує дію з конкретним користувачем і є персональними даними.

### 3.9 SyncLog

Представляє журнал спроб синхронізації розкладу із САЗ.

**Атрибути:**
- `id` — UUID, первинний ключ;
- `started_at` — дата й час початку;
- `finished_at` — необов'язкова дата й час завершення;
- `status` — `in_progress`, `success` або `failed`;
- `trigger` — `manual` або `scheduled`, джерело запуску синхронізації;
- `error_message` — повідомлення про помилку.

Під час виконання синхронізація має статус `in_progress`. Після завершення статус змінюється на `success` або `failed`.

Відповідно до ADR-003, для запобігання паралельним синхронізаціям передбачено частковий унікальний індекс для записів зі статусом `in_progress`. У поточному `Backend/api/models.py` це обмеження в `SyncLog.Meta` не оголошено; воно залишається запланованим архітектурним рішенням.

У разі помилки синхронізації система продовжує працювати з останнім успішно імпортованим знімком даних.

## 4. Зв’язки між сутностями

- `User` може належати до однієї `AcademicGroup` або не мати групи;
- одна `AcademicGroup` може містити багато користувачів-студентів;
- одна `AcademicGroup` може мати багато `Lesson`;
- один викладач `User` може проводити багато `Lesson`;
- кожне `Lesson` належить одній `AcademicGroup` і пов’язане з одним викладачем;
- одне `Lesson` може мати пов’язані записи `Booking`;
- кожне `Booking` належить одному `Lesson` та одній `Room`;
- кожне `Booking` може бути пов'язане з одним `User` — автором бронювання; поле `user_id` необов'язкове;
- одна `Room` може мати багато бронювань у різний час;
- кожен `Conflict` посилається на два `Lesson` та одну `Room`;
- один `User` може отримувати багато `Notification`;
- одне `Booking` може мати багато `AuditLog`;
- один `User` може бути автором багатьох записів `AuditLog`;
- `previous_room_id` і `new_room_id` в `AuditLog` є необов’язковими.

## 5. Основні правила цілісності

- САЗ є джерелом істини для академічного розкладу; UniSpace лише зчитує дані й не записує зміни назад.
- Повторний імпорт незміненого розкладу не повинен створювати дублікати занять або початкових бронювань.
- Одна аудиторія не може мати декілька активних бронювань на часові проміжки, що перетинаються.
- Скасування бронювання переводить його в `cancelled`, але не видаляє заняття.
- Студенти не можуть змінювати бронювання; викладачі можуть змінювати власні заняття; диспетчер має розширені права відповідно до вимог.
- Зміни аудиторій і скасування бронювань фіксуються в `AuditLog`.
- Для `AuditLog` реалізовано append-only обмеження на рівні Django ORM; захист на рівні PostgreSQL та гарантоване зберігання протягом 12 місяців ще потребують реалізації.
- У разі помилки синхронізації із САЗ останній успішний знімок розкладу залишається доступним.

## 6. Персональні та чутливі дані

Для подальшого STRIDE-аналізу в моделі явно позначено:

- `User.external_identity_id` — чутливі дані;
- `User.email` — персональні дані;
- `User.full_name` — персональні дані;
- `Notification.user_id` — персональні дані;
- `AuditLog.user_id` — персональні дані.

UniSpace не зберігає паролі Microsoft Account.

## 7. Відкриті питання реалізації

У документації не визначено, який саме стабільний claim Microsoft буде використаний як `external_identity_id`.

Також не визначено точний механізм зіставлення викладача, імпортованого із САЗ, з відповідним Microsoft-автентифікованим користувачем UniSpace.
