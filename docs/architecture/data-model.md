# Модель даних UniSpace

## 1. Призначення

Цей документ описує логічну модель даних UniSpace. Для проєкту обрано ER-модель, оскільки система використовує реляційну базу даних, а ключовими для моделювання є сутності, їх атрибути, первинні та зовнішні ключі й зв’язки між ними.

Модель враховує актуальну архітектуру UniSpace: Django, Django ORM, PostgreSQL, автентифікацію через Microsoft Account з університетською електронною поштою та односторонній імпорт розкладу із САЗ.

ER-діаграма знаходиться у файлі [`docs/architecture/uml/data_model.puml`](uml/data_model.puml).
## 2. Ключові функції, які покриває модель

ER-модель охоплює дані для 7 ключових функцій UniSpace:

1. керування користувачами, ролями та академічними групами;
2. синхронізація і перегляд розкладу із САЗ;
3. ведення довідника аудиторій;
4. бронювання, зміна та скасування бронювань аудиторій;
5. виявлення та розв’язання конфліктів;
6. внутрішні сповіщення;
7. ведення історії змін в аудит-лозі.

## 3. Основні сутності

### 3.1 User

Представляє користувача UniSpace, який проходить автентифікацію через Microsoft Account.

| Атрибут                | Тип / Ключ                  | Обов’язковість | Опис                                                                                                   |
|:-----------------------|:----------------------------|:--------------:|:-------------------------------------------------------------------------------------------------------|
| `id`                   | UUID (PK)                   |      Так       | Первинний ключ                                                                                         |
| `external_identity_id` | String (Unique)             |       Ні       | Стабільний зовнішній ідентифікатор користувача від Microsoft — claim `oid` з `id_token` (чутливі дані) |
| `email`                | Email (Unique)              |      Так       | Університетська електронна пошта (персональні дані)                                                    |
| `full_name`            | String                      |       Ні       | Повне ім’я користувача (персональні дані)                                                              |
| `role`                 | Enum                        |      Так       | Роль користувача: `student`, `teacher` або `dispatcher`                                                |
| `group_id`             | UUID (FK → `AcademicGroup`) |       Ні       | Зовнішній ключ на групу, використовується для студентів                                                |

Модель `User` успадковує `django.contrib.auth.models.AbstractUser`, тому також має стандартні поля та механізми Django, не перелічені в цій логічній ER-моделі. Для входу через Microsoft Account система не зберігає пароль облікового запису Microsoft. Права доступу визначаються на основі ролі користувача.

### 3.2 AcademicGroup

Представляє академічну групу студентів.

| Атрибут      | Тип / Ключ      | Обов’язковість | Опис                                                                                                                                                                                   |
|:-------------|:----------------|:--------------:|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `id`         | UUID (PK)       |      Так       | Первинний ключ                                                                                                                                                                         |
| `name`       | String          |      Так       | Назва групи                                                                                                                                                                            |
| `source_key` | String (Unique) |      Так       | Логічний ідентифікатор для зіставлення даних під час повторної синхронізації із САЗ; формується як `saz:group:<хеш>` (хеш від спеціальності, року набору та номера групи або «лекція») |

### 3.3 Lesson

Представляє заняття, імпортоване із САЗ.

| Атрибут      | Тип / Ключ                  | Обов’язковість | Опис                                                                                                                                                                       |
|:-------------|:----------------------------|:--------------:|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `id`         | UUID (PK)                   |      Так       | Первинний ключ                                                                                                                                                             |
| `source_key` | String (Unique)             |      Так       | Логічний ідентифікатор для уникнення дублікатів; формується як `saz:lesson:<хеш>` (хеш від спеціальності, року набору, групи, дати, часу початку, дисципліни та викладача) |
| `subject`    | String                      |      Так       | Назва дисципліни                                                                                                                                                           |
| `date`       | Date                        |      Так       | Дата заняття                                                                                                                                                               |
| `start_time` | Time                        |      Так       | Час початку заняття                                                                                                                                                        |
| `end_time`   | Time                        |      Так       | Час завершення заняття                                                                                                                                                     |
| `teacher_id` | UUID (FK → `User`)          |      Так       | Зовнішній ключ на викладача                                                                                                                                                |
| `group_id`   | UUID (FK → `AcademicGroup`) |      Так       | Зовнішній ключ на академічну групу                                                                                                                                         |

Предмет, група, дата та час заняття надходять із САЗ і не змінюються UniSpace у зовнішній системі.

Імпорт розгортає кожен рядок розкладу на заняття за тижнями семестру: `дата = понеділок першого тижня + (номер тижня − 1) тижнів + день тижня`. Повторний імпорт оновлює заняття за `source_key`, а чинне активне бронювання заняття (зокрема перенесене викладачем) не змінює.

### 3.4 Room

Представляє університетську аудиторію.

| Атрибут             | Тип / Ключ | Обов’язковість | Опис                                            |
|:--------------------|:-----------|:--------------:|:------------------------------------------------|
| `id`                | UUID (PK)  |      Так       | Первинний ключ                                  |
| `building`          | String     |      Так       | Корпус                                          |
| `number`            | String     |      Так       | Номер аудиторії (унікальний у межах корпусу)    |
| `capacity`          | Integer    |      Так       | Місткість (додатне значення)                    |
| `board_type`        | String     |       Ні       | Тип дошки                                       |
| `projector_working` | Boolean    |      Так       | Наявність справного проєктора                   |
| `has_computers`     | Boolean    |      Так       | Наявність комп’ютерів                           |
| `is_available`      | Boolean    |      Так       | Загальна доступність аудиторії для використання |

Доступність аудиторії на конкретний часовий проміжок визначається на основі активних бронювань.

### 3.5 Booking

Представляє призначення аудиторії для конкретного заняття.

| Атрибут      | Тип / Ключ           | Обов’язковість | Опис                                  |
|:-------------|:---------------------|:--------------:|:--------------------------------------|
| `id`         | UUID (PK)            |      Так       | Первинний ключ                        |
| `lesson_id`  | UUID (FK → `Lesson`) |      Так       | Зовнішній ключ на заняття             |
| `room_id`    | UUID (FK → `Room`)   |      Так       | Зовнішній ключ на аудиторію           |
| `user_id`    | UUID (FK → `User`)   |       Ні       | Автор бронювання                      |
| `start_time` | DateTime             |      Так       | Дата й час початку бронювання         |
| `end_time`   | DateTime             |      Так       | Дата й час завершення бронювання      |
| `status`     | Enum                 |      Так       | Статус: `active` або `cancelled`      |
| `source`     | Enum                 |      Так       | Джерело створення: `saz` або `manual` |
| `created_at` | DateTime             |      Так       | Дата й час створення                  |
| `updated_at` | DateTime             |      Так       | Дата й час останнього оновлення       |

Поле `title` у моделі `Booking` відсутнє, оскільки назва дисципліни зберігається в пов'язаній сутності `Lesson`.

Часові поля `start_time` та `end_time` зберігаються окремо в `Booking`, оскільки вони потрібні для перевірки перетинів через PostgreSQL `ExclusionConstraint` (`booking_active_room_time_excl`). Окрім цього, частковий унікальний індекс `uniq_active_booking_per_lesson` гарантує наявність не більше одного активного бронювання на кожне заняття. Метод `save()` автоматично встановлює `start_time` та `end_time` на основі дати й часу пов'язаного заняття (`Lesson`).

Система не повинна дозволяти декілька активних бронювань однієї аудиторії на часові проміжки, що перетинаються, або кілька активних бронювань для одного заняття. Скасування бронювання переводить його в статус `cancelled` і не видаляє заняття.

### 3.6 Conflict

Представляє конфлікт, коли два заняття призначені в одну аудиторію на час, що перетинається.

| Атрибут            | Тип / Ключ           | Обов’язковість | Опис                            |
|:-------------------|:---------------------|:--------------:|:--------------------------------|
| `id`               | UUID (PK)            |      Так       | Первинний ключ                  |
| `first_lesson_id`  | UUID (FK → `Lesson`) |      Так       | Зовнішній ключ на перше заняття |
| `second_lesson_id` | UUID (FK → `Lesson`) |      Так       | Зовнішній ключ на друге заняття |
| `room_id`          | UUID (FK → `Room`)   |      Так       | Зовнішній ключ на аудиторію     |
| `overlap_start`    | DateTime             |      Так       | Початок перетину                |
| `overlap_end`      | DateTime             |      Так       | Кінець перетину                 |
| `detected_at`      | DateTime             |      Так       | Дата й час виявлення            |
| `status`           | Enum                 |      Так       | Статус: `open` або `resolved`   |
| `resolved_at`      | DateTime             |       Ні       | Дата й час розв’язання          |

### 3.7 Notification

Представляє внутрішнє сповіщення користувача.

| Атрибут      | Тип / Ключ         | Обов’язковість | Опис                                                               |
|:-------------|:-------------------|:--------------:|:-------------------------------------------------------------------|
| `id`         | UUID (PK)          |      Так       | Первинний ключ                                                     |
| `user_id`    | UUID (FK → `User`) |      Так       | Отримувач сповіщення (персональні дані)                            |
| `type`       | String             |      Так       | Тип сповіщення (наприклад, `room_changed` або `schedule_conflict`) |
| `message`    | Text               |      Так       | Текст сповіщення                                                   |
| `created_at` | DateTime           |      Так       | Дата й час створення                                               |
| `is_read`    | Boolean            |      Так       | Ознака прочитання                                                  |

### 3.8 AuditLog

Представляє історію змін бронювань.

| Атрибут            | Тип / Ключ            | Обов’язковість | Опис                                                        |
|:-------------------|:----------------------|:--------------:|:------------------------------------------------------------|
| `id`               | UUID (PK)             |      Так       | Первинний ключ                                              |
| `booking_id`       | UUID (FK → `Booking`) |      Так       | Зовнішній ключ на бронювання                                |
| `user_id`          | UUID (FK → `User`)    |      Так       | Користувач, який виконав дію (персональні дані)             |
| `action`           | String                |      Так       | Тип дії (наприклад, `room_changed` або `booking_cancelled`) |
| `previous_room_id` | UUID (FK → `Room`)    |       Ні       | Попередня аудиторія                                         |
| `new_room_id`      | UUID (FK → `Room`)    |       Ні       | Нова аудиторія                                              |
| `reason`           | Text                  |       Ні       | Причина зміни                                               |
| `created_at`       | DateTime              |      Так       | Дата й час дії                                              |

На рівні Django ORM для `AuditLog` реалізовано append-only поведінку через `AppendOnlyManager` та перевизначені методи `save()` і `delete()`. Повний захист від змін безпосередньо в PostgreSQL ще не реалізовано. Зберігання записів щонайменше 12 місяців залишається вимогою, механізм забезпечення якої потребує реалізації.

### 3.9 SyncLog

Представляє журнал спроб синхронізації розкладу із САЗ.

| Атрибут         | Тип / Ключ | Обов’язковість | Опис                                                                             |
|:----------------|:-----------|:--------------:|:---------------------------------------------------------------------------------|
| `id`            | UUID (PK)  |      Так       | Первинний ключ                                                                   |
| `started_at`    | DateTime   |      Так       | Дата й час початку                                                               |
| `finished_at`   | DateTime   |       Ні       | Дата й час завершення                                                            |
| `status`        | Enum       |      Так       | Статус: `in_progress`, `success` або `failed`                                    |
| `trigger`       | Enum       |      Так       | Джерело запуску: `manual` або `scheduled` (зараз використовується лише `manual`) |
| `error_message` | Text       |       Ні       | Повідомлення про помилку                                                         |

Під час виконання синхронізація має статус `in_progress`. Після завершення статус змінюється на `success` або `failed`. Імпорт САЗ ([`services/saz_import.py`](../../Backend/api/services/saz_import.py), функція `run_sync`) створює запис `in_progress`, виконує розбір і запис даних однією транзакцією, після чого фіксує результат; у разі нерозпізнаної сторінки `error_message` містить причину, а сам запис журналу лишається.

Відповідно до [ADR-003](decisions/ADR-003.md), для запобігання паралельним синхронізаціям передбачено частковий унікальний індекс для записів зі статусом `in_progress`. У поточному [`Backend/api/models.py`](../../Backend/api/models.py) це обмеження в `SyncLog.Meta` не оголошено; воно залишається запланованим архітектурним рішенням.

У разі помилки синхронізації система продовжує працювати з останнім успішно імпортованим знімком даних.

## 4. Зв’язки між сутностями

- `User` може належати до однієї `AcademicGroup` або не мати групи;
- одна `AcademicGroup` може містити багато користувачів-студентів;
- одна `AcademicGroup` може мати багато `Lesson`;
- один викладач `User` може проводити багато `Lesson`;
- кожне `Lesson` належить одній `AcademicGroup` і пов’язане з одним викладачем;
- одне `Lesson` може мати пов’язані записи `Booking`;
- кожне `Booking` належить одному `Lesson` та одній `Room`;
- кожне `Booking` може бути пов'язане з одним `User` — автором бронювання; поле `user_id` необов'язкове;
- одна `Room` може мати багато бронювань у різний час;
- кожен `Conflict` посилається на два `Lesson` та одну `Room`;
- один `User` може отримувати багато `Notification`;
- одне `Booking` може мати багато `AuditLog`;
- один `User` може бути автором багатьох записів `AuditLog`;
- `previous_room_id` і `new_room_id` в `AuditLog` є необов’язковими.

## 5. Основні правила цілісності

- САЗ є джерелом істини для академічного розкладу; UniSpace лише зчитує дані й не записує зміни назад.
- Повторний імпорт незміненого розкладу не повинен створювати дублікати занять або початкових бронювань.
- Одна аудиторія не може мати декілька активних бронювань на часові проміжки, що перетинаються.
- Скасування бронювання переводить його в `cancelled`, але не видаляє заняття.
- Студенти не можуть створювати, змінювати чи скасовувати бронювання; викладач може переглядати, бронювати, змінювати аудиторію та скасовувати бронювання лише для власних занять; диспетчер має права на керування всіма бронюваннями, довідником аудиторій та імпортом розкладу із САЗ.
- Зміни аудиторій і скасування бронювань фіксуються в `AuditLog`.
- Для `AuditLog` реалізовано append-only обмеження на рівні Django ORM; захист на рівні PostgreSQL та гарантоване зберігання протягом 12 місяців ще потребують реалізації.
- У разі помилки синхронізації із САЗ останній успішний знімок розкладу залишається доступним.

## 7. Відкриті питання реалізації

- **Зіставлення викладачів із САЗ:** імпорт САЗ знаходить викладача за ПІБ (`full_name`, роль `teacher`), а якщо такого немає, створює його з тимчасовою адресою `saz-teacher-<хеш>@saz.invalid` і невикористовуваним паролем. Механізм зіставлення такого викладача з Microsoft-автентифікованим користувачем (вхід зв'язує обліковий запис за email) ще не визначено.
