# ADR 001: Вибір основного архітектурного стилю

**Дата:** 28 вересня 2026 р.  
**Статус:** Затверджено  
**Ініціатор:** Мельник Дар'я (Architecture Lead)

## Контекст
Команді необхідно розробити систему керування аудиторним фондом (UniSpace) протягом одного навчального семестру. Команда складається з 5 розробників із навантаженням 5–8 годин на тиждень. Обраний технологічний стек - Python (Django) та SQLite. 

Необхідно обрати архітектурний стиль, який забезпечить чітке розділення відповідальності між інтерфейсом та бізнес-логікою, дозволить реалізувати рольову модель доступу та логіку перевірки конфліктів, але при цьому не створить надмірного інфраструктурного навантаження (overengineering), характерного для мікросервісів.

## Рішення
Ми обрали гібридний підхід: **Клієнт-серверна архітектура з багатошаровим монолітним бекендом (Modular Monolith)**.

1. **Клієнт-сервер:** Розділяє UI (клієнтський вебзастосунок) та Backend (REST API). Це дозволяє незалежно тестувати бізнес-логіку.
2. **Багатошаровий бекенд:** Логіка сервера поділяється на ізольовані модулі: 
   - API Gateway / Auth (контролер входу та прав).
   - Business Logic Services (Task, Resource, Reporting).
   - Data Access Layer (ORM).

## Обґрунтування (Чому не мікросервіси чи інші стилі?)
- **Обмежені ресурси та час:** Налаштування оркестрації мікросервісів, міжсервісної комунікації та розподілених транзакцій вимагає часу, якого немає в межах семестру.
- **Цілісність даних:** Вимога NFR-2 (заборона накладок при конкурентному бронюванні) вимагає сильної узгодженості та транзакцій, що найлегше і надійніше реалізується в монолітній базі даних через єдиний шар Data Access Layer, а не через кінцеву узгодженість, властиву мікросервісам чи керованій подіями архітектурі.
- **Відповідність стеку:** Фреймворк Django за своєю природою найкраще працює як багатошаровий моноліт з єдиною ORM.

## Наслідки (Наслідки рішення)
**Позитивні:**
- Швидкий старт розробки та простота локального розгортання.
- Просте забезпечення транзакційності при перевірці вільних аудиторій.
- Легке написання E2E та інтеграційних тестів.

**Негативні (Ризики):**
- Усі компоненти масштабуються лише разом. Якщо навантаження на систему зросте (наприклад, під час масового перегляду розкладу), доведеться масштабувати весь застосунок, а не лише модуль зчитування. </br> *Мітигація: для поточних вимог продуктивності (PERF-001: 100 користувачів) моноліту буде цілком достатньо.*
