# ADR 001: Вибір основного архітектурного стилю

**Дата:** 28 вересня 2026 р.  
**Статус:** Затверджено (Частково доповнено рішенням [ADR-002](ADR-002.md) щодо переходу на PostgreSQL)
**Ініціатор:** Мельник Дар'я (Architecture Lead)

## Контекст
Команді необхідно розробити систему керування аудиторним фондом (UniSpace) протягом одного навчального семестру. Команда складається з 5 розробників із навантаженням 5–8 годин на тиждень. Технологічний стек — Python (Django), а основною базою даних визначено PostgreSQL (згідно з [ADR-002](ADR-002.md), що замінює початкове рішення про використання SQLite) 

Необхідно обрати архітектурний стиль, який забезпечить чітке розділення відповідальності між інтерфейсом та бізнес-логікою, дозволить реалізувати рольову модель доступу та логіку перевірки конфліктів, але при цьому не створить надмірного інфраструктурного навантаження (overengineering), характерного для мікросервісів.

## Рішення
Ми обрали гібридний підхід: **Клієнт-серверна архітектура з багатошаровим монолітним бекендом (Modular Monolith)**.

1. **Клієнт-сервер:** Розділяє UI (клієнтський вебзастосунок) та Backend (REST API). При цьому і фронтенд, і бекенд фізично розділені на два незалежні Django-проєкти (Frontend на базі Django Templates, Backend на базі Django REST).
2. **Багатошаровий бекенд:** Логіка сервера поділяється на ізольовані сервісні модулі, що відповідають актуальній UML-діаграмі компонентів:
   - **API Gateway & Router**
   - **Auth & User Service** (керування авторизацією через Microsoft SSO та перевірка прав)
   - **CA3 Parser Service** (імпорт розкладу із САЗ)
   - **Classroom Directory Service**
   - **Booking & Conflict Service** (основна бізнес-логіка бронювань та перевірка накладок)
   - **Notification Service**
   - **Audit Service**
   - **Data Access Layer** (через Django ORM)

## Обґрунтування (Чому не мікросервіси чи інші стилі?)
- **Обмежені ресурси та час:** Налаштування оркестрації мікросервісів, міжсервісної комунікації та розподілених транзакцій вимагає часу, якого немає в межах семестру.
- **Цілісність даних:** Вимога NFR-2 (заборона накладок при конкурентному бронюванні) вимагає сильної узгодженості та транзакцій, що найлегше і надійніше реалізується в монолітній базі даних (PostgreSQL) через єдиний шар Data Access Layer, а не через кінцеву узгодженість, властиву мікросервісам чи керованій подіями архітектурі.
- **Відповідність стеку:** Фреймворк Django за своєю природою найкраще працює як багатошаровий моноліт з єдиною ORM.

## Наслідки (Наслідки рішення)
**Позитивні:**
- Швидкий старт розробки та простота локального розгортання.
- Просте забезпечення транзакційності при перевірці вільних аудиторій на рівні БД.
- Легке написання E2E та інтеграційних тестів.

**Негативні (Ризики):**
- Усі компоненти масштабуються лише разом. Якщо навантаження на систему зросте, доведеться масштабувати весь застосунок.</br> *Мітигація: для поточних вимог продуктивності (PERF-001: 100 користувачів) моноліту буде цілком достатньо*.
