# ADR-002: Міграція бази даних з SQLite на PostgreSQL

**Дата:** 28 вересня 2026  
**Статус:** Прийнято  
**Ініціатор:** Михайлик Ольга

## Контекст (Context)
Під час початкового проєктування архітектури SpaceOps було обрано SQLite як тимчасове рішення для швидкого прототипування. Проте специфіка системи бронювання кабінетів передбачає велику кількість конкурентних запитів. Наприклад, на початку семестру або в моменти пікових навантажень кілька користувачів можуть одночасно намагатися забронювати вільні аудиторії. 

SQLite використовує блокування рівня всієї бази даних під час операцій запису. Це створює "вузьке місце", яке прямо загрожує виконанню наших вимог щодо надійності при паралельних запитах (REL-001) та швидкодії (PERF-001).

## Рішення (Decision)
Ми змінюємо основну систему керування базами даних з SQLite на PostgreSQL. 

Оскільки взаємодія з даними інкапсульована в компоненті `Data Access Layer` через Entity Framework, перехід здійснюється шляхом заміни EF-провайдера на `Npgsql.EntityFrameworkCore.PostgreSQL` та оновлення рядків підключення. Бізнес-логіка (Task, Resource та Reporting сервіси) залишається повністю незмінною.

## Обґрунтування (Justification)
* **Підтримка високої конкурентності:** Наша система вимагає одночасного читання (перегляд розкладу сотнями студентів) та запису (бронювання/перенесення пар викладачами). PostgreSQL нативно підтримує такі навантаження без блокування всієї бази.
* **Готовність до Production:** SQLite є файловою базою даних, яка чудово підходить для локальної розробки, але не розрахована на використання у вебсерверах з множинними потоками. PostgreSQL є надійним індустріальним стандартом для клієнт-серверних застосунків.
* **Легкість міграції:** Завдяки використанню Entity Framework як ORM (Object-Relational Mapper), заміна бази даних вимагає мінімального втручання в код — лише встановлення нового пакета та зміни конфігурації підключення, що не порушує поточний графік розробки.
* **Розширені типи даних:** PostgreSQL надає потужну підтримку для складних типів даних (наприклад, JSONB для зберігання деталей в аудит-лозі), що ідеально відповідає нашим потребам з ведення незмінної історії бронювань (US-04).

## Наслідки (Consequences)

### Позитивні
* **Продуктивність та надійність:** PostgreSQL використовує механізм MVCC (Multiversion Concurrency Control), що дозволяє транзакціям на читання не блокувати запис, і навпаки. Це гарантує стабільну роботу системи навіть при масових одночасних змінах розкладу.
* **Гнучкість даних:** Розширені можливості роботи з JSONB-полями дозволять більш гнучко структурувати записи в нашому аудит-лозі.

### Негативні (Компроміси)
* **Складність розробки:** Зростає поріг входу для команди. Замість роботи з локальним файлом, кожному розробнику доведеться піднімати локальний екземпляр PostgreSQL на своєму комп'ютері (рекомендується використання Docker Compose).
* **Інфраструктура (CI):** Ускладнюється налаштування автоматизованого тестування. У GitHub Actions необхідно буде налаштувати сервісний контейнер з PostgreSQL (через блок `services` у файлі `ci.yml`), щоб інтеграційні тести мали доступ до реальної бази під час перевірок Pull Request-ів.

### Примітка
Структуровано за допомогою ШІ. Верифіковано шляхом перевірки та аналізу всіма учасниками команди.
