# ADR-002: Міграція бази даних з SQLite на PostgreSQL

**Дата:** 28 вересня 2026 (оновлено 31 жовтня 2026)  
**Статус:** Прийнято  
**Ініціатор:** Михайлик Ольга  
**Зв'язок з іншими рішеннями:** частково замінює [ADR-001](ADR-001.md) — у частині початкового вибору SQLite як основної БД. Архітектурний стиль (клієнт-сервер з модульним монолітом) з ADR-001 залишається чинним.

## Контекст (Context)
Під час початкового проєктування UniSpace було обрано SQLite як тимчасове рішення для швидкого прототипування (початкові редакції ADR-001 та обмеження C-002). Проте специфіка системи бронювання аудиторій передбачає велику кількість конкурентних запитів: на початку семестру або в моменти пікових навантажень кілька викладачів можуть одночасно намагатися перебронювати ту саму аудиторію, а сотні студентів — одночасно переглядати розклад.

SQLite під час запису блокує весь файл бази даних і не підтримує блокування на рівні рядків: у Django `select_for_update()` на SQLite не має ефекту. Це створює «вузьке місце», яке прямо загрожує виконанню вимог щодо надійності при паралельних запитах (REL-001) та швидкодії (PERF-001).

## Рішення (Decision)
Ми змінюємо основну систему керування базами даних з SQLite на PostgreSQL.

Уся взаємодія з даними інкапсульована в компоненті `Data Access Layer (Django ORM)`, тому перехід здійснюється засобами Django:
- у `Backend/Backend/settings.py` параметр `DATABASES['default']['ENGINE']` змінюється з `django.db.backends.sqlite3` на `django.db.backends.postgresql`;
- до залежностей бекенду (`Backend/requirements.txt`) додається драйвер `psycopg` (psycopg 3);
- параметри підключення (`NAME`, `USER`, `PASSWORD`, `HOST`, `PORT`) зчитуються зі змінних середовища (`.env`), а не зберігаються в коді (R-002);
- схема бази даних створюється стандартними міграціями Django (`python manage.py migrate`).

Бізнес-логіка (`Booking & Conflict Service`, `Classroom Directory Service`, `CA3 Parser Service`, `Audit Service` та інші сервіси) працює через Django ORM і не потребує змін.

## Обґрунтування (Justification)
* **Підтримка конкурентності:** Запобігання часовим накладкам забезпечується PostgreSQL `ExclusionConstraint` (`booking_active_room_time_excl`) у моделі `Booking`, а не блокуванням `SELECT ... FOR UPDATE`. Створення та зміна бронювань виконуються в `transaction.atomic()`, а конфлікти обмежень БД перетворюються на `409 Conflict` (REL-001).
* **Швидкодія читання:** механізм MVCC (Multiversion Concurrency Control) дозволяє транзакціям на читання не блокувати запис і навпаки. Перегляд розкладу студентами не сповільнюється під час перебронювань (PERF-001).
* **Готовність до production:** SQLite — файлова база даних, яка добре підходить для локальної розробки, але не розрахована на вебсервер із багатьма паралельними процесами (Gunicorn). PostgreSQL є індустріальним стандартом для клієнт-серверних застосунків і офіційно підтримується Django.
* **Легкість міграції:** завдяки Django ORM заміна СКБД зводиться до зміни налаштування `DATABASES` і встановлення драйвера `psycopg`. Моделі та запити залишаються незмінними, тож графік розробки не порушується.

## Розглянуті альтернативи
* **Залишити SQLite:** найпростіше для розробки, але не забезпечує REL-001 і створює ризик помилок `database is locked` під навантаженням.
* **MySQL / MariaDB:** також підтримується Django і має рядкові блокування, але команда має більше досвіду з PostgreSQL, а модель даних і модель загроз уже орієнтовані на PostgreSQL.

## Наслідки (Consequences)

### Позитивні
* **Надійність:** накладки бронювань запобігаються на рівні транзакцій БД навіть при паралельних запитах.
* **Продуктивність:** читання розкладу не блокується операціями запису.
* **Узгодженість документації:** [ADR-001](ADR-001.md), [високорівневий дизайн](../high-level-design.md), [діаграма компонентів](../uml/component_diagram.puml), [діаграма розгортання](../uml/deployment_diagram.puml), [модель даних](../data-model.md), [модель загроз](../threat-model.md) та обмеження C-002 у [requirements.md](../../requirements/requirements.md) описують PostgreSQL як основне сховище.

### Негативні (Компроміси)
* **Складність розробки:** зростає поріг входу для команди. Замість роботи з локальним файлом `db.sqlite3` кожному розробнику доведеться піднімати локальний екземпляр PostgreSQL (рекомендується Docker Compose).
* **Інфраструктура (CI):** ускладнюється налаштування автоматизованого тестування. У GitHub Actions потрібно додати сервісний контейнер PostgreSQL (блок `services` у файлі `ci.yml`), щоб інтеграційні тести, зокрема тест на 10 паралельних бронювань (REL-001), працювали з реальною БД під час перевірки Pull Request-ів.

### Стан реалізації
Рішення впроваджено (стан на 31 жовтня 2026):
 
* **Налаштування:** `DATABASES` у `Backend/Backend/settings.py` обирається за змінною середовища `DATABASE_URL`. Якщо її задано, використовується `django.db.backends.postgresql` (формат `postgresql://<user>:<password>@<host>:<port>/<db_name>`, інші схеми відхиляються з `ImproperlyConfigured`). SQLite лишається лише запасним варіантом, коли `DATABASE_URL` не задано (швидкий старт без Docker).
* **Драйвер:** `psycopg[binary]` (psycopg 3) додано до `Backend/requirements.txt`. Параметри підключення беруться зі змінних середовища, у коді їх немає (R-002).
* **Локальна розробка:** PostgreSQL 16 піднімається через `Backend/docker-compose.yml` (`docker compose up -d`), шаблон змінних — `Backend/.env.example`.
* **Розгортання:** на Render бекенд підключено до PostgreSQL через `DATABASE_URL` (Internal Database URL).
* **CI:** у `.github/workflows/ci.yml` додано сервісний контейнер `postgres:16`, у ньому виконуються перевірка й застосування міграцій та тести. Це потрібно, бо `ExclusionConstraint` для `Booking` існує лише в PostgreSQL.
* **Верифікація конкурентності (REL-001):** Інтеграційний тест із 10 паралельними запитами підтверджує, що PostgreSQL `ExclusionConstraint` разом з атомарними транзакціями та обробкою помилок у `services/bookings.py` забезпечує рівно одне успішне бронювання (`201 Created`), тоді як решта 9 запитів отримують `409 Conflict`.

### Примітка
Структуровано за допомогою ШІ. Верифіковано шляхом перевірки та аналізу всіма учасниками команди.
