# ADR-003: Спрощений circuit breaker на основі SyncLog для обмеження ручного імпорту розкладу

Статус: Запропоновано (чекає на рев'ю)
Дата: 06.10.2026
Ініціатор: Трекурова Анастасія (Керівник документації)

## Контекст
Система UniSpace інтегрується з Системою Автоматизації Закладу (САЗ) шляхом виконання HTTP GET запиту та подальшого парсингу HTML-сторінки, оскільки публічного API САЗ не надає (припущення A-001). Імпорт ініціюється автоматично планувальником або вручну диспетчером через POST-запит до API Gateway. За поточним архітектурним дизайном ручний імпорт виконується синхронно всередині HTTP-запиту клієнта.

На надійність імпорту впливають вимоги REL-002, FR-004, FR-005, TM-06 та TM-07. Згідно з data-model.md (таблиця SyncLog) та FR-005, історія синхронізацій фіксується в системному лозі, а цілісність даних забезпечується атомарним імпортом (TM-06). Студенти завжди читають розклад з локальної БД PostgreSQL (ADR-002), тому збій САЗ не впливає на їхній сценарій перегляду.

Головними причинами відмов процесу імпорту є:
1. Мережева недоступність САЗ (перевищення таймауту 30 с).
2. Зміна HTML-розмітки САЗ, через яку падає парсинг (R-001, TM-06).

Проблема виникає під час тривалих збоїв або зміни розмітки: диспетчер може багаторазово натискати кнопку імпорту вручну (загроза TM-10). Через синхронну обробку це призводить до блокування worker-процесів веб-сервера Gunicorn (відображеного на deployment-діаграмі) тривалими таймаутами по 30 с або виконанням приреченого на збій парсингу. Крім того, існує ризик неконтрольованого паралельного запуску кількох синхронізацій одночасно.

## Рішення
Впровадити спрощену реалізацію патерну Circuit Breaker, яка спирається на розширену таблицю SyncLog у PostgreSQL, для обмеження надлишкових ручних запусків та запобігання паралельним процесам імпорту:

1. Атомарне блокування паралельних запусків: Перед стартом імпорту (ручного чи за розкладом) бекенд створює запис у SyncLog зі статусом in_progress. Захист від стану гонитви (race condition) між двома одночасними запитами гарантується на рівні PostgreSQL через частковий унікальний індекс. У Django він задається в міграції як UniqueConstraint(fields=['status'], condition=Q(status='in_progress'), name='idx_sync_in_progress'), що еквівалентно SQL (назва таблиці залежить від Django-застосунку, наприклад, api_synclog):
   CREATE UNIQUE INDEX idx_sync_in_progress ON api_synclog (status) WHERE status = 'in_progress';
   Спроба створення другого одночасного запису відхиляється базою даних на рівні обмеження унікальності.
2. Захист від блокування при аварії (stale lock threshold): Якщо запис зі статусом in_progress має вік понад 60 с, він вважається застарілим, автоматично переводиться у статус failed, і блокування знімається. Щоб живий процес не міг пережити цей поріг, таймаут worker-процесів Gunicorn (параметр --timeout) встановлюється на 45 с (за замовчуванням 30 с, що збігалося б із таймаутом запиту до САЗ, і Gunicorn завершував би worker раніше, ніж той встигне записати failed). Таким чином, таймаут запиту до САЗ (30 с) < таймаут Gunicorn (45 с) < поріг застарілості (60 с). Додатково, перед фіксацією транзакції імпорту виконується перевірка (SELECT ... FOR UPDATE), що відповідний запис SyncLog досі має статус in_progress; якщо він уже переведений у failed як застарілий, імпорт відкочується, а його результат відкидається. Це запобігає перетину двох імпортів.
3. Ліміт помилок і пауза: Перед виконанням ручного імпорту бекенд перевіряє останні записи в SyncLog. Враховуються ручні збої (trigger = 'manual', status = 'failed'), що відбулися після останнього успішного імпорту будь-якого типу. Якщо їх 3 або більше, система активує тимчасове блокування нових ручних запусків на 15 хвилин, які відраховуються від finished_at останнього збою. Заблоковані спроби не створюють нових записів у SyncLog, щоб не пролонгувати паузу нескінченно. Константи (3 спроби, 15 хвилин) виносяться в конфігурацію Django (settings.py).
4. Скидання стану та режим half-open: Успішне завершення імпорту будь-якого типу (як ручного, так і фонового за розкладом) свідчить про відновлення роботи САЗ і негайно скидає лічильник збоїв до нуля. Після спливу 15 хвилин система переходить у стан *half-open*, пропускаючи одну пробну ручну спробу. При успіху лічильник обнуляється, при повторній помилці — блокування поновлюється на 15 хвилин.
5. Відповідь API на блокування: У разі відхилення запиту через тимчасове блокування після серії збоїв API повертає HTTP статус 429 Too Many Requests із заголовком Retry-After: <кількість_секунд> та стандартним JSON-тілом помилки. Якщо запит відхилено через уже виконуваний паралельний імпорт, API повертає HTTP статус 409 Conflict (за аналогією з накладками бронювань) також зі стандартним JSON-тілом помилки.
6. Ізоляція транзакцій: Створення запису in_progress та фіксація підсумкового статусу (success/failed) виносяться в окремі транзакції поза атомарною транзакцією збереження розкладу (TM-06). Запис in_progress створюється в режимі autocommit, поза будь-яким блоком transaction.atomic() та без використання ATOMIC_REQUESTS. Це гарантує, що in_progress негайно видно іншим worker-процесам Gunicorn, а статус failed не відкочується при rollback помилки імпорту.
7. Відображення в документації моделі даних: Ці зміни мають бути відображені в docs/architecture/data-model.md та docs/architecture/uml/data_model.puml шляхом додавання поля trigger (manual / scheduled) та розширення переліку статусів status (in_progress, success, failed), а також часткового унікального обмеження на статус in_progress.

8. ## Обґрунтування
Рішення спирається на наявний стек Django + PostgreSQL (ADR-002) і середовище виконання Gunicorn (deployment-діаграма), захищаючи worker-процеси від блокування (TM-10) без внесення нових інфраструктурних залежностей (Redis/Celery). Використання часткового унікального індексу в PostgreSQL гарантує строгу атомарність без гонитви, а врахування помилок парсингу разом із таймаутами повністю закриває специфіку роботи з непублічним HTML САЗ (R-001, TM-06).

## Наслідки

Плюси:
* Захист worker-процесів Gunicorn від вичерпання через повторювані ручні кліки диспетчера під час недоступності САЗ.
* Атомарне запобігання паралельним процесам імпорту на рівні СУБД.
* Відсутність «вічного замка» завдяки 60-секундному порогу скидання завислого статусу in_progress.
* Стандартизована поведінка REST API: HTTP 429 із заголовком Retry-After (пауза після збоїв) та HTTP 409 (паралельний імпорт).
* Відсутність нових інфраструктурних компонентів у requirements.txt чи на deployment-діаграмі.

Застереження:
* Свідомий компроміс і коригування FR-005: Тимчасове блокування обмежує можливість диспетчера запустити імпорт у будь-яку мить. Якщо САЗ відновиться за 5 хвилин, диспетчер чекатиме завершення 15-хвилинного вікна (або автоматичного планового запуску). У зв'язку з цим пропонується уточнити критерій FR-005 у requirements.md та матриці простежуваності: «…крім періоду тимчасового блокування після серії збоїв, коли система повертає час до зняття блокування».
* Синхронізація з моделлю даних: Вимагає оновлення документації моделі даних (data-model.md, data_model.puml) у частині полів та індексів таблиці SyncLog.
* Конфігурація Gunicorn: Вимагає явного налаштування --timeout 45 (див. пункт 2 розділу «Рішення»); за замовчуванням Gunicorn використовує 30 с.

Мінуси:
* Додатковий SELECT-запит до SyncLog перед кожною спробою імпорту для валідації стану запобіжника.
* Потенційна затримка отримання свіжого розкладу ручним шляхом, якщо САЗ відновилася швидше за інтервал half-open.

## Розглянуті альтернативи

* Повноцінний Circuit Breaker (бібліотека pybreaker + Redis):
  * *Причина відхилення:* Redis відсутній у requirements.txt та на діаграмі розгортання. Додавання нової служби заради одного сценарію є надлишковим ускладненням архітектури.
* Відсутність запобіжника (лише таймаут 30 с):
  * *Причина відхилення:* Не захищає від спаму ручними запитами диспетчера (загроза TM-10), що здатне повністю паралізувати пул воркерів Gunicorn.
* Блокування паралельних викликів у пам'яті процесу Python (наприклад, `threading.Lock`):
  * *Причина відхилення:* Gunicorn працює через кілька ізольованих OS-процесів (workers), які не мають спільної оперативної пам'яті без зовнішнього брокера. Надійне блокування можливе лише через спільну БД PostgreSQL.
