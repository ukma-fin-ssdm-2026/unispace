# Високорівневий дизайн системи (High-Level Design)
## 1. Архітектурний стиль
Проєкт UniSpace використовує гібридний архітектурний стиль: **Клієнт-серверна архітектура у поєднанні з багатошаровою моделлю бекенду (Modular Monolith)**. 

- **Клієнт-сервер:** Забезпечує чіткий поділ між користувацьким інтерфейсом (Frontend) та бізнес-логікою (Backend), які спілкуються через REST API. Це дозволяє незалежно розробляти UI та серверну частину.
- **Багатошарова архітектура:** Серверна частина фізично розділена на два незалежні Django-проєкти (Frontend та Backend), а сам бекенд логічно розділений на ізольовані сервісні модулі. Це знижує складність розробки для команди з 5 осіб у межах одного семестру, зберігаючи чистоту коду.

## 2. Огляд компонентів
Згідно з нашою діаграмою компонентів (див. [component_diagram.puml](uml/component_diagram.puml)), архітектура поділяється на такі блоки:

### Frontend (Client)
- Client Application (Web UI): Вебзастосунок на базі Django Templates (серверна генерація HTML, CSS та JavaScript), з яким взаємодіє кінцевий користувач. Відповідає за відображення розкладу, пошук аудиторій та інтерфейс бронювань.

### Backend (Business Logic - Django)
- **API Gateway & Router:** Точка входу для запитів, що виконує маршрутизацію.
- **Auth & User Service:** Відповідає за валідацію користувачів через Microsoft SSO, керування сесіями та перевірку ролей (RBAC).
- **CA3 Parser Service:** Ізольований модуль, що відповідає за ідемпотентний імпорт розкладу із САЗ.
- **Classroom Directory Service:** Керує довідником аудиторій, їхніми характеристиками (місткість, обладнання) та загальною доступністю.
- **Booking & Conflict Service:** Керує логікою бронювань, автопідбором вільних аудиторій, перевіркою накладок та розв'язанням конфліктів.
- **Notification Service:** Відповідає за відправку email та внутрішніх сповіщень студентам і викладачам.
- **Audit Service:** Забезпечує незмінне логування всіх дій з бронюваннями (Append-only).

### Data Layer
- **Django ORM:** Надає уніфікований інтерфейс для роботи з базою даних, абстрагуючи бізнес-сервіси від прямих SQL-запитів.
- **PostgreSQL Database:** Основне реляційне сховище даних системи (користувачі, розклад, аудиторії, аудит-лог).

### External Services
- **Microsoft Identity Platform:** Провайдер єдиного входу (SSO) для автентифікації.
- **Email Service (SMTP):** Сервіс для відправки сповіщень.
- **CA3 System (САЗ):** Зовнішня система автоматизації закладу, з якої зчитується базовий розклад.

## 3. Внутрішні та зовнішні інтерфейси
Взаємодія між компонентами та зовнішніми системами відбувається через такі інтерфейси:
- **Client Web UI ↔ Backend API:** Внутрішній HTTP / REST (обмін даними у форматі JSON).
- **Auth & User Service ↔ Microsoft Identity Platform:** HTTPS / OAuth 2.0 (OpenID Connect) для обміну авторизаційними токенами.
- **CA3 Parser Service ↔ CA3 System:** HTTPS (GET-запити) з подальшим парсингом HTML-розмітки.
- **Notification Service ↔ SMTP Server:** Протокол SMTP (із шифруванням TLS) для передачі сформованих email-повідомлень.
- **Django ORM ↔ PostgreSQL Database:** TCP/IP (протокол PostgreSQL/psycopg) для виконання транзакційних SQL-запитів.

## 4. Огляд розгортання (Deployment)
Система розгортається на трьох базових вузлах (див. [deployment_diagram.puml](uml/deployment_diagram.puml)):
1. **Client Device:** Веббраузер кінцевого користувача, який відображає згенеровані HTML-сторінки.
2. **Application Server:** Хостить два незалежні Django-застосунки (відповідно до обмеження C-004): `Frontend` (клієнтський UI на базі Django Templates, працює на порту **8001**) та `Backend` (серверна частина з REST API, працює на порту **8000**).
3. **Database Server:** Хостить PostgreSQL схему `unispace_db`.
