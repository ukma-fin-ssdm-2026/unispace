# Модель загроз UniSpace

## 1. Мета та підхід

Цей документ містить STRIDE-аналіз загроз для UniSpace.

Аналіз виконано на основі актуальної deployment-діаграми `docs/architecture/uml/deployment_diagram.puml`.

Для кожної межі довіри та критичного компонента розглянуто категорії STRIDE:

- **S — Spoofing** — підміна особи;
- **T — Tampering** — несанкціонована зміна даних;
- **R — Repudiation** — можливість заперечити виконану дію;
- **I — Information Disclosure** — розкриття інформації;
- **D — Denial of Service** — відмова в обслуговуванні;
- **E — Elevation of Privilege** — підвищення привілеїв.

Позначені в ER-моделі персональні та чутливі дані використані як одна з відправних точок аналізу.

## 2. Компоненти та межі довіри

Актуальна deployment-діаграма містить:

- **Client Device / Web Browser / Client Application**;
- **Application Server / Django Web Server (Gunicorn) / Backend API**;
- **Database Server / PostgreSQL / `unispace_db`**;
- зовнішню **CA3 System (САЗ)**;
- зовнішню **Microsoft Identity Platform**;
- зовнішній **SMTP Server**.

Основні межі довіри:

1. **Web Browser ↔ Backend API** — запити користувача надходять із клієнтського середовища до серверної частини через HTTPS/REST.
2. **Backend API ↔ Microsoft Identity Platform** — автентифікація виконується через зовнішній Microsoft Identity Platform по OAuth2/OIDC.
3. **Backend API ↔ PostgreSQL** — сервер застосунку читає та змінює дані через Django ORM.
4. **Backend API ↔ САЗ** — зовнішні HTML-дані розкладу зчитуються через HTTPS у режимі read-only.
5. **Backend API ↔ SMTP Server** — зовнішній поштовий сервіс використовується для надсилання email-сповіщень.

Кожен перехід між цими зонами розглядається як межа, на якій дані або ідентичність можуть бути підмінені, змінені, розкриті чи зроблені недоступними.

## 3. STRIDE-аналіз

| ID | Компонент / межа довіри | STRIDE | Сценарій загрози | Рівень | Мітигація |
|---|---|---|---|---|---|
| TM-01 | Web Browser ↔ Backend API / Microsoft Identity Platform | **Spoofing** | Зловмисник отримує викрадений або підроблений токен/сесію користувача та намагається виконувати дії від його імені. | High | Використовувати Microsoft OAuth2/OIDC; перевіряти підпис, issuer, audience та строк дії токенів; використовувати HTTPS; захищені session cookies; не зберігати Microsoft-паролі в UniSpace. |
| TM-02 | Backend API / Auth & User Service | **Elevation of Privilege** | Студент або інший користувач намагається обійти RBAC і викликати endpoint зміни/скасування бронювання або функції диспетчера. | High | Перевіряти роль і ownership на сервері для кожної state-changing операції; не покладатися на приховані елементи UI; для студентів такі endpoints повинні повертати HTTP 403 відповідно до SEC-001. |
| TM-03 | Web Browser ↔ Backend API / Booking & Conflict Service | **Tampering** | Користувач змінює параметри запиту, наприклад `lesson_id` або `room_id`, щоб змінити чуже заняття чи призначити недоступну аудиторію. | High | Серверна валідація всіх ідентифікаторів і прав на заняття; перевірка доступності кімнати; транзакційне збереження; заборона довіряти даним із клієнта без перевірки. |
| TM-04 | Backend API ↔ PostgreSQL / AuditLog | **Tampering / Repudiation** | Користувач або помилкова функціональність намагається змінити чи видалити запис аудит-логу, після чого неможливо достовірно встановити, хто змінив або скасував бронювання. | High | Append-only audit log; заборона update/delete через прикладний рівень; мінімальні права DB-користувача; фіксація actor, timestamp, action, previous/new room; зберігання щонайменше 12 місяців відповідно до SEC-003. |
| TM-05 | PostgreSQL / `unispace_db` | **Information Disclosure** | Несанкціонований доступ до БД розкриває університетські email, ПІБ, Microsoft identity identifier, сповіщення та історію дій користувачів. | High | Least-privilege доступ до БД; секрети підключення поза кодом; обмеження мережевого доступу до PostgreSQL; захист резервних копій; доступ до персональних даних лише через авторизовану серверну логіку. |
| TM-06 | Backend API ↔ САЗ | **Tampering** | Структура HTML САЗ змінюється або сервер повертає неочікувані/пошкоджені дані, через що parser може імпортувати некоректний розклад або бронювання. | Medium | Ізольований parser/adapter; валідація отриманих даних до збереження; атомарний імпорт; логування помилки; не замінювати останній коректний snapshot при невдалому імпорті. |
| TM-07 | Backend API ↔ САЗ | **Denial of Service** | САЗ недоступний або відповідає занадто довго, тому синхронізація не може завершитися. | Medium | Timeout для зовнішніх запитів; контроль помилок; логування невдалої синхронізації; продовження роботи на останньому успішному snapshot відповідно до REL-002. |
| TM-08 | Backend API ↔ SMTP Server | **Information Disclosure** | Дані зі сповіщень можуть бути розкриті під час передавання або через помилково вказаного одержувача. | Medium | Використовувати захищене SMTP-з’єднання, не включати зайві персональні дані в листи, перевіряти адресу одержувача на сервері та зберігати SMTP credentials у секретах середовища. |
| TM-09 | Booking & Conflict Service ↔ PostgreSQL | **Tampering / Denial of Service** | Дві паралельні операції намагаються одночасно забронювати одну аудиторію на той самий часовий слот, що може створити накладку або помилки блокування. | High | Транзакції PostgreSQL, серверна перевірка overlap та механізм синхронізації/обмеження на рівні даних; тест із 10 паралельними запитами відповідно до REL-001. |
| TM-10 | Backend API / sync endpoint | **Elevation of Privilege / Denial of Service** | Неавторизований користувач багаторазово запускає ручну синхронізацію із САЗ, створюючи навантаження на UniSpace та зовнішню систему. | Medium | Дозволяти запуск синхронізації лише диспетчеру; перевіряти RBAC на сервері; не допускати неконтрольованих паралельних sync jobs; логувати запуск і результат синхронізації. |

## 4. Перевірка STRIDE за межами довіри

### Browser ↔ Backend API

Розглянуті:

- **Spoofing** — викрадення сесії або токена;
- **Tampering** — модифікація параметрів booking-запиту;
- **Repudiation** — заперечення зміни бронювання, що покривається аудит-логом;
- **Information Disclosure** — доступ до даних іншого користувача;
- **Denial of Service** — надмірна кількість запитів;
- **Elevation of Privilege** — обхід ролей student/teacher/dispatcher.

### Backend API ↔ Microsoft Identity Platform

Розглянуті:

- **Spoofing** — використання недійсного або викраденого токена;
- **Tampering** — підміна токена;
- **Information Disclosure** — витік токена або identity data;
- **Denial of Service** — тимчасова недоступність зовнішнього identity provider.

Основна мітигація — стандартний OAuth2/OIDC flow, HTTPS і серверна валідація токенів.

### Backend API ↔ PostgreSQL

Розглянуті:

- **Tampering** — несанкціонована зміна бронювань або аудит-логу;
- **Repudiation** — видалення доказів виконаної дії;
- **Information Disclosure** — витік персональних та чутливих даних;
- **Denial of Service** — проблеми конкурентного доступу;
- **Elevation of Privilege** — надмірні права DB-користувача.

### Backend API ↔ САЗ

Розглянуті:

- **Tampering** — неочікувані або змінені HTML-дані;
- **Information Disclosure** — передавання даних зовнішній системі не потрібне, оскільки інтеграція read-only;
- **Denial of Service** — недоступність САЗ або зміна HTML, яка ламає parser.

UniSpace не виконує write-back у САЗ.

### Backend API ↔ SMTP Server

Розглянуті:

- **Spoofing** — неправильна конфігурація або підміна поштового сервісу;
- **Information Disclosure** — витік вмісту повідомлень;
- **Denial of Service** — недоступність SMTP і затримка email-сповіщень.

## 5. Зв’язок із вимогами

- `SEC-001` зменшує ризик **Elevation of Privilege** для state-changing booking endpoints.
- `SEC-002` визначає використання Microsoft Account і відсутність локального зберігання паролів, що враховано для **Spoofing**.
- `SEC-003` є основною мітигацією для **Tampering/Repudiation** аудит-логу.
- `REL-001` зменшує ризик неконсистентних бронювань при конкурентних запитах.
- `REL-002` зменшує вплив **Denial of Service** або зміни HTML САЗ.
- `PERF-002` задає вимогу до своєчасності email-сповіщень і має враховуватися при відмовах SMTP.

## 6. Залишкові ризики та припущення

- Microsoft Identity Platform, САЗ та SMTP є зовнішніми системами, тому UniSpace не може повністю усунути ризик їх недоступності.
- Формат HTML САЗ може змінитися без попередження; цей ризик зменшується ізоляцією parser-а, валідацією та використанням останнього успішного snapshot.
- Вимога `SEC-003` формулює захист аудит-логу навіть від адміністратора. На рівні застосунку update/delete повинні бути заборонені; права інфраструктурного або PostgreSQL superuser потребують окремого організаційного та інфраструктурного контролю.
- Deployment-діаграма позначає SMTP-з’єднання як `SMTP Protocol`, але не уточнює, чи використовується TLS. Для захисту повідомлень це потрібно уточнити під час реалізації.
