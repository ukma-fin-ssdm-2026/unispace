# Архітектурна матриця простежуваності (Architecture Traceability Matrix)

Цей документ відображає зв'язок між бізнес-вимогами (FR/US), нефункціональними вимогами (NFR) та архітектурними компонентами системи SpaceOps. Він гарантує, що кожна вимога має відповідний модуль для реалізації, а кожен компонент виконує конкретну бізнес-ціль.

## 1. Матриця відображення «Вимога ↔ Компонент»

## 2. Сценарії атрибутів якості (Quality Attribute Scenarios)

### Сценарій 1: Безпека (Security) - Захист від несанкціонованих дій
- **Джерело (Source):** Авторизований користувач із роллю "Студент".
- **Стимул (Stimulus):** Спроба надіслати HTTP-запит на зміну або скасування існуючого бронювання (дія, дозволена лише викладачам та диспетчерам).
- **Артефакт (Artifact):** `API Gateway / Auth Service`, `REST API (HTTPS)`.
- **Середовище (Environment):** Звичайна робота системи.
- **Реакція (Response):** `API Gateway` ідентифікує токен користувача, перевіряє роль, блокує передачу запиту до `Task Management Service` та логує спробу порушення доступу.
- **Міра реакції (Measure):** Запит відхиляється із статус-кодом `403 Forbidden` за час < 100 мс; дія успішно фіксується в системному лозі.

### Сценарій 2: Надійність (Reliability) - Відмовостійкість зовнішніх систем
- **Джерело (Source):** Внутрішній планувальник системи SpaceOps.
- **Стимул (Stimulus):** Спроба ініціювати плановий імпорт розкладу, коли зовнішня система САЗ недоступна.
- **Артефакт (Artifact):** `Task Management Service`, `Calendar / CA3`.
- **Середовище (Environment):** Збій мережі або падіння зовнішнього API САЗ.
- **Реакція (Response):** Сервіс фіксує таймаут з'єднання, перериває процес імпорту без пошкодження поточних даних у `SQLite Database`, надсилає попередження диспетчеру та продовжує обслуговувати клієнтів, використовуючи останній успішний знімок розкладу.
- **Міра реакції (Measure):** 0% втрати або пошкодження існуючих даних; час відгуку системи для кінцевих користувачів не деградує.

### Сценарій 3: Продуктивність (Performance) - Пікове навантаження на розклад
- **Джерело (Source):** Студенти (велика кількість одночасних користувачів).
- **Стимул (Stimulus):** 150 студентів одночасно відкривають сторінку свого розкладу на початку першої пари в понеділок.
- **Артефакт (Artifact):** `Client Application`, `Task Management Service`, `Data Access Layer`.
- **Середовище (Environment):** Режим пікового навантаження.
- **Реакція (Response):** Запити паралельно обробляються через `REST API`; `Data Access Layer` виконує оптимізовані read-only запити до `SQLite Database` без блокування таблиць.
- **Міра реакції (Measure):** 95% запитів на отримання розкладу обробляються та повертаються клієнту за час ≤ 500 мс без помилок (HTTP 500/503).

### Примітка
Структуровано за допомогою ШІ. Верифіковано шляхом перевірки та аналізу Михайлик Ольгою (керівником простежуваності).
