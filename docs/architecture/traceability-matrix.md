# Архітектурна матриця простежуваності (Architecture Traceability Matrix)

Цей документ відображає зв'язок між функціональними вимогами (FR), нефункціональними вимогами (NFR) та логічними компонентами модульного моноліту UniSpace. Він гарантує, що кожна вимога має відповідний модуль для реалізації, а кожен компонент виконує конкретну бізнес-ціль. Назви компонентів відповідають [діаграмі компонентів](uml/component_diagram.puml), сутності — [моделі даних](data-model.md), ідентифікатори тестів — [RTM](../requirements/rtm.md).

## 1. Матриця відображення «Вимога ↔ Компонент»

| :--- | :--- | :--- | :--- | :--- |
| **FR-001 / SEC-002** | Автентифікація через Microsoft Account без збереження паролів | `Auth & User Service`, `API Gateway & Router`, `Client Application` | Інтеграція з Microsoft SSO (OAuth2 / OpenID Connect). `Auth & User Service` валідує токени; у `User` зберігаються лише `external_identity_id`, `email`, `full_name`, `role` — паролі не зберігаються. | Тестування флоу авторизації через Microsoft (ST-002). |
| **FR-002 / SEC-001** | Розмежування доступу за ролями; заборона зміни бронювань студентам | `API Gateway & Router`, `Auth & User Service` | Перед маршрутизацією запиту `API Gateway & Router` перевіряє в `Auth & User Service` роль (`student` / `teacher` / `dispatcher`) та належність заняття. Для студента операції зміни бронювань повертають `403 Forbidden`. | Security-тести на обхід авторизації (ST-001). |

| **FR-004** | Періодичний імпорт розкладу із САЗ | `CA3 Parser Service`, `Booking & Conflict Service` | `CA3 Parser Service` зчитує HTML САЗ (тільки читання) і передає заняття до `Booking & Conflict Service`, який створює бронювання за замовчуванням (`Booking.source = saz`). Дублікати не створюються завдяки `source_key`. | Юніт-тести парсера на збережених HTML-сторінках; тест повторного імпорту. |

Імпорт виконується атомарно: у разі таймауту або зміни HTML САЗ дані в БД не змінюються, а спроба записується в `SyncLog` зі статусом `failed`. | Тестування імпорту з імітацією падіння САЗ (PT-004). |
| **FR-006 / PERF-001** | Перегляд розкладу студентом (швидкодія ≤ 500 мс) | `Client Application`, `Booking & Conflict Service`, `Data Access Layer (Django ORM)`, `PostgreSQL Database` | Оптимізований read-only запит через `Django ORM` для отримання розкладу групи з актуальними аудиторіями; MVCC PostgreSQL не блокує читання під час записів. | Навантажувальне тестування (PT-001), TC-005. |
| **FR-007** | Перегляд розкладу викладачем | `Client Application`, `Booking & Conflict Service` | Вибірка занять за `Lesson.teacher_id`; предмет, група й час доступні лише для читання. | Інтеграційне тестування API. |
| **FR-008** | Ведення довідника аудиторій (CRUD) | `Classroom Directory Service`, `Client Application` | `Classroom Directory Service` керує сутністю `Room` (корпус, номер, місткість, обладнання, доступність). Зміни дозволені лише диспетчеру. | Інтеграційне тестування CRUD-операцій. |
| **FR-009** | Перегляд місткості та обладнання аудиторії | `Classroom Directory Service`, `Client Application` | Повернення характеристик `Room`; за відсутності обладнання UI показує «Обладнання відсутнє». | Перевірка відповідності даним у БД (TC-006). |
| **FR-010** | Підбір вільних аудиторій за місткістю та корпусом | `Booking & Conflict Service`, `Classroom Directory Service` | `Booking & Conflict Service` отримує з `Classroom Directory Service` аудиторії за корпусом і місткістю та відкидає ті, що мають активні бронювання з перетином у часі. | Інтеграційне тестування пошуку (TC-010). |

Предмет, група й час не змінюються. | E2E тестування сценарію користувача (TC-003). |

| **FR-015 / PERF-002** | Сповіщення студентів про зміну аудиторії (email ≤ 2 хв) | `Notification Service`, `Booking & Conflict Service` | Після збереження зміни `Booking & Conflict Service` передає подію в `Notification Service`, який створює внутрішнє сповіщення та асинхронно надсилає email через SMTP. | Мокування SMTP у тестовому середовищі (TC-007, PT-002). |
| **FR-016** | Сповіщення викладачів про конфлікт імпорту | `Notification Service`, `CA3 Parser Service` | Після виявлення конфлікту `CA3 Parser Service` ініціює в `Notification Service` сповіщення для викладачів обох занять. | Інтеграційний тест імпорту з конфліктом. |
| **FR-017 / SEC-003** | Ведення аудит-логу та його захист від змін | `Audit Service`, `Data Access Layer (Django ORM)`, `PostgreSQL Database` | Виклик `logAction` у межах транзакції зміни бронювання та запис у `AuditLog` (хто, коли, попередня/нова аудиторія, причина). Записи append-only: без операцій UPDATE/DELETE, зберігання ≥ 12 місяців. | Перевірка незмінності записів у БД (TC-004, ST-003). |
| **FR-018** | Фільтрація аудиторій за наявністю проєктора | `Classroom Directory Service`, `Client Application` | Фільтр списку аудиторій за полем `Room.projector_working`. | Інтеграційне тестування API (TC-001). |
| **FR-019** | Перегляд інформації про попередню пару | `Booking & Conflict Service`, `Client Application` | Вибірка бронювання тієї ж аудиторії в попередньому таймслоті; якщо його немає — повідомлення «Попередньої пари не було». | Юніт-тестування логіки вибірки часу (TC-002). |
| **FR-020** | Скасування активного бронювання | `API Gateway & Router`, `Booking & Conflict Service`, `Audit Service` | Перевірка ролі та належності заняття, після чого статус бронювання змінюється на `cancelled`, а дія фіксується в `AuditLog`. | E2E тестування сценарію користувача (TC-008). |

**Перевірка повноти:** кожна з 20 FR та 8 NFR має щонайменше один компонент, і кожен компонент діаграми (`Client Application`, `API Gateway & Router`, `Auth & User Service`, `CA3 Parser Service`, `Classroom Directory Service`, `Booking & Conflict Service`, `Notification Service`, `Audit Service`, `Data Access Layer (Django ORM)`, `PostgreSQL Database`) реалізує щонайменше одну вимогу.

## 2. Сценарії атрибутів якості (Quality Attribute Scenarios)

### Сценарій 1: Безпека (Security) - Захист від несанкціонованих дій
- **Джерело (Source):** Авторизований користувач із роллю "Студент".
- **Стимул (Stimulus):** Спроба надіслати HTTP-запит `POST /api/v1/bookings/change` на зміну існуючого бронювання.
- **Артефакт (Artifact):** `API Gateway & Router` та `Auth & User Service` (перевірка ролей).
- **Середовище (Environment):** Звичайна робота системи.
- **Реакція (Response):** `API Gateway & Router` передає токен на перевірку в `Auth & User Service`, отримує роль "студент", не передає запит до `Booking & Conflict Service` та логує спробу порушення доступу.
- **Міра реакції (Measure):** Запит відхиляється зі статус-кодом `403 Forbidden` за час < 100 мс; 0 змін у бронюваннях.

### Сценарій 2: Надійність (Reliability) - Відмовостійкість імпорту з САЗ
- **Джерело (Source):** Внутрішній планувальник системи UniSpace.
- **Стимул (Stimulus):** Спроба ініціювати плановий імпорт розкладу, коли зовнішня система САЗ (CA3) недоступна або змінила HTML-розмітку.
- **Артефакт (Artifact):** `CA3 Parser Service`.
- **Середовище (Environment):** Збій мережі або зміна структури сторінок САЗ.
- **Реакція (Response):** `CA3 Parser Service` фіксує таймаут або помилку парсингу, перериває імпорт без змін у `PostgreSQL Database`, записує спробу в `SyncLog` зі статусом `failed`, а система продовжує обслуговувати користувачів на останньому успішному знімку.
- **Міра реакції (Measure):** Імпорт переривається не пізніше ніж через 30 с; 0% втрати чи зміни існуючих даних; час відгуку розкладу для користувачів залишається ≤ 500 мс.

### Сценарій 3: Продуктивність (Performance) - Пікове навантаження на розклад
- **Джерело (Source):** Студенти (велика кількість одночасних користувачів).
- **Стимул (Stimulus):** 150 студентів одночасно відкривають сторінку свого розкладу на початку першої пари в понеділок.
- **Артефакт (Artifact):** `Client Application`, `API Gateway & Router`, `Booking & Conflict Service`, `Data Access Layer (Django ORM)`, `PostgreSQL Database`.
- **Середовище (Environment):** Режим пікового навантаження.
- **Реакція (Response):** Запити проходять через `API Gateway & Router` до `Booking & Conflict Service`; `Data Access Layer (Django ORM)` виконує оптимізовані read-only запити до `PostgreSQL Database` з використанням MVCC (без блокування таблиць).
- **Міра реакції (Measure):** 95% запитів обробляються та повертаються клієнту за час ≤ 500 мс без помилок (HTTP 500/503).

### Примітка
Структуровано за допомогою ШІ. Верифіковано шляхом перевірки та аналізу Михайлик Ольгою (керівником простежуваності).
