# Код і прогрес проєкту

У межах поточного етапу розробки (створення мінімального робочого прототипу) налаштовано базову архітектуру системи та повністю реалізовано структуру доменної моделі даних бекенду на базі Django та PostgreSQL.

## 1. Інфраструктура та середовище розробки
На початкових етапах створено ізольоване та надійне середовище для командної роботи:

* **Роздільна архітектура:** Проєкт фізично розділено на два незалежні Django-застосунки — Backend (REST API на базі Django REST Framework) та Frontend (клієнтський вебзастосунок на базі Django Templates із серверною генерацією HTML/CSS/JS).
* **Конфігурація та безпека середовища:** Налаштовано використання `.env` файлів для безпечного управління секретами (ключами, реквізитами БД). Впроваджено безпечне керування змінною `DEBUG` (вимкнення за замовчуванням у продакшен-середовищі).
* **Мережева взаємодія (CORS):** Налаштовано та оновлено пакет `django-cors-headers` для забезпечення безпечної міждоменної взаємодії (Cross-Origin Resource Sharing) між розділеними клієнтською та серверною частинами системи.
* **База даних:** Налаштовано роботу з PostgreSQL (включно з Docker-контейнеризацією для локальної розробки). Успішно підключено та активовано розширення `btree_gist` для забезпечення унікальності бронювань на рівні СУБД.
* **Контроль якості (CI/CD):** Впроваджено GitHub Flow. Налаштовано GitHub Actions для автоматичної перевірки коду в Pull Request (форматування `black`, лінтер `flake8`, аналізатор безпеки `bandit`).
* **Локальні перевірки:** Інтегровано pre-commit хуки (зокрема сканер секретів `gitleaks`) для запобігання потраплянню неякісного коду чи паролів до репозиторію.
* **Розгортання:** Налаштовано хмарне розгортання бекенду на платформі Render та генерацію живої інтерактивної документації Swagger UI.

## 2. Реалізовані моделі даних (Backend / БД)
Архітектура модельного шару використовує уніфіковані ідентифікатори UUID та підтримує бізнес-логіку управління аудиторним фондом поверх розкладу із САЗ:

* **User (Користувач):** Авторизація на основі електронної пошти замість стандартного юзернейму. Підтримка ролей (`student`, `teacher`, `dispatcher`) та зв'язок з академічною групою.
* **AcademicGroup (Академічна група):** Зберігає назву групи та унікальний зовнішній ключ САЗ (`source_key`) для синхронізації розкладу.
* **Lesson (Заняття):** Відображає навчальне заняття, завантажене із САЗ. Містить обмеження (`CheckConstraint`) на те, що час початку завжди передує часу завершення, та індекси для швидкого пошуку.
* **Room (Аудиторія університету):** Описує фізичні характеристики приміщення. Має обмеження унікальності комбінації корпусу й номера та перевірку додаттної місткості.
* **Booking (Бронювання):** Ключова сутність для управління розподілом аудиторій. Використовує `ExclusionConstraint` із оператором `OVERLAPS` на рівні PostgreSQL, що унеможливлює подвійне бронювання однієї аудиторії в той самий час (Race Condition).
* **Conflict (Конфлікт):** Реєструє наявні перетини занять в одній аудиторії з фіксацією часу перетину та статусу вирішення.
* **Notification (Сповіщення):** Забезпечує зберігання внутрішніх сповіщень користувачів із підтримкою індексів прочитання.
* **AuditLog (Журнал аудиту):** Реалізує пасивну безпеку та незмінність історії дій. Записи аудит-логу створюються за принципом append-only і зберігаються щонайменше 12 місяців.
* **SyncLog (Журнал синхронізації):** Фіксує статус успішності (`success`, `failed`) та час спроб імпорту розкладу.

## 3. REST API, Безпека та автоматизоване тестування
Окрім моделей бази даних, розроблено програмний інтерфейс (API) та логіку контролю доступу:

* **Проєктування API (Code-First та Mock-дані):** Створено базову структуру серіалізаторів та контролерів (`views`) для основних операцій (робота з аудиторіями та бронюваннями). На поточному етапі ці ендпоінти повертають статичні Mock-дані. Це дозволило швидко узгодити контракти та успішно згенерувати інтерактивну OpenAPI-документацію (Swagger). Написання повноцінного CRUD із прив'язкою до бази даних заплановано на наступний етап.
* **Узгоджена обробка помилок:** Впроваджено єдиний машинозчитуваний формат обробки помилок (через `ErrorResponseSerializer`), який гарантує, що всі відповіді з помилками мають стандартизовану структуру (`code`, `message`, `details`, `request_id`).
* **Контроль доступу (RBAC):** Повноцінно впроваджено перевірку ролей на рівні API (кастомний клас `IsTeacherOrDispatcher`). Відповідно до вимог безпеки (SEC-001 та NFR-4), створення та скасування бронювань дозволено виключно авторизованим викладачам і диспетчерам. Запити від анонімних користувачів та студентів на зміну даних жорстко блокуються (HTTP 403 Forbidden).
* **Регресійне тестування:** Написано набір автоматизованих безпекових та модульних тестів (`APISimpleTestCase`) для контролерів бронювання. Тести повністю покривають сценарії успішного створення/видалення бронювань, а також спроби несанкціонованого доступу з боку студентів та анонімів. Запуск тестів (`python manage.py test`) успішно перевірено локально та інтегровано в CI-конвеєр.
