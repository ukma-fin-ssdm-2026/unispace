# Код і прогрес проєкту

У межах поточного етапу розробки (створення мінімального робочого прототипу) налаштовано базову архітектуру системи. Структуру доменної моделі даних бекенду на базі Django та PostgreSQL підготовлено.

## 1. Інфраструктура та середовище розробки
На початкових етапах створено ізольоване та надійне середовище для командної роботи:

* **Роздільна архітектура:** Проєкт фізично розділено на два незалежні Django-застосунки — Backend (REST API на базі Django REST Framework) та Frontend (клієнтський вебзастосунок на базі Django Templates із серверною генерацією HTML/CSS/JS).
* **Конфігурація та безпека середовища:** Налаштовано використання `.env` файлів для безпечного управління секретами (ключами, реквізитами БД). Впроваджено безпечне керування змінною `DEBUG` (вимкнення за замовчуванням у продакшен-середовищі).
* **Мережева взаємодія (CORS):** Налаштовано пакет `django-cors-headers` для забезпечення міждоменної взаємодії (наразі адреси прописані жорстко, перенесення у змінні середовища для продакшену заплановано).
* **База даних:** Налаштовано роботу з PostgreSQL (включно з Docker-контейнеризацією для локальної розробки). Розширення `btree_gist` для забезпечення унікальності бронювань активовано.
* **Контроль якості (CI/CD):** Впроваджено GitHub Flow. CI-конвеєр (GitHub Actions) суттєво розширено: налаштовано `pip-audit`, перевірку форматування `black`, лінтер `flake8`, аналізатор безпеки `bandit`, запуск автоматизованих тестів, перевірку міграцій PostgreSQL, валідацію актуальності OpenAPI-специфікації, а також додано окремий job для перевірки фронтенду.
* **Локальні перевірки:** Інтегровано pre-commit хуки (зокрема сканер секретів `gitleaks`) для запобігання потраплянню неякісного коду чи паролів до репозиторію.
* **Розгортання:** Налаштовано хмарне розгортання бекенду на платформі Render та генерацію живої інтерактивної документації Swagger UI.

## 2. Реалізовані моделі даних
Архітектура модельного шару використовує уніфіковані ідентифікатори UUID та підтримує бізнес-логіку управління аудиторним фондом поверх розкладу із САЗ:

* **User (Користувач):** Авторизація на основі електронної пошти замість стандартного юзернейму. Підтримка ролей (`student`, `teacher`, `dispatcher`) та зв'язок з академічною групою.
* **AcademicGroup (Академічна група):** Зберігає назву групи та унікальний зовнішній ключ САЗ (`source_key`) для синхронізації розкладу.
* **Lesson (Заняття):** Відображає навчальне заняття, завантажене із САЗ. Містить обмеження (`CheckConstraint`) на те, що час початку завжди передує часу завершення, та індекси для швидкого пошуку.
* **Room (Аудиторія університету):** Описує фізичні характеристики приміщення. Має обмеження унікальності комбінації корпусу й номера та перевірку додатної місткості.
* **Booking (Бронювання):** Ключова сутність для управління розподілом аудиторій. Використовує `ExclusionConstraint` із оператором `OVERLAPS` на рівні PostgreSQL, що унеможливлює подвійне бронювання однієї аудиторії в той самий час (Race Condition).
* **Conflict (Конфлікт):** Реєструє наявні перетини занять в одній аудиторії з фіксацією часу перетину та статусу вирішення.
* **Notification (Сповіщення):** Забезпечує зберігання внутрішніх сповіщень користувачів із підтримкою індексів прочитання.
* **AuditLog (Журнал аудиту):** Реалізує пасивну безпеку. Записи створюються за принципом append-only на рівні ORM; жорсткий захист у БД і фіксований термін зберігання заплановано реалізувати згодом.
* **SyncLog (Журнал синхронізації):** Фіксує час спроб імпорту розкладу, джерело запуску (`manual` або `scheduled`) та деталізований статус виконання (`in_progress`, `success`, `failed`).

## 3. Перший робочий компонент: REST API, Безпека та автоматизоване тестування
Головним компонентом, який наразі працює і відповідає стандартам якості, є **REST API (5 ендпоінтів) з валідацією та перевіркою ролей: проходить 22 тести, black, flake8 і bandit у CI**. Усі контролери побудовані на основі базових класів `APIView` для забезпечення точного контролю над логікою

* **Часткова інтеграція з БД (ORM):** Ендпоінти отримання списку аудиторій (`GET /rooms/`), бронювань користувача (`GET /users/me/bookings/`) та логів синхронізації (`GET /sync-logs/`) вже підключені до реальної бази даних PostgreSQL.
* **Проєктування API (Mock-дані):** Решта 4 ендпоінти на базі `APIView` (створення/видалення бронювань, пошук вільних слотів, запуск синхронізації) тимчасово повертають статичні Mock-дані. Це дозволило швидко узгодити контракти та згенерувати інтерактивну OpenAPI-документацію (Swagger).
* **Узгоджена обробка помилок:** Впроваджено `ErrorResponseSerializer` — помилки валідації (400) і 404 бронювання мають єдиний машинозчитуваний формат.
* **Контроль доступу (RBAC):** Перевірку ролі на рівні API (кастомний клас `IsTeacherOrDispatcher`) реалізовано. Вона запрацює повністю після підключення інтеграції з Microsoft OAuth. Мета — дозволити створення та скасування бронювань виключно авторизованим викладачам і диспетчерам.
* **Автоматизоване тестування:** Написано 22 тести на всі 5 ендпоінтів (аудиторії, вільні слоти, створення й скасування бронювань, бронювання користувача), а також на схему OpenAPI. З них 4 — тести безпеки. Тести повністю покривають контракт API і контроль доступу на поточних заглушках, успішно перевірені локально та в CI. Старий монолітний файл `tests.py` замінено на модульні `test_views.py` та `test_audit_log.py` для кращої підтримки коду.
* **Узгодження моделі й API:** Логіку створення бронювань оновлено. API та роутер (`urls.py`) тепер суворо орієнтуються на `lesson_id` та `UUID` для доступу до записів, а поле `title` видалено задля нормалізації бази даних (DRY). Час бронювання (`start_time` та `end_time`) автоматично синхронізується з часом самого заняття на рівні моделі для забезпечення узгодженості та роботи `ExclusionConstraint`.

* **Оновлення документації API:** актуалізація схем `BookingCreate` та `BookingResponse` в документації дизайну API (`api-design.md`) та специфікації `openapi-generated.yaml`, щоб вони повністю відповідали логіці БД (очікування `lesson_id` замість `title` і ручного вводу часу).
* **Інтеграція автентифікації з Microsoft (OAuth2 / OIDC):** фіналізація формату `external_identity_id` у моделі користувача.
* **Менеджер користувачів:** написання власного менеджера для `User` (необхідно для коректної роботи команди `createsuperuser`).
* **Автоматика синхронізації САЗ:** реалізація фонових завдань. Доопрацювання `SyncLog` згідно з ADR-003 (додавання часткового індексу для оптимізації запитів).
* **Захист AuditLog на рівні бази даних:** написання тригерів PostgreSQL (Rules/Triggers) для абсолютної заборони `UPDATE` та `DELETE` у таблиці журналу.
* **Глобальна обробка помилок та логування:** налаштування `EXCEPTION_HANDLER` та `LOGGING` для DRF, щоб перехоплювати всі типи винятків.
* **CORS:** винесення дозволених адрес (origins) у змінні середовища для безпечного продакшен-розгортання.
* **Фронтенд-інтерфейс:** розробка HTML/JS шаблонів Django для візуальної взаємодії диспетчерів та викладачів.
