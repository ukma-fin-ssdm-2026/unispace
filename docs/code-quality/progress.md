# Код і прогрес проєкту

У межах поточного етапу розробки налаштовано базову архітектуру системи, запроваджено строгі практики тестування (TDD, перевірка властивостей) та оптимізовано структуру доменної моделі даних бекенду на базі Django та PostgreSQL.

## 1. Інфраструктура та середовище розробки
Створено та підтримується ізольоване та надійне середовище для командної роботи:

* **Роздільна архітектура:** Проєкт фізично розділено на два незалежні Django-застосунки — Backend (REST API на базі Django REST Framework) та Frontend (клієнтський вебзастосунок на базі Django Templates із серверною генерацією HTML/CSS/JS).
* **Конфігурація та безпека середовища:** Налаштовано використання `.env` файлів для безпечного управління секретами (ключами, реквізитами БД). Впроваджено безпечне керування змінною `DEBUG` (вимкнення за замовчуванням у продакшен-середовищі).
* **Мережева взаємодія (CORS):** Налаштовано пакет `django-cors-headers` для забезпечення міждоменної взаємодії (дозволені origin — локальний фронтенд і `unispace-front.onrender.com` — та `CSRF_TRUSTED_ORIGINS` поки прописані в `settings.py`; у production при `DEBUG=False` сесійна та CSRF-cookie отримують `Secure` і `SameSite=None`, увімкнено `CORS_ALLOW_CREDENTIALS`; перенесення списків у змінні середовища заплановано).
* **База даних:** Налаштовано роботу з PostgreSQL (включно з Docker-контейнеризацією для локальної розробки). Розширення `btree_gist` для забезпечення унікальності бронювань активовано.
* **Контроль якості (CI/CD):** Впроваджено GitHub Flow. CI-конвеєр (GitHub Actions) суттєво розширено: налаштовано `pip-audit`, перевірку форматування `black`, лінтер `flake8`, аналізатор безпеки `bandit`, запуск автоматизованих тестів (`pytest`), перевірку міграцій PostgreSQL, валідацію актуальності OpenAPI-специфікації, а також додано окремий job для перевірки фронтенду.
* **Автоматична перевірка простежуваності:** Впроваджено кастомний скрипт `check_traceability.py`, який у CI зіставляє мітки вимог у тестах (`pytest.mark.req`) із `rtm.md`.
* **Ворота покриття (Coverage Gates):** CI-збірка автоматично падає, якщо тестове покриття падає нижче цільового порогу в 75%.
* **Локальні перевірки:** Інтегровано pre-commit хуки (зокрема сканер секретів `gitleaks`) для запобігання потраплянню неякісного коду чи паролів до репозиторію.
* **Розгортання:** Бекенд (разом із PostgreSQL) і фронтенд розгорнуто на Render як два окремі вебсервіси; налаштовано також генерацію живої інтерактивної документації Swagger UI.

## 2. Реалізовані моделі даних
Архітектура модельного шару використовує уніфіковані ідентифікатори UUID та підтримує бізнес-логіку управління аудиторним фондом поверх розкладу із САЗ:

* **User (Користувач):** Авторизація на основі електронної пошти. Підтримка ролей (`student`, `teacher`, `dispatcher`) та зв'язок з академічною групою. Інтегровано ідентифікатор `external_identity_id` для Microsoft SSO.
* **AcademicGroup (Академічна група):** Зберігає назву групи та унікальний зовнішній ключ САЗ (`source_key`).
* **Lesson (Заняття):** Відображає навчальне заняття. Містить `CheckConstraint` (початок передує завершенню) та індекси.
* **Room (Аудиторія університету):** Описує фізичні характеристики приміщення. Має `UniqueConstraint` (корпус + номер) та перевірку додатної місткості.
* **Booking (Бронювання):** Використовує `ExclusionConstraint` (оператор `OVERLAPS`) у PostgreSQL для унеможливлення подвійного бронювання аудиторії.
* **Conflict (Конфлікт):** Реєструє наявні перетини занять в одній аудиторії (з САЗ) з фіксацією часу та статусу.
* **Notification (Сповіщення):** Забезпечує зберігання внутрішніх сповіщень. Додано логіку створення сповіщень при зміні аудиторії.
* **AuditLog (Журнал аудиту):** Реалізує пасивну безпеку. Записи створюються за принципом append-only на рівні ORM.
* **SyncLog (Журнал синхронізації):** Фіксує час, джерело та статус спроб імпорту розкладу.

## 3. Перший робочий компонент: REST API, Бізнес-логіка та Автоматизоване тестування
Головним компонентом, який наразі працює і відповідає стандартам якості, є **REST API (14 шляхів, 18 операцій) з валідацією та перевіркою ролей: проходить усі юніт-тести, black, flake8 і bandit у CI**. Усі контролери побудовані на основі базових класів `APIView` для забезпечення точного контролю над логікою.

* **Інтеграція з БД (CRUD):** Повністю завершено заміну Mock-даних на реальні ORM-запити. Реалізовано повноцінні CRUD-операції для бронювань та аудиторій, підключені до бази даних PostgreSQL. Лише `POST /api/v1/sync/` тимчасово є заглушкою до інтеграції парсера САЗ.
* **Автентифікація Microsoft (SSO):** Повністю реалізовано вхід через університетські акаунти (модулі `microsoft_auth.py` та `auth_views.py`), інтегровано ідентифікатор `external_identity_id`.
* **Чиста доменна логіка:** Бізнес-правила (тривалість заняття, перевірка місткості, маркер «Змінено») винесено в ізольований шар `api/services/booking_rules.py`. Алгоритми розрахунку часу відокремлено у `scheduling.py`.
* **Сервіс бронювань та сповіщень:** Транзакції бази даних (створення, скасування, перенесення заняття) виділено в `api/services/bookings.py`. Реалізовано `api/services/notifications.py` для генерації Email-шаблонів (із підтримкою підстановки `room_id`).
* **Інтелектуальний підбір аудиторій:** Впроваджено функцію `suggest_rooms` для пошуку альтернативних приміщень (`GET /bookings/{id}/alternatives/`).
* **Попередня пара в аудиторії (FR-019):** `GET /api/v1/bookings/{id}/previous/` повертає дисципліну, групу й викладача попередньої пари або повідомлення «Попередньої пари не було»; скасовані бронювання не враховуються.
* **Журнал аудиту для диспетчера (FR-017):** `GET /api/v1/audit-logs/` з фільтрами за бронюванням, аудиторією, дією та періодом і пагінацією; записи доступні лише для читання.
* **Пошук альтернатив за FR-010:** `GET /api/v1/bookings/{id}/alternatives/` спершу шукає лише в бажаному корпусі, а за `expand=true` розширює пошук на інші корпуси; відповідь містить `building`, `expanded`, `rooms` і `message`.
* **Конкурентні бронювання:** тест `test_concurrent_bookings.py` підтверджує, що з 10 паралельних запитів на один слот успішним є лише один (REL-001).
* **Демонстраційні дані:** команда `python manage.py seed_demo` (лише при `DEBUG=True`) створює групи, аудиторії, користувачів трьох ролей і заняття з бронюваннями на 02.11.2026.
* **Узгоджена обробка помилок та RBAC:** Впроваджено стандартизований формат помилок (400) через `ErrorResponseSerializer`. Усі `POST/PATCH/DELETE` запити бронювань надійно захищені від студентів (HTTP 403).
* **Багаторівневе тестування:** Успішно застосовано TDD. Додано property-based тести (через Hypothesis) для перевірки інваріантів правил бронювання. Додано перевірки на `ExclusionConstraint` для запобігання race conditions.
