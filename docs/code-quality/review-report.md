## Обсяг огляду

Розглянуто `OrganizationController`, `OrganizationService`,
`OrganizationCreateRequest`, `OrganizationUpdateRequest`,
`OrganizationRules`, `Organization`, `OffsetPage` та `OpenApiConfig`.

Код не запускався. Конфігурацію авторизації, автоматичні тести
та результати перевірок CI не перевірено.

## 1. Оцінка за критеріями

### Стиль і стандарти кодування

Назви класів і методів відповідають їхньому призначенню.
Відступи послідовні, константи мають назви у верхньому регістрі.

У сервісі використовується імпорт `java.util.*` і скорочені назви
змінних `r`, `cur`, `o`. Більш описові назви полегшили б читання.
Описи API змішують українську й англійську мови та містять
неформальні приклади.

### Якість і підтримуваність

Контролер, сервіс і DTO розділені. Спільні правила валідації
винесені в `OrganizationRules`, а перевірка унікальності slug —
у метод `ensureSlugFree()`.

Сервіс також відповідає за зберігання даних і створення
демонстраційних записів. Для лабораторної заглушки це допустимо.
При розвитку проєкту варто відокремити сховище від бізнес-логіки.

### Безпека

DTO містять обмеження довжини та формату полів, а контролер
використовує `@Valid` для тіла запитів. Для пагінації зазначені
допустимі межі параметрів.

Валідація назви при PATCH потребує доопрацювання: рядок із
пробілів проходить перевірку довжини, але після `trim()`
зберігається як порожнє значення.

JWT описаний в OpenAPI, однак у конфігурації зазначено, що
в заглушках він не перевіряється. `@SecurityRequirement`
документує вимогу авторизації, але сама її не забезпечує.
Фактичний захист endpoint’ів і керування сесіями потребують
окремої перевірки. У наданому сервісі журналювання змін не показано.

### Використання фреймворків

Маршрутизація та формування HTTP-відповідей знаходяться
в контролері. Пошук, перевірка slug і зміна організацій —
у сервісі.

Бізнес-методи не використовують `HttpServletRequest` або
`ResponseEntity`, що полегшує їх окреме тестування.
Водночас виділення окремого сховища спростило б подальший
перехід до бази даних.

### Документація і статичний аналіз

OpenAPI-анотації описують endpoint’и, параметри, моделі,
приклади та коди відповідей. Спільні відповіді помилок
винесені в конфігурацію.

Є незаповнене посилання `YOUR-REPO`. Опис видалення обіцяє
видалення пов’язаних подій, хоча показаний метод сервісу
видаляє лише організацію.

Для допоміжного методу `OffsetPage.of()` корисно додати
JavaDoc із допустимими аргументами. Наявність налаштованого
лінтера та звітів статичного аналізу не підтверджена.

## 2. Три сильні сторони

1. **Розділення відповідальностей.** Контролер обробляє HTTP,
   сервіс містить бізнес-логіку, а DTO описують вхідні дані.
   Це робить структуру зрозумілою та полегшує підтримку.

2. **Повторне використання правил і перевірок.** Формати полів
   визначені в `OrganizationRules`, перевірка slug не дублюється.
   Помилки мають конкретні коди й деталі через `FieldViolation`.

3. **Документований контракт API.** Описані операції та відповіді.
   Створення повертає `201 Created` із заголовком `Location`,
   видалення — `204 No Content`.

## 3. Три пропозиції покращення

### 3.1. Перевіряти назву після обрізання пробілів

**Місце:** `OrganizationUpdateRequest.name`,
`OrganizationService.update()`.

Значення `"   "` проходить `@Size(min = 3)`, але після `trim()`
стає порожнім. Значення `" a "` також проходить перевірку,
хоча зберігається лише один символ.

**Пропозиція:** перевіряти непорожність і довжину очищеної назви.
Зберегти семантику `null` як «не змінювати поле».
Додати тести для пробілів і короткої назви після обрізання.

### 3.2. Валідувати аргументи допоміжного методу пагінації

**Місце:** `OffsetPage.of()`.

Метод сам не перевіряє `limit` та `offset`. При виклику поза
контролером від’ємні значення можуть спричинити помилку
індексів у `subList()`.

**Пропозиція:** додати перевірки аргументів і документувати
допустимі значення. Перевірити від’ємні аргументи, порожній
список та offset за межами списку.

### 3.3. Узгодити документацію з реалізацією

**Місце:** `OpenApiConfig`,
`OrganizationController.deleteOrganization()`.

Посилання містить `YOUR-REPO`, а опис видалення не відповідає
показаній реалізації щодо пов’язаних подій.

**Пропозиція:** замінити шаблонне посилання, уточнити поведінку
заглушки та узгодити мову й приклади документації.

## 4. Потенційний ризик

### Повторна поява видаленої організації

**Місце:** `OrganizationService.update()` і `delete()`.

Методи `create()` та `update()` синхронізовані, а `delete()` — ні.
При одночасних запитах можлива така послідовність:

1. `update()` читає організацію через `get(id)`.
2. `delete()` видаляє її зі сховища.
3. `update()` записує оновлений об’єкт через `put()`.

У результаті успішно видалена організація може з’явитися знову.
`ConcurrentHashMap` захищає окремі операції, але не всю
послідовність «прочитати — змінити — записати».

**Рекомендація:** узгодити синхронізацію всіх операцій зміни,
зокрема `delete()`, та додати тест із контрольованим порядком
паралельних операцій.

## 5. Автоматичні перевірки та CI

| Перевірка | Спосіб |
| --- | --- |
| Форматування, імпорти, правила іменування | Форматер і Checkstyle |
| Підозрілі конструкції Java | SpotBugs |
| Валідація після `trim()` | Модульні або інтеграційні тести |
| Одночасне оновлення й видалення | Тест конкурентних операцій |
| Права доступу | Інтеграційні тести авторизації |
| Відповідність документації поведінці | Огляд колегою та API-тести |

Bandit призначений для Python, тому для цього Java-модуля
потрібні відповідні Java-інструменти.

У CI варто запускати перевірки стилю, статичний аналіз і тести
для кожного pull request. Успішне проходження перевірок
і схвалення колегою мають бути умовами злиття.
