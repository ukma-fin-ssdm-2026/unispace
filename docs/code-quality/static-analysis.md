| | |
|---|---|
| **Що знайдено** | `assert expected == actual` у `test_init.py:4` |

## 3. Знахідка безпеки з огляду коду: обхід перевірки ролі

Bandit шукає небезпечні виклики та конструкції, але не перевіряє бізнес-логіку авторизації. Тому найважливішу знахідку виявлено ручним оглядом коду.

### Знахідка S-2: `IsTeacherOrDispatcher` завжди дозволяє доступ

| | |
|---|---|
| **Що знайдено** | `Backend/api/views.py`, клас `IsTeacherOrDispatcher`: метод `has_permission` повертає `True` для будь-якого запиту. Справжню перевірку ролі закоментовано. |
| **Чим знайдено** | Ручний огляд коду (bandit такі логічні вади не виявляє) |
| **Загроза** | **TM-02** з `threat-model.md` (STRIDE: *Elevation of Privilege*): студент або неавтентифікований користувач обходить RBAC і створює чи скасовує бронювання. |
| **Порушена вимога** | **SEC-001**: endpoints, що змінюють стан бронювань, мають повертати 403 для ролі «студент» (тест ST-001 у `rtm.md`). |
| **Уражені endpoints** | `POST /api/v1/bookings/`, `DELETE /api/v1/bookings/{id}/` |
| **Чому це ризик** | Severity High за моделлю загроз: будь-хто може змінювати чужі бронювання. Наразі вплив обмежений, бо endpoints повертають заглушки і не змінюють даних. |
| **Рішення** | Заглушку свідомо залишено в Lab04 для Swagger-демо без токенів; це зазначено в `quality-attributes.md`. **До появи реальних даних заглушку треба замінити** на перевірку `is_authenticated` і ролі, з тестом, який перевіряє 403. Відповідальна: керівник прототипу. |

### Інші спостереження з безпеки

- `GET /api/v1/users/me/bookings/` має `AllowAny`, хоча за змістом повертає бронювання поточного користувача. Після появи автентифікації тут потрібен `IsAuthenticated`.
- У `REST_FRAMEWORK` не задано `DEFAULT_AUTHENTICATION_CLASSES`, `DEFAULT_PERMISSION_CLASSES` і throttling. Безпечніше зробити за замовчуванням `IsAuthenticated` і відкривати публічні endpoints явно.
- `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS` беруться зі змінних середовища, `DEBUG` за замовчуванням `False`. Секретів у коді bandit не знайшов (правила B105/B106).

## 6. Висновки та план

1. **Безпека.** Bandit не знайшов вразливостей середньої чи високої серйозності; єдину знахідку (B101 у тесті) прийнято. Головна вада безпеки, S-2 (TM-02, SEC-001), логічна, і її виявив огляд коду, а не інструмент. Вона має бути виправлена до роботи з реальними даними.
2. **Стиль.** Більшість зауважень flake8 стосуються форматування і зникнуть після `black .`. Форматування робиться **окремим pull request**, погодженим з керівником прототипу, щоб не створити конфліктів з її гілками.
3. **Автоматизація.** Наступний крок: додати `bandit`, `flake8` і `black --check` у CI (`.github/workflows/ci.yml`), щоб нові порушення не потрапляли в `main`.
