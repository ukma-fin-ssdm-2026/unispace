## REL-H01 — HTTP-запити без тайм-ауту

**Категорія:** B — зовнішні залежності; E — продуктивність і блокування.  
**Файл:** [`Frontend/static/js/api.js`](https://github.com/ukma-fin-ssdm-2026/unispace/blob/main/Frontend/static/js/api.js)

**До виправлення:**

```javascript
const response = await fetch(url, { method, headers, body, credentials: 'include' });
```

**Проблема:** немає явного обмеження тривалості запиту (`AbortController`/`AbortSignal.timeout`). Аналогічно `fetch` у `getCsrfToken()`.

**Чому небезпечно:** повільна чи недоступна залежність може надовго залишити інтерфейс в очікуванні. Поведінка залежить від браузера й мережевого стека; не стверджуємо, що запит гарантовано зависне назавжди.

**Потенційний вплив:** користувач не отримує вчасної відповіді на операцію, можливі повторні кліки й дубльовані дії.

- **Несправність:** відсутній прикладний timeout.
- **Помилка:** запит залишається в очікуванні довше допустимого часу.
- **Відмова:** UI не завершує операцію і не повідомляє про контрольований тайм-аут.
- **Критичність:** висока.
- **Рекомендація:** обмежити час через `AbortController`, показати зрозумілу помилку; значення timeout визначити за вимірами затримок.

**Актуальний стан:** у поточному коді для отримання CSRF-токена додано `AbortSignal.timeout(10000)`, а для основного API-запиту — `AbortSignal.timeout(timeout)`. Типове значення `timeout` становить 10000 мс. Виправлення присутнє в коді; перевірка скасування повільного запиту та повідомлення користувачу ще потрібна.

Обґрунтування саме 10000 мс вимірами затримок у межах цього дослідження не підтверджене. Значення слід перевірити за перцентилями фактичних затримок залежності. Отримання CSRF-токена та основний запит мають окремі тайм-аути, тому це не є спільним дедлайном усього сценарію.

## REL-H02 — Некоректна успішна JSON-відповідь непомітно стає `null`

**Категорія:** A — обробка помилок; D — потенційні мовчазні збої.  
**Файл:** [`Frontend/static/js/api.js`](https://github.com/ukma-fin-ssdm-2026/unispace/blob/main/Frontend/static/js/api.js)

**До виправлення:**

```javascript
const payload = await response.json().catch(() => null);
if (!response.ok) {
    throw new ApiError(response.status, payload);
}
return payload;
```

**Проблема:** помилка парсингу тіла перетворюється на `null` незалежно від статусу. Для HTTP 200 із некоректним JSON клієнт поверне `null` як нібито успішний результат.

**Чому небезпечно:** пошкоджена відповідь не відрізняється від очікуваного порожнього результату.

**Потенційний вплив:** наступний код може впасти при доступі до полів або показати порожні дані без зрозумілої причини.

- **Несправність:** надто загальне поглинання помилки JSON.
- **Помилка:** некоректний payload замінено на `null`.
- **Відмова:** користувач бачить порожній екран або некоректну помилку.
- **Критичність:** середня.
- **Рекомендація:** для успішних статусів вимагати коректний JSON (крім 204), а помилку парсингу явно повідомляти.

**Актуальний стан:** для успішної відповіді з некоректним JSON код тепер породжує помилку «Отримано некоректну JSON-відповідь від сервера». HTTP 204 обробляється окремо та повертає `null` без спроби JSON-парсингу. Виправлення присутнє в коді; поведінкова перевірка ще потрібна.

## REL-H04 — Некоректні `rowspan` і `colspan` у HTML — виправлено

**Категорія:** C — валідація входу.  
**Файл:** [`Backend/api/services/saz_parser.py`](https://github.com/ukma-fin-ssdm-2026/unispace/blob/main/Backend/api/services/saz_parser.py)

**До виправлення:**

```python
span = (int(attrs.get("rowspan") or 1), int(attrs.get("colspan") or 1))
self._cell = [[], span]
```

**Проблема:** значення з HTML безпосередньо передаються в `int()`, без обробки `ValueError` та перевірки діапазону. Далі `colspan` використовується в `range(colspan)`.

**Чому небезпечно:** нечисловий атрибут зупиняє парсинг, а надмірне число може створити велику кількість елементів і навантаження на пам'ять/CPU.

**Потенційний вплив:** імпорт не завершується або надмірно споживає ресурси.

- **Несправність:** немає валідації HTML-атрибутів.
- **Помилка:** внутрішня таблиця розкладу надмірно розростається або має некоректну структуру через неприйнятні значення атрибутів.
- **Відмова:** розклад не імпортується, можлива затримка відповіді.
- **Критичність:** висока.
- **Рекомендація:** перевіряти числові значення та розумні межі, некоректний HTML відхиляти через `SazParseError`.

**Виправлено (Етап 3, Ольга Михайлик).**

- **Тип відмови — швидка.** Некоректний `rowspan` зсуває день і час у всіх наступних рядках, тож «безпечне» значення за замовчуванням дало б хибний розклад і хибні бронювання. Неправильна відповідь тут гірша за відсутність відповіді, тому сторінку відхиляємо, а вже імпортовані дані лишаються без змін (REL-002).
- **Перевірка входу (guard clause):** нова функція `_span` приймає лише ціле число в межах `1…MAX_ROWSPAN` (200) і `1…MAX_COLSPAN` (20). Межі взято з запасом відносно справжньої сторінки САЗ (`rowspan` до 19, `colspan` до 6).
- **Чітка помилка замість сирого винятку:** `SazParseError «Некоректний атрибут colspan=«1000000» у таблиці розкладу (дозволено 1–20)»` замість `ValueError: invalid literal for int()`; роздута сітка більше не створюється.
- **Логування:** `run_sync` записує спробу в `SyncLog` зі статусом `failed` і цим повідомленням, тож диспетчер бачить причину.

```python
def _span(attrs, name, limit):
    raw = (attrs.get(name) or "1").strip()
    if not raw.isdigit() or not 1 <= int(raw) <= limit:
        raise SazParseError(f"Некоректний атрибут {name}=«{raw[:20]}» у таблиці розкладу (дозволено 1–{limit})")
    return int(raw)
```

**Тести:** `test_saz_parser.py::test_invalid_span_rejects_page_with_clear_parse_error` (10 випадків: `abc`, `-1`, `0`, `2.5`, `1000000` для обох атрибутів), `test_saz_parser.py::test_span_with_spaces_and_upper_limit_is_accepted`, `test_saz_import.py::test_page_with_invalid_colspan_is_logged_as_failed_and_keeps_data`.

## REL-H05 — Некоректний час із HTML не перетворюється на попередження

**Категорія:** C — валідація входу.  
**Файл:** [`Backend/api/services/saz_parser.py`](https://github.com/ukma-fin-ssdm-2026/unispace/blob/main/Backend/api/services/saz_parser.py)

**До виправлення:**

```python
h1, m1, h2, m2 = (int(value) for value in match.groups())
return time(h1, m1), time(h2, m2)
```

**Проблема:** шаблон регулярного виразу допускає, наприклад, `25:99-26:99`, але `datetime.time` відхилить ці значення через `ValueError`. У `_parse_time` виняток не перехоплюється; це відрізняється від гілки, де нерозпізнаний час записується до `warnings`.

**Чому небезпечно:** один пошкоджений рядок може перервати імпорт усього файлу.

**Потенційний вплив:** відсутній оновлений розклад, замість локального попередження — загальна помилка імпорту.

- **Можлива несправність:** різна реакція на некоректний час без погодженої політики відхилення документа або пропуску рядка.
- **Помилка:** `ValueError` перериває `parse_schedule()`.
- **Можлива відмова:** весь імпорт відхиляється замість пропуску одного рядка, якщо контракт передбачає частковий імпорт.
- **Критичність:** попередньо середня; залежить від погодженого контракту.
- **Рекомендація:** явно перевіряти час, відхиляти некоректний рядок або формувати `SazParseError` згідно з узгодженим контрактом.

**Уточнення після повторної перевірки:** `run_sync()` перехоплює `ValueError`, переводить синхронізацію у `failed` і повертає результат невдалого імпорту. Тому це не безумовний необроблений збій системи.

**Виправлено.**

- У `_parse_time()` додано вузьке перехоплення `ValueError` із перетворенням на `SazParseError` та зрозумілим повідомленням про допустимі години й хвилини.
- Додано перевірку, що час завершення пізніше за час початку.
- **Тип відмови — швидка.** Документ із некоректним числовим часом відхиляється повністю: автоматична підміна часу могла б створити неправильний розклад і бронювання. Для нерозпізнаного формату часу збережено попередню поведінку — пропуск рядка з попередженням.
- **Контрольована деградація:** попередній успішний розклад залишається доступним. Диспетчер отримує пояснення, виправляє файл і повторює імпорт.

**Після виправлення:**

```python
def _parse_time(text):
    match = _TIME_RANGE.search(text)
    if not match:
        return None

    h1, m1, h2, m2 = (int(value) for value in match.groups())
    try:
        start = time(h1, m1)
        end = time(h2, m2)
    except ValueError as error:
        raise SazParseError(
            f"Некоректний час заняття «{text}»: години мають бути 0–23, хвилини — 0–59"
        ) from error

    if end <= start:
        raise SazParseError(
            f"Некоректний час заняття «{text}»: час завершення має бути пізніше за час початку"
        )
    return start, end
```

**Тести:** `Backend/api/tests/reliability/test_saz_time.py` — некоректні години та хвилини, порядок початку й завершення, валідні граничні значення, попередня поведінка для нерозпізнаного часу та невдалий імпорт без зміни наявних занять і бронювань.

**Статус:** виправлено; тести пройдено локально.

## REL-H06 — Необмежений діапазон навчальних тижнів

**Категорія:** C — валідація входу; E — продуктивність.  
**Файл:** [`Backend/api/services/saz_parser.py`](https://github.com/ukma-fin-ssdm-2026/unispace/blob/main/Backend/api/services/saz_parser.py)

```python
first, last = int(match.group(1)), int(match.group(2))
if first > last:
    raise ValueError(f"Некоректний діапазон тижнів: {text}")
weeks.update(range(first, last + 1))
```

**Проблема:** перевіряється лише порядок `first <= last`, але не максимальна кількість тижнів. У `import_schedule()` кожен тиждень спричиняє окрему обробку заняття.

**Чому небезпечно:** діапазон на кшталт `1-1000000` може створити надмірну кількість елементів та ітерацій, спричинити зайві DB-операції або помилку обчислення дати.

**Потенційний вплив:** тривале виконання імпорту, перевантаження БД, тайм-аут HTTP-запиту.

- **Несправність:** немає допустимих меж навчальних тижнів.
- **Помилка:** формується непропорційно великий набір тижнів або недопустима дата заняття.
- **Відмова:** імпорт надто довгий, завершується помилкою або створює заняття поза семестром.
- **Критичність:** висока.
- **Рекомендація:** обмежити тижні межами семестру та відхиляти некоректний діапазон до початку його розгортання й імпорту.

**Доповнення після повторної перевірки:** відсутня також нижня межа. `parse_weeks("0")` приймає тиждень `0`. У `saz_import.py` дата обчислюється через `timedelta(weeks=week - 1, days=weekday)`, тому такий вхід може створити заняття за тиждень до першого навчального тижня. Потрібно перевіряти як нижню, так і верхню межу; верхню межу погодити відповідно до правил семестру. Некоректні значення слід відхиляти явно, без автоматичної підміни дати заняття.

## REL-H07 — Непередбачений виняток залишає синхронізацію незавершеною — виправлено

**Файл:** [`Backend/api/services/saz_import.py`](https://github.com/ukma-fin-ssdm-2026/unispace/blob/main/Backend/api/services/saz_import.py)

**До виправлення:**

```python
log = SyncLog.objects.create(
    status=SyncLog.SyncStatus.IN_PROGRESS,
    trigger=trigger or SyncLog.SyncTrigger.MANUAL,
)
try:
    result = import_schedule(parse_schedule(html), semester_start)
except (SazParseError, ValueError) as error:
    log.status = SyncLog.SyncStatus.FAILED
    log.error_message = str(error)

log.save(update_fields=["status", "error_message", "finished_at"])
```

**Проблема:** `OperationalError`, `IntegrityError` та інші неочікувані винятки з імпорту не переводять створений `SyncLog` у `failed`, бо код завершення розташований після `try/except`.

**Чому небезпечно:** журнал може залишитися зі статусом `in_progress` навіть після завершення запиту з помилкою. Окремі DB-збої можуть також перешкодити запису `failed`, тому потрібна обережна стратегія логування.

**Потенційний вплив:** неправильна інформація про стан імпорту; майбутня логіка блокування паралельних запусків може сприймати запис як активний.

- **Несправність:** відсутній контрольований шлях завершення для неочікуваних помилок.
- **Помилка:** `SyncLog.status` лишається `in_progress`.
- **Відмова:** диспетчер бачить незавершений імпорт після збою.
- **Критичність:** висока.
- **Рекомендація:** логувати неочікувані винятки, безпечно намагатися перевести журнал у `failed`, не приховувати системну помилку; окремо врахувати недоступність БД.

**Виправлено (Етап 3, Ольга Михайлик).**

- **Тип відмови — швидка.** Неочікуваний збій (база, помилка в коді) не можна видати за успішний чи «майже успішний» імпорт: запит завершується помилкою, а не безпечним значенням. Перед цим система намагається закрити журнал, щоб стан відповідав результату операції.
- **Окремий вузький шлях для очікуваних помилок** (`SazParseError`, `ValueError`) лишився як був: зрозуміле повідомлення для диспетчера, `failed`, без винятку назовні.
- **Для решти винятків:** `logger.exception(...)` пише повний traceback у лог сервера; `_mark_failed` намагається перевести `SyncLog` у `failed` з `finished_at`; виняток передається далі (`raise`), тобто збій не приховано.
- **Без витоку внутрішніх деталей:** у `error_message`, який бачить диспетчер, лише тип помилки («Неочікувана помилка імпорту: OperationalError»), а текст винятку (SQL, шляхи) — тільки в лозі.
- **Недоступна сама база:** якщо не вдається записати й статус `failed`, `_mark_failed` перехоплює лише `DatabaseError`, логує її й не підміняє початкову помилку.

```python
except Exception as error:
    logger.exception("Неочікувана помилка імпорту САЗ (SyncLog %s)", log.pk)
    _mark_failed(log, f"Неочікувана помилка імпорту: {type(error).__name__}")
    raise
```

**Тести:** `test_saz_import.py::test_unexpected_error_marks_sync_failed_and_is_reraised` (`OperationalError` і `RuntimeError`: журнал `failed`, `finished_at` заповнено, повідомлення без деталей, запис у лозі, виняток не приховано), `test_saz_import.py::test_original_error_is_kept_when_sync_log_cannot_be_updated` (база недоступна й для запису журналу: назовні початкова помилка, проблема залогована).

**Обмеження:** якщо БД недоступна, статус може залишитися `in_progress`; логування не гарантує його узгодження після відновлення БД. Повторне породження винятку також саме по собі не гарантує контрольованої HTTP-відповіді: у `SyncTriggerAPIView` окремої обробки цього винятку немає.

## REL-H08 — Не всі зовнішні збої Microsoft OAuth перетворюються на контрольовану помилку

**Категорія:** A — обробка помилок; B — зовнішні залежності.  
**Файл:** [`Backend/api/services/microsoft_auth.py`](https://github.com/ukma-fin-ssdm-2026/unispace/blob/main/Backend/api/services/microsoft_auth.py)

```python
try:
    result = build_msal_app().acquire_token_by_auth_code_flow(flow, query_params)
except ValueError as error:
    raise MicrosoftLoginError("Невалідна відповідь Microsoft") from error
```

**Проблема:** лише `ValueError` трансформується у доменну помилку. Мережеві/транспортні помилки або збої бібліотеки, що мають інші типи, не проходять через контрольований шлях `MicrosoftLoginError`, який обробляє `microsoft_callback`.

**Чому небезпечно:** тимчасова недоступність Microsoft може дати необроблений 500 замість контрольованої відповіді. Не стверджуємо, що MSAL не має власних тайм-аутів: їхня конфігурація тут не встановлена явно.

**Потенційний вплив:** користувач не може увійти, отримує загальну серверну помилку.

- **Несправність:** неповне зіставлення зовнішніх винятків із доменною помилкою.
- **Помилка:** виняток проходить поза очікуваним `MicrosoftLoginError`.
- **Відмова:** можливий HTTP 500 при тимчасовому збої автентифікації.
- **Критичність:** середня.
- **Рекомендація:** визначити конкретні типи винятків MSAL/HTTP, обробляти їх окремо, логувати технічні деталі серверно та повертати безпечне повідомлення.

## REL-H09 — Необмежений розмір сторінки аудиторій

**Категорія:** C — валідація входу; E — продуктивність.  
**Файли:** [`Backend/api/serializers.py`](https://github.com/ukma-fin-ssdm-2026/unispace/blob/main/Backend/api/serializers.py), [`Backend/api/views.py`](https://github.com/ukma-fin-ssdm-2026/unispace/blob/main/Backend/api/views.py)

```python
class RoomQuerySerializer(serializers.Serializer):
```


- **Несправність:** відсутній `max_value` у пагінації.
- **Помилка:** надто велика вибірка та серіалізація.
- **Відмова:** затримка відповіді або тайм-аут.
- **Критичність:** середня.
- **Рекомендація:** додати обґрунтований верхній ліміт (наприклад, узгоджений командою після оцінки потреб API) та граничний тест.

## Контрольована деградація

Для кожного виправлення потрібно визначити, що небезпечніше: неправильна відповідь чи відсутність відповіді.

- **REL-H01:** після тайм-ауту потрібна явна помилка та відновлення доступності елементів UI. Тайм-аут браузера не доводить, що сервер не виконав запис, тому перед повторною дією потрібно перевірити результат попередньої операції.
- **REL-H02:** некоректний JSON успішної відповіді не повинен перетворюватися на успішний `null`. Поточна явна помилка є правильною реакцією на порушення контракту.
- **REL-H03:** некоректний CSRF-токен має зупиняти основний запит. Виконувати запис із підставним токеном або обходити перевірку не можна.
- **REL-H04 та очікувані помилки імпорту:** документ відхиляється, а раніше імпортований розклад залишається доступним. У `Frontend/static/js/saz_import.js` диспетчер бачить повідомлення «Імпорт не вдався… Попередні дані не змінено». Після виправлення файлу він може повторити імпорт.
- **REL-H06 та REL-H09 після виправлення:** недопустимий вхід слід відхиляти зрозумілою помилкою до витратних операцій. Користувач має виправити параметри.
- **REL-H07:** система намагається записати `failed` та передає неочікуваний виняток далі. Якщо БД недоступна, потрібне окреме рішення щодо незавершених записів після її відновлення.
- **REL-H08 після підтвердження та виправлення:** потрібна контрольована помилка входу без створення сесії та без обходу автентифікації.

Збережений розклад є резервним варіантом при невдалому імпорті. Повідомлення на сторінці імпорту показує диспетчеру, що оновлення не відбулося. Наявність загальної позначки свіжості або часу останнього успішного знімка на всіх сторінках розкладу не підтверджена.

У проєкті також є приклад деградації другорядної функції: відправка email після зміни аудиторії. У `Backend/api/services/bookings.py` вона викликається через `transaction.on_commit()`, а в `Backend/api/services/notifications.py` помилка `OSError` під час `send_mass_mail()` логується, після чого функція повертає `0`. Уже збережене перенесення не скасовується; повідомлення всередині системи створюються в транзакції до коміту. Для SMTP встановлено `EMAIL_TIMEOUT = 10`.

Цей захист стосується перехопленої помилки відправки: збої підготовки листів і читання одержувачів поза відповідним `try` ним не покриваються. Постійна черга повторної доставки та явний статус невдалого email у UI цим кодом не підтверджені.

## Поєднання патернів стійкості

У перевірених прикладних шляхах тайм-аути додано до `fetch()` і SMTP. Це не доводить, що всі віддалені залежності системи мають перевірені межі очікування. Для MSAL потрібна окрема перевірка транспортної конфігурації. `CONN_MAX_AGE` у Django визначає час повторного використання з’єднання, а не тайм-аут виконання запиту до БД.

Власних автоматичних повторів із backoff/jitter та circuit breaker у перевірених шляхах не виявлено. Їх не слід описувати як реалізовані. За умовами Lab09 реалізація обмежених повторів із джитером є окремим бонусним пунктом.

Якщо команда додаватиме повтори:

- Кожна віддалена спроба має бути обмежена тайм-аутом.
- Повторювати потрібно лише тимчасові збої, обмеженою кількістю спроб, з експоненційним відступом, стелею та повним джитером.
- Повтори мають виконуватися на одному погодженому рівні, щоб не множити кількість викликів.
- Помилки валідації, невалідний CSRF і некоректний HTML не виправляються автоматичними повторами того самого входу.
- Для записів потрібна підтверджена ідемпотентність, наприклад клієнтський токен операції з серверним захистом від повторного виконання. Сам тайм-аут або обмеження БД не доводять безпечність повтору всієї операції.
- Якщо додано circuit breaker, відкритий вимикач має припиняти подальші спроби.
- Після вичерпання спроб потрібен явний результат: чітка помилка або перевірений резервний варіант. Якщо повертаються застарілі дані, це має бути позначено.

Ці правила передаються інженерці надійності та тестувальниці для реалізації й перевірки відповідних сценаріїв.
