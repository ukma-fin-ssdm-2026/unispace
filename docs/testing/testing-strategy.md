# Стратегія тестування команди UniSpace

## Поточний статус тестування
На даному етапі в проєкті впроваджено автоматизоване тестування бекенду на Django REST Framework: **33 тестові модулі** у `Backend/api/tests/` (**435 тестів** загалом разом із параметризованими випадками `pytest`) та **19 тестових функцій** скриптів CI у `Backend/scripts/tests/`.

**Розподіл тестових модулів у `Backend/api/tests/`:**
* **`integration/` (17 модулів):** ендпоінти API (аудиторії, бронювання, зміна аудиторії, підбір вільних аудиторій, попередня пара, розклад, аудит-лог, імпорт розкладу САЗ, вхід через Microsoft, журнал синхронізації), права доступу в Django-адмінці та доменні правила в `Backend/api/services/`. Працюють із реальною базою PostgreSQL (у CI — сервіс `postgres`), оскільки правило накладок (`ExclusionConstraint`) існує лише на рівні СУБД.
* **`unit/` (9 модулів):** ізольовані перевірки серіалізаторів, парсера HTML, прав доступу, правил тривалості/місткості та алгоритму підбору аудиторій.
* **`reliability/` (7 модулів):** тести стійкості та обробки відмов (граничні значення, тайм-аути, ін'єкція збоїв БД та Microsoft OAuth, перевірка `/api/v1/health/`).

## Тестові дублери та ізольовані юніт-тести

Для перевірки серіалізаторів, прав доступу й доменних правил застосовуються ізольовані юніт-тести з `mock`-об'єктами та `APIRequestFactory` у `Backend/api/tests/unit/` (зокрема `unit/test_serializers.py`, `unit/test_room_suggestions.py`, `unit/test_room_occupancy.py`, а у `unit/test_microsoft_auth.py` замість реального сервісу Microsoft використовується заглушка MSAL). Такий підхід дозволяє перевіряти валідацію даних і бізнес-логіку без звернення до БД чи зовнішніх сервісів, роблячи тести швидкими, стабільними та незалежними від стану бази.

Доменні правила, на яких виконували TDD, мутаційне тестування та тести властивостей, винесено в окремі сервіси й підключено безпосередньо до ендпоінтів:
* правило місткості (`services/booking_rules.py`) — у підборі аудиторій;
* перетин інтервалів (`services/scheduling.py`) — у визначенні зайнятих аудиторій для `GET /bookings/{id}/alternatives/`;
* маркер «Змінено» (`is_recently_changed`) — у формуванні розкладу.

Таким чином, юніт-тести цих правил перевіряють код, який безпосередньо виконується в API.

## Плани для інтеграційних, системних та приймальних тестів
* **Інтеграційні тести:** конкурентний сценарій `REL-001` (10 паралельних бронювань одного слота, `test_concurrent_bookings.py`) уже реалізовано на реальній PostgreSQL. Надалі планується аналогічно перевірити паралельну зміну аудиторії (`POST /bookings/{id}/change/`) і паралельні запуски імпорту САЗ.
* **Системні тести (E2E):** після завершення розробки фронтенду планується автоматизація наскрізних користувацьких сценаріїв (від вибору слота в UI до запису в БД та генерації сповіщення).
* **Приймальні тести (UAT):** ручна валідація на staging-середовищі, зокрема наскрізної автентифікації через Microsoft OAuth2 та коректності розмежування ролей.

## Плани для тестування продуктивності, безпеки та property-based тестування
* **Безпека (Security):** окрім інструментів `bandit` та `pip-audit`, уже діють тести контролю доступу (`403 Forbidden` та обмеження прав в адмінці) для ролей без відповідних прав (`BookingSecurityTests`, `test_audit_log_api.py`, `test_booking_previous_lesson.py`, `test_saz_import.py`, `test_admin.py`); їх планується розширювати на нові ендпоінти. 
* **Продуктивність (Performance):** тестування швидкодії системи під час масового перегляду розкладу (очікуваний час відповіді ≤ 500 мс за `PERF-001`) та навантажувальне тестування імпорту великих HTML-файлів розкладу із САЗ.
* **Тестування на основі властивостей (Property-based):** уже реалізовано для правил бронювання (див. розділ «Бонуси»); надалі поширюватиметься на нові модулі з чистою бізнес-логікою.

## Інтеграція у конвеєр CI/CD
Тести інтегровані в GitHub Actions (`.github/workflows/ci.yml`). Під час створення кожного Pull Request у гілку `main` конвеєр автоматично піднімає оточення з PostgreSQL, встановлює залежності та запускає `pytest` із перевіркою порогу покриття (`--cov-fail-under=75`). Збірка блокується, якщо падає будь-який тест, покриття нижче 75% або не проходять лінтери.

## Бонуси

### 1. Мутаційне тестування
Використано інструмент `mutmut` 3 для Python на модулі правил бронювання `Backend/api/services/booking_rules.py` (до рефакторингу — `Backend/api/booking_rules.py`, функції `booking_duration` і `validate_attendees_fit_room`). Запуск: `mutmut run` із каталогу `Backend/`.

* **Оцінка мутації:**
  * Перший запуск: згенеровано **35 мутантів**, знищено **24**, вижило **11** (≈69%).
  * Після підсилення тестів: знищено **33 із 35** (≈94%), вижило **2**. Без урахування 2 еквівалентних мутантів, які неможливо виявити тестом, результат становить **33 із 33 (100%)**.


* **Які мутанти вижили:**
  * *Основна група (9 із 11):* зміна тексту повідомлень про помилки (`"XX…XX"` або зміна регістру першої літери). Тести перевіряли винятки через пошук підрядка `pytest.raises(..., match="...")`, тому мутований текст проходив перевірку.
  * *Еквівалентні мутанти (2 із 11):* заміна `astimezone(timezone.utc)` на `astimezone(None)`. Оскільки Python обчислює різницю `aware`-дат через їхні зміщення від UTC, поведінка функції не змінюється.


* **Як їх знищено:**
  * Для 9 мутантів із текстами помилок: `match="..."` замінено на перевірку точного збігу всього рядка `match=f"^{re.escape(message)}$"` (допоміжна функція `assert_raises_message`), а також розділено тести для наївного (без часового поясу) початку й кінця інтервалу (`naive_start` і `naive_end`).
  * Для межі місткості (превентивно): додано перевірку `30` місць із 30 (допустимо) проти `31` із 30 (відхиляється), що закриває мутацію `>` → `>=`, а також граничні випадки `1 з 1`, `0` і `-1` учасників.

### 2. Тести на основі властивостей (Property-based testing)
Застосовано бібліотеку `hypothesis` у файлі `Backend/api/tests/unit/test_booking_properties.py`.

* **Властивість:** для будь-якої згенерованої пари валідного часу `start_time` та `end_time` (`end_time > start_time`) функція `booking_duration` повертає додатну тривалість, що дорівнює реальному проміжку часу, незалежно від високосних років, часових поясів і переведення годинників.


* **Пояснення:** `hypothesis` генерує сотні пар `aware`-дат у діапазоні 2020–2035 років у 5 часових поясах. Додатково перевіряються інваріанти: перевернутий інтервал завжди відхиляється; тривалість є адитивною; кількість учасників у межах місткості завжди допустима, а понад місткість — відхиляється.

### 3. Ворота покриття в CI

* **Поріг:** налаштовано обов'язкову перевірку `--cov-fail-under=75` у CI-конвеєрі (крок `Run tests with coverage and gate`).
* **Обґрунтування:** поріг 75% обрано як баланс між надійністю бізнес-логіки та гнучкістю розробки — він гарантує тестування критичних доменних функцій без потреби писати штучні тести для конфігураційних файлів або простих DTO.
* **Підтвердження:** у репозиторії є щонайменше один успішний прогін CI, де покриття склало понад 75%: [CI Pipeline #371](https://github.com/ukma-fin-ssdm-2026/unispace/actions/runs/39688274707/job/119527773647).
