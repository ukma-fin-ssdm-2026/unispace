# Стратегія тестування команди SpaceOps

## Поточний статус тестування
На даному етапі в проєкті впроваджено базове автоматизоване модульне тестування для бекенду на Django REST Framework.
Наразі успішно проходять 29 тестів (включно з тестами безпеки, зокрема перевірками на видалення), які покривають усі 5 поточних ендпоїнтів (аудиторії, вільні слоти, створення/скасування бронювань, бронювання користувача) та схему OpenAPI. Тестування реалізовано за допомогою pytest (у модулях test_views.py, test_audit_log.py та test_test_doubles.py). Для ендпоїнтів, які тимчасово не підключені до реальної БД (створення/скасування бронювань), використовуються Mock-дані для узгодження контрактів. Статичний аналіз коду та перевірки на безпеку (black, flake8, bandit, pip-audit) інтегровані в процес розробки.

## Тестові дублери та ізольовані юніт-тести

Для перевірки серіалізаторів і прав доступу ми застосовуємо ізольовані юніт-тести з використанням mock-об'єктів та APIRequestFactory 
(див. test_test_doubles.py). Такий підхід дозволяє тестувати валідацію даних і логіку дозволів без звернення до бази даних, 
не створюючи зайвого навантаження на неї, що робить ці тести швидкими, стабільними та незалежними від стану БД.

## Підсумок покриття
* **Загальний відсоток покриття:** ~95% (деталі у звіті `htmlcov/index.html`). Це вже перевищує цільовий поріг:
* у CI поріг налаштовано на 75% для балансу між надійністю та гнучкістю, а фактичне покриття його перевершує.
* **Що залишилося непокритим і чому:** Частково непокритою залишається логіка прямого парсингу HTML-сторінок зовнішньої системи САЗ, оскільки для стабільності тестів ми використовуємо моковані дані замість реальних HTTP-запитів до нестабільного зовнішнього ресурсу.
Глобальні обробники винятків (DRF EXCEPTION_HANDLER) та тригери БД для пасивного захисту таблиці AuditLog наразі перебувають у статусі розробки (TODO), тому ще не мають повного тестового покриття.

## Плани для інтеграційних, системних та приймальних тестів
* **Інтеграційні тести:** Заміна Mock-даних на реальні ORM-запити дозволить перевірити коректність транзакцій і роботу блокувань на рівні бази даних PostgreSQL (зокрема ExclusionConstraint для запобігання Race Condition при бронюванні однієї аудиторії).
* **Системні тести (E2E):** Після розробки фронтенду планується автоматизація повних користувацьких сценаріїв (від вибору слота на UI до запису в БД та генерації сповіщення).
* **Приймальні тести (UAT):** Ручна валідація на staging-середовищі, особливо для перевірки наскрізної автентифікації через Microsoft OAuth2 та коректності розподілу ролей.

## Плани для тестування продуктивності, безпеки та property-based тестування
* **Безпека (Security):** Окрім інструментів `bandit` та `pip-audit`, які вже працюють, ми додамо автоматичні тести на спробу несанкціонованого доступу (403 Forbidden) для ролей без прав на модифікацію розкладу.
* **Продуктивність (Performance):** Тестування швидкодії системи під час масового перегляду розкладу (очікуваний час відповіді <500мс) та перевірка відмовостійкості (Circuit Breaker) фонового завдання імпорту розкладу із САЗ.
* **Тестування на основі властивостей (Property-based):** Використання бібліотеки hypothesis для автоматичної генерації граничних випадків при розрахунку тривалості занять, щоб гарантувати узгодженість start_time та end_time у всіх можливих сценаріях часових поясів.

## Інтеграція у конвеєр CI/CD
Наші тести повністю інтегровані в GitHub Actions (файл `ci.yml`). Під час створення кожного Pull Request у гілку `main` конвеєр автоматично піднімає оточення, встановлює залежності та запускає `pytest`. Злиття PR неможливе, якщо тести падають або не проходять лінтери.

## Бонуси

### 1. Мутаційне тестування 
**1) Варіант Трекурової Анастасії**
Ми використали інструмент `mutmut` 3 для Python на модулі правил бронювання `Backend/api/booking_rules.py`
(функції `booking_duration` і `validate_attendees_fit_room`). Запуск: `mutmut run` із папки `Backend/`.
**Оцінка мутації**
- Перший запуск: згенеровано 35 мутантів, знищено 24, вижило 11 (≈69%).
- Після підсилення тестів: знищено 33 із 35 (≈94%), вижило 2. Якщо не враховувати 2 еквівалентні мутанти,
  які неможливо вбити тестом, то 33 із 33 (100%).
**Мутант, що вижив**
- Основна група (9 мутантів із 11): зміна тексту повідомлень про помилки. Мутація обгортала текст у `XX…XX`
  (наприклад, `"XXКількість учасників перевищує місткість аудиторії.XX"`) або замінювала першу літеру на малу.
  Тести перевіряли помилки через `pytest.raises(..., match="...")`, а це пошук підрядка, тому змінений текст усе одно
  проходив перевірку.
- Решта (2 мутанти): `astimezone(timezone.utc)` → `astimezone(None)` для початку або кінця бронювання. Це еквівалентні
  мутанти: Python віднімає aware-дати з різними часовими поясами через їхні зміщення від UTC, тож результат
  функції не змінюється і розрізнити такий код тестом неможливо.
**Як ми його вбили**
- Для 9 мутантів із текстами повідомлень: замінили `match="..."` на перевірку повного тексту повідомлення через
  `match=f"^{re.escape(message)}$"` (допоміжна функція `assert_raises_message`). Тепер будь-яка зміна тексту, зокрема
  `XX…XX` і регістр, ламає тест. Також розділили перевірку на непрозорий початок і кінець (окремі тести для
  `naive_start` і `naive_end`).
- Тест на межу місткості: бронювання на 30 учасників в аудиторії на 30 місць (і на 31 в аудиторії на 30)
  перевіряє, що межа включна, і вбиває мутант `>` → `>=` у перевірці місткості. Додаткові випадки (1 з 1, 0 і -1 учасників)
  закривають межі `< 1`.
- 2 еквівалентні мутанти залишено навмисно, їх неможливо вбити без зміни поведінки коду.

**2) Варіант Мельник Дар'ї**
Ми застосували інструмент mutmut для перевірки надійності тестів модуля api/views.py.
**Оцінка мутації:**
- Більшість логічних мутантів (наприклад, зміна логічних операторів у перевірці прав `IsDispatcher`) були успішно "вбиті" наявними параметризованими тестами.
**Мутант, що вижив:**
- Мутатор змінив строкову константу "VALIDATION_ERROR" на інший рядок у функції get_validation_error_response. Мутант вижив, оскільки оригінальний тест test_validation_error_response_contains_field_name перевіряв виключно вкладене поле field у масиві details, ігноруючи перевірку головного коду відповіді.
**Як ми його вбили:**
- Ми дописали новий ізольований тест test_validation_error_response_has_correct_code, який містить прямий assert result["error"]["code"] == "VALIDATION_ERROR", тим самим закривши цю прогалину в покритті контракту.

### 2. Тести на основі властивостей (Property-based testing)
Ми застосували бібліотеку `hypothesis` для Python у наборі `tests/`.
* **Властивість:** Перевірка функції розрахунку тривалості бронювання. 
* **Пояснення:** Тест перевіряє, що для будь-якої згенерованої пари валідного часу `start_time` та `end_time` (де кінець завжди пізніше за початок), тривалість події завжди є додатною величиною, незалежно від високосних років чи переведення годинників.

### 3. Ворота покриття в CI
* **Поріг:** Ми налаштували перевірку `--cov-fail-under=75` у нашому CI-конвеєрі.
* **Пояснення:** Цей поріг обрано як баланс між надійністю бізнес-логіки та гнучкістю розробки.
* Він гарантує, що всі критичні доменні функції протестовані, але не змушує писати штучні тести для конфігураційних файлів чи простих DTO.
* У репозиторії є щонайменше один успішний прогін, де покриття склало понад 75%.
