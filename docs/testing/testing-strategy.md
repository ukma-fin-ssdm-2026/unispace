# Стратегія тестування команди SpaceOps

## Поточний статус тестування
На даному етапі в проєкті впроваджено базове автоматизоване модульне тестування для бекенду на Django. 
Ми використовуємо `pytest` для перевірки ключової бізнес-логіки, серіалізаторів (наприклад, `SyncLogSerializer`) та ендпоїнтів. 
Тести структуровані за шаблоном AAA (Arrange-Act-Assert) і використовують тестові дублери (моки) для ізоляції бази даних і зовнішніх залежностей. 
Статичний аналіз та перевірка стилю (black, flake8, bandit) вже інтегровані в процес розробки.

## Підсумок покриття
* **Загальний відсоток покриття:** ~80% (деталі у звіті `htmlcov/index.html`).
* **Що залишилося непокритим і чому:** Частково непокритими залишаються глобальні обробники винятків (`EXCEPTION_HANDLER`), оскільки їх тестування вимагає імітації низькорівневих збоїв фреймворку.
* Також без повного покриття залишається модуль прямого парсингу HTML-сторінок зовнішньої системи САЗ, оскільки для стабільності тестів ми наразі використовуємо моковані дані замість реальних HTTP-запитів до нестабільного ресурсу.

## Плани для інтеграційних, системних та приймальних тестів
* **Інтеграційні тести:** У наступних ітераціях ми плануємо перевіряти взаємодію між нашими сервісами та базою даних PostgreSQL (наприклад, коректність транзакцій при створенні бронювань).
* **Системні тести (E2E):** Планується використання Playwright або Cypress для автоматизації повних користувацьких сценаріїв (від кліка на фронтенді до запису в БД).
* **Приймальні тести (UAT):** Будуть проводитися вручну на staging-середовищі перед релізом для валідації User Stories (перевірка RBAC-авторизації, фільтрація аудиторій).

## Плани для тестування продуктивності, безпеки та property-based тестування
* **Безпека (Security):** Окрім інструментів `bandit` та `pip-audit`, які вже працюють, ми додамо автоматичні тести на спробу несанкціонованого доступу (403 Forbidden) для ролей без прав на модифікацію розкладу.
* **Продуктивність (Performance):** Застосуємо `Locust` для перевірки швидкодії системи під час масового запиту розкладу студентами (очікуваний час відповіді <500мс) та тестування логіки Circuit Breaker при ручному імпорті розкладу.

## Інтеграція у конвеєр CI/CD
Наші тести повністю інтегровані в GitHub Actions (файл `ci.yml`). Під час створення кожного Pull Request у гілку `main` конвеєр автоматично піднімає оточення, встановлює залежності та запускає `pytest`. Злиття PR неможливе, якщо тести падають або не проходять лінтери.

## Бонуси

### 1. Мутаційне тестування
Ми використали інструмент `mutmut` для Python на модулі валідації бронювань. 
* **Оцінка мутації:** Знищено 92% мутантів.
* **Мутант, що вижив:** Зміна логічного оператора з `<` на `<=` при перевірці місткості аудиторії.
* **Дописаний тест:** Написано тест, який створює бронювання рівно на межі місткості аудиторії (наприклад, 30 студентів для аудиторії на 30 місць), щоб вбити цього мутанта.

### 2. Тести на основі властивостей (Property-based testing)
Ми застосували бібліотеку `hypothesis` для Python у наборі `tests/`.
* **Властивість:** Перевірка функції розрахунку тривалості бронювання. 
* **Пояснення:** Тест перевіряє, що для будь-якої згенерованої пари валідного часу `start_time` та `end_time` (де кінець завжди пізніше за початок), тривалість події завжди є додатною величиною, незалежно від високосних років чи переведення годинників.

### 3. Ворота покриття в CI
* **Поріг:** Ми налаштували перевірку `--cov-fail-under=75` у нашому CI-конвеєрі.
* **Пояснення:** Цей поріг обрано як баланс між надійністю бізнес-логіки та гнучкістю розробки.
* Він гарантує, що всі критичні доменні функції протестовані, але не змушує писати штучні тести для конфігураційних файлів чи простих DTO.
* У репозиторії є щонайменше один успішний прогін, де покриття склало понад 75%.
