# Стратегія тестування команди UniSpace

## Поточний статус тестування
На даному етапі в проєкті впроваджено автоматизоване модульне тестування для бекенду на Django REST Framework.
Наразі успішно проходять 29 тестів (включно з тестами безпеки, зокрема перевірками на видалення), які покривають усі 5 поточних ендпоїнтів (аудиторії, вільні слоти, створення/скасування бронювань, бронювання користувача) та схему OpenAPI. Тестування реалізовано за допомогою pytest (у модулях test_views.py, test_audit_log.py та test_test_doubles.py, а також test_booking_rules.py і test_booking_properties.py для бонусів).). Тести ендпоїнтів, створення й скасування бронювань працюють із реальною базою даних PostgreSQL. Статичний аналіз коду та перевірки на безпеку (black, flake8, bandit, pip-audit) інтегровані в процес розробки.

## Тестові дублери та ізольовані юніт-тести

Для перевірки серіалізаторів і прав доступу ми застосовуємо ізольовані юніт-тести з використанням mock-об'єктів та APIRequestFactory 
(див. test_test_doubles.py). Такий підхід дозволяє тестувати валідацію даних і логіку дозволів без звернення до бази даних, 
не створюючи зайвого навантаження на неї, що робить ці тести швидкими, стабільними та незалежними від стану БД.

## Підсумок покриття
* **Загальний відсоток покриття:** ~95% (деталі у звіті `htmlcov/index.html`, який CI зберігає як артефакт coverage-html).
* Це вже перевищує цільовий поріг: у CI поріг налаштовано на 75% для балансу між надійністю та гнучкістю, а фактичне покриття його перевершує.
* **Що залишилося непокритим і чому:** Детальний перелік непокритих рядків дивіться у звіті htmlcov/index.html (колонка «missing»). Це переважно службовий код (наприклад, admin.py та apps.py), який не містить бізнес-логіки й не потребує окремих тестів.
* Імпорт розкладу із САЗ поки що не реалізований як парсер: наявні лише модель журналу синхронізації та ендпоїнти sync/ і sync-logs/, які ми тестуємо. Тести на сам парсинг з'являться разом із його реалізацією.

## Плани для інтеграційних, системних та приймальних тестів
* **Інтеграційні тести:** Розширення набору тестів, що працюють із реальною базою PostgreSQL, для перевірки транзакцій і конкурентного доступу, зокрема ExclusionConstraint для запобігання Race Condition при бронюванні однієї аудиторії.
* **Системні тести (E2E):** Після розробки фронтенду планується автоматизація повних користувацьких сценаріїв (від вибору слота на UI до запису в БД та генерації сповіщення).
* **Приймальні тести (UAT):** Ручна валідація на staging-середовищі, особливо для перевірки наскрізної автентифікації через Microsoft OAuth2 та коректності розподілу ролей.

## Плани для тестування продуктивності, безпеки та property-based тестування
* **Безпека (Security):** Окрім інструментів `bandit` та `pip-audit`, які вже працюють, ми додамо автоматичні тести на спробу несанкціонованого доступу (403 Forbidden) для ролей без прав на модифікацію розкладу.
* **Продуктивність (Performance):** Тестування швидкодії системи під час масового перегляду розкладу (очікуваний час відповіді <500мс) та перевірка відмовостійкості (Circuit Breaker) фонового завдання імпорту розкладу із САЗ.
* **Тестування на основі властивостей (Property-based):** вже реалізовано для правил бронювання (див. розділ «Бонуси»); надалі плануємо поширити їх на інші модулі, коли там з'явиться чиста бізнес-логіка.

## Інтеграція у конвеєр CI/CD
* Наші тести інтегровані в GitHub Actions (файл ci.yml). Під час створення кожного Pull Request у гілку main конвеєр автоматично піднімає оточення, встановлює залежності та запускає pytest із перевіркою покриття (--cov-fail-under=75). Конвеєр завершується помилкою, якщо тести падають, покриття нижче порогу або не проходять лінтери.

## Бонуси

### 1. Мутаційне тестування 
Ми використали інструмент `mutmut` 3 для Python на модулі правил бронювання `Backend/api/booking_rules.py`
(функції `booking_duration` і `validate_attendees_fit_room`). Запуск: `mutmut run` із папки `Backend/`.
**Оцінка мутації**
- Перший запуск: згенеровано 35 мутантів, знищено 24, вижило 11 (≈69%).
- Після підсилення тестів: знищено 33 із 35 (≈94%), вижило 2. Якщо не враховувати 2 еквівалентні мутанти,
  які неможливо вбити тестом, то 33 із 33 (100%).
* **Мутант, що вижив**
- Основна група (9 мутантів із 11): зміна тексту повідомлень про помилки. Мутація обгортала текст у `XX…XX`
  (наприклад, `"XXКількість учасників перевищує місткість аудиторії.XX"`) або замінювала першу літеру на малу.
  Тести перевіряли помилки через `pytest.raises(..., match="...")`, а це пошук підрядка, тому змінений текст усе одно
  проходив перевірку.
- Решта (2 мутанти): `astimezone(timezone.utc)` → `astimezone(None)` для початку або кінця бронювання. Це еквівалентні
  мутанти: Python віднімає aware-дати з різними часовими поясами через їхні зміщення від UTC, тож результат
  функції не змінюється і розрізнити такий код тестом неможливо.
* **Як ми його вбили**
- Для 9 мутантів із текстами повідомлень: замінили `match="..."` на перевірку повного тексту повідомлення через
  `match=f"^{re.escape(message)}$"` (допоміжна функція `assert_raises_message`). Тепер будь-яка зміна тексту, зокрема
  `XX…XX` і регістр, ламає тест. Також розділили перевірку на непрозорий початок і кінець (окремі тести для
  `naive_start` і `naive_end`).
- Тест на межу місткості (написано превентивно, у переліку вижилих цього мутанта не було): бронювання на 30 учасників в аудиторії на 30 місць допустиме, а на 31 у такій самій аудиторії відхиляється. Він вбиває мутант > → >= у перевірці місткості. Додаткові випадки (1 з 1, 0 і -1 учасників) закривають межі < 1.

### 2. Тести на основі властивостей (Property-based testing)
Ми застосували бібліотеку `hypothesis` для Python у файлі `Backend/api/tests/test_booking_properties.py`.
* **Властивість:** для будь-якої згенерованої пари валідного часу `start_time` та `end_time` (де кінець завжди пізніше
за початок) функція `booking_duration` повертає додатну тривалість, що дорівнює реальному проміжку часу, незалежно
від високосних років, часових поясів і переведення годинників.
* **Пояснення:** `hypothesis` генерує сотні пар aware-дат у діапазоні 2020-2035 (включно з високосними роками та датами
зміни часу) у 5 часових поясах. Додатково перевіряються властивості: перевернутий інтервал завжди відхиляється;
тривалість адитивна; кількість учасників до місткості аудиторії завжди допустима, а понад місткість ніколи.
Тривалість рахується в UTC, бо для aware-дат з однаковим tzinfo Python ігнорує перехід на зимовий час.

### 3. Ворота покриття в CI
* **Поріг:** Ми налаштували перевірку `--cov-fail-under=75` у нашому CI-конвеєрі(крок «Run tests with coverage and gate»).
* **Пояснення:** Цей поріг обрано як баланс між надійністю бізнес-логіки та гнучкістю розробки.
* Він гарантує, що всі критичні доменні функції протестовані, але не змушує писати штучні тести для конфігураційних файлів чи простих DTO.
* У репозиторії є щонайменше один успішний прогін, де покриття склало понад 75%: [CI Pipeline #371](https://github.com/ukma-fin-ssdm-2026/unispace/actions/runs/39688274707/job/119527773647)
