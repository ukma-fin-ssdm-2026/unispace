# Стратегія тестування команди UniSpace

## Поточний статус тестування
На даному етапі в проєкті впроваджено автоматизоване тестування бекенду на Django REST Framework: 21 тестовий модуль у `Backend/api/tests/` (244 тестові функції; параметризовані тести pytest розгортає в більшу кількість випадків) та 19 тестових функцій скриптів CI у `Backend/scripts/tests/`. Вони покривають усі ендпоінти API (аудиторії, бронювання, зміна аудиторії, підбір вільних аудиторій, попередня пара в аудиторії, розклад, аудит-лог, імпорт розкладу САЗ, вхід через Microsoft, журнал синхронізації) і доменні правила в `Backend/api/services/`. Тести ендпоінтів працюють із реальною базою PostgreSQL (у CI — сервіс postgres), бо правило накладок (`ExclusionConstraint`) існує лише в ній. Окремий тест `test_concurrent_bookings.py` запускає 10 паралельних запитів на один слот і перевіряє, що успішним є лише один (REL-001), а `test_booking_concurrency_errors.py` детерміновано перевіряє, що deadlock і serialization failure PostgreSQL дають 409, а не 500. Парсер САЗ (`test_saz_parser.py`) перевіряється на анонімізованій фікстурі `Backend/api/tests/fixtures/saz/schedule_preview.html` без звернення до справжнього САЗ, а імпорт і ендпоінт синхронізації (`test_saz_import.py`) — на реальній базі; `test_seed_demo.py` перевіряє команду створення демонстраційних даних. Кожен тест позначено міткою вимоги з `rtm.md`, а CI перевіряє простежуваність. Статичний аналіз коду та перевірки на безпеку (black, flake8, bandit, pip-audit) інтегровані в процес розробки.

## Тестові дублери та ізольовані юніт-тести

Для перевірки серіалізаторів, прав доступу й доменних правил ми застосовуємо ізольовані юніт-тести з mock-об'єктами та APIRequestFactory (див. `test_serializers.py`, `test_room_suggestions.py`, `test_room_occupancy.py`, а у `test_microsoft_auth.py` замість справжнього Microsoft — заглушка MSAL). Такий підхід дозволяє тестувати валідацію даних і логіку без звернення до бази даних чи зовнішніх сервісів, що робить ці тести швидкими, стабільними та незалежними від стану БД.

Доменні правила, на яких робили TDD, мутаційне тестування й тести властивостей, зведено в одне місце й підключено до кінцевих точок: правило місткості (`services/booking_rules.py`) використовує підбір аудиторій, перетин інтервалів (`services/scheduling.py`) визначає зайняті аудиторії в `GET /bookings/{id}/alternatives/`, а маркер «Змінено» (`is_recently_changed`) — розклад. Тож тести цих правил покривають код, який справді працює в API.

**Що залишилося непокритим і чому:**
* `management/commands/import_saz.py`: обгортка командного рядка над `run_sync()`; саму логіку імпорту перевіряє `test_saz_import.py`, а тесту на виклик команди (`call_command`) ще немає. Його варто дописати першим.
* `auth_views.py` (рядки 125–149): `dev_login` — вхід без Microsoft лише для локальної розробки (`DEBUG=True`), тестів на нього немає.
* `admin.py`: налаштування адмінки Django (відображення, inline, заборона редагування журналу) — свідомо не тестуємо, бо це не бізнес-логіка.
* `views.py`: фільтр `has_computers` у списку аудиторій, 400 на невалідне тіло `POST /bookings/` і `POST /bookings/{id}/change/`, 409 при зміні на недоступну аудиторію і 400 на невалідні параметри `GET /users/me/bookings/`. Прості гілки, їх варто дописати.
* `saz_parser.py` і `saz_import.py`: рідкісні гілки розбору (комірка з кількома абзацами, предмет без викладача, рядок без дня чи часу, сторінка без заголовка спеціальності, повторний пропуск уже зайнятої аудиторії).
* `serializers.py`: відмова для файлу розкладу понад 5 МБ; `bookings.py`: повторне підняття помилки бази, що не є конфліктом конкурентності (сама гілка перевірена в `test_booking_concurrency_errors.py` через `create_booking`, а для зміни аудиторії — ні).
* `models.py`: методи `__str__` моделей (використовуються лише в адмінці) — свідомо не тестуємо, бо вони не містять бізнес-логіки.
* `services/microsoft_auth.py`: `build_msal_app()` створює справжній клієнт MSAL, а в тестах його підмінено заглушкою, щоб не звертатися до Microsoft; також не перевірено відповідь Microsoft без `id_token` і збереження імені для вже наявного користувача без імені.

## Плани для інтеграційних, системних та приймальних тестів
* **Інтеграційні тести:** Конкурентний сценарій REL-001 (10 паралельних бронювань одного слота, `test_concurrent_bookings.py`) уже реалізовано на реальній PostgreSQL. Далі планується аналогічно перевірити паралельну зміну аудиторії (`POST /bookings/{id}/change/`) і паралельні запуски імпорту САЗ.
* **Системні тести (E2E):** Після розробки фронтенду планується автоматизація повних користувацьких сценаріїв (від вибору слота на UI до запису в БД та генерації сповіщення).
* **Приймальні тести (UAT):** Ручна валідація на staging-середовищі, особливо для перевірки наскрізної автентифікації через Microsoft OAuth2 та коректності розподілу ролей.

## Плани для тестування продуктивності, безпеки та property-based тестування
* **Безпека (Security):** Окрім інструментів `bandit` та `pip-audit`, які вже працюють, тести на спробу несанкціонованого доступу (403 Forbidden) для ролей без відповідних прав уже є (`BookingSecurityTests`, `test_audit_log_api.py`, `test_booking_previous_lesson.py`, `test_saz_import.py`); їх планується розширювати на нові ендпоінти.
* **Продуктивність (Performance):** Тестування швидкодії системи під час масового перегляду розкладу (очікуваний час відповіді <500мс) та перевірка відмовостійкості (Circuit Breaker) фонового завдання імпорту розкладу із САЗ.
* **Тестування на основі властивостей (Property-based):** вже реалізовано для правил бронювання (див. розділ «Бонуси»); надалі плануємо поширити їх на інші модулі, коли там з'явиться чиста бізнес-логіка.

## Інтеграція у конвеєр CI/CD
* Наші тести інтегровані в GitHub Actions (файл ci.yml). Під час створення кожного Pull Request у гілку main конвеєр автоматично піднімає оточення, встановлює залежності та запускає pytest із перевіркою покриття (--cov-fail-under=75). Конвеєр завершується помилкою, якщо тести падають, покриття нижче порогу або не проходять лінтери.

## Бонуси

### 1. Мутаційне тестування
Ми використали інструмент `mutmut` 3 для Python на модулі правил бронювання `Backend/api/services/booking_rules.py` (до рефакторингу — `Backend/api/booking_rules.py`)
(функції `booking_duration` і `validate_attendees_fit_room`). Запуск: `mutmut run` із папки `Backend/`.
**Оцінка мутації**
- Перший запуск: згенеровано 35 мутантів, знищено 24, вижило 11 (≈69%).
- Після підсилення тестів: знищено 33 із 35 (≈94%), вижило 2. Якщо не враховувати 2 еквівалентні мутанти,
  які неможливо вбити тестом, то 33 із 33 (100%).
* **Мутант, що вижив**
- Основна група (9 мутантів із 11): зміна тексту повідомлень про помилки. Мутація обгортала текст у `XX…XX`
  (наприклад, `"XXКількість учасників перевищує місткість аудиторії.XX"`) або замінювала першу літеру на малу.
  Тести перевіряли помилки через `pytest.raises(..., match="...")`, а це пошук підрядка, тому змінений текст усе одно
  проходив перевірку.
- Решта (2 мутанти): `astimezone(timezone.utc)` → `astimezone(None)` для початку або кінця бронювання. Це еквівалентні
  мутанти: Python віднімає aware-дати з різними часовими поясами через їхні зміщення від UTC, тож результат
  функції не змінюється і розрізнити такий код тестом неможливо.
* **Як ми його вбили**
- Для 9 мутантів із текстами повідомлень: замінили `match="..."` на перевірку повного тексту повідомлення через
  `match=f"^{re.escape(message)}$"` (допоміжна функція `assert_raises_message`). Тепер будь-яка зміна тексту, зокрема
  `XX…XX` і регістр, ламає тест. Також розділили перевірку на непрозорий початок і кінець (окремі тести для
  `naive_start` і `naive_end`).
- Тест на межу місткості (написано превентивно, у переліку вижилих цього мутанта не було): бронювання на 30 учасників в аудиторії на 30 місць допустиме, а на 31 у такій самій аудиторії відхиляється. Він вбиває мутант > → >= у перевірці місткості. Додаткові випадки (1 з 1, 0 і -1 учасників) закривають межі < 1.

### 2. Тести на основі властивостей (Property-based testing)
Ми застосували бібліотеку `hypothesis` для Python у файлі `Backend/api/tests/test_booking_properties.py`.
* **Властивість:** для будь-якої згенерованої пари валідного часу `start_time` та `end_time` (де кінець завжди пізніше
  за початок) функція `booking_duration` повертає додатну тривалість, що дорівнює реальному проміжку часу, незалежно
  від високосних років, часових поясів і переведення годинників.
* **Пояснення:** `hypothesis` генерує сотні пар aware-дат у діапазоні 2020-2035 (включно з високосними роками та датами
  зміни часу) у 5 часових поясах. Додатково перевіряються властивості: перевернутий інтервал завжди відхиляється;
  тривалість адитивна; кількість учасників до місткості аудиторії завжди допустима, а понад місткість ніколи.
  Тривалість рахується в UTC, бо для aware-дат з однаковим tzinfo Python ігнорує перехід на зимовий час.
